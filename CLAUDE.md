# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ContextTrail (PyPI package, import name and command `contexttrail`, short alias `ct`; the earlier working name `projectflow` survives only in compatibility identifiers: an existing `.git/projectflow/` state directory is still used, `projectflow-eval-v1` fixtures still load, and the tool's own `projectflow-run-` runner sessions stay excluded) reads local Codex, Claude Code and opencode transcripts plus Git history for one project, and uses an LLM (via the installed Codex or Claude CLI, sandboxed) to reconstruct an evidence-linked graph of goals, attempts, failures, and decisions. It is a development alpha (`0.1.0a9`). The README is English; most `docs/` are Korean. Console entry points `project`, `contexttrail`, and `contexttrail` all map to `contexttrail.cli:main`. With no command (or with a folder as the first argument) the CLI runs `view` on the current (or given) folder (`cli._default_command`); it never defaults to `analyze`.

## Commands

```bash
python -m pip install -e '.[dev]'          # add ,studio or ,langsmith extras as needed
scripts/test.sh -q                          # full suite; sets PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
scripts/test.sh tests/test_engine.py -q     # one file
scripts/test.sh tests/test_engine.py::test_name -q   # one test
scripts/contexttrail demo --path /tmp/contexttrail-demo --no-tui   # source-tree launcher; synthetic data + Mock Runner, no AI
scripts/contexttrail view /tmp/contexttrail-demo/sample-project
scripts/contexttrail scan /path/to/project       # input selection diagnostics, zero runner calls
scripts/contexttrail eval --fixture demo --runner mock --output /tmp/pf-eval   # offline eval of the demo story, writes review.html
python scripts/compare_models.py PROJECT --models claude:haiku claude:sonnet codex:gpt-luna codex:gpt-sol --units 5 --output /tmp/ct-compare --yes   # real models (needs consent): same units, one state copy per model
```

There is no linter/formatter configured. Tests use synthetic transcripts in temp dirs, loopback HTTP, and PTYs; they never call real AI accounts. Keep it that way — do not run `analyze`, `eval --runner codex|claude`, or `doctor --smoke` against real accounts without the user's explicit consent (they send data to a model service). Write any output/demo artifacts outside the repo.

## Architecture

**Pipeline (one engine, three log sources, two runners):**

1. `git_context.Scope.resolve()` normalizes the target folder, finds the Git common dir and linked worktrees. Path containment is by path components (`/app` ≠ `/app-backup`). State lives at `<git-common-dir>/contexttrail/<scope-key>/` (or `<folder>/.contexttrail/` without Git).
2. `sources/local.py` parses Codex (`CODEX_HOME`/`~/.codex` `sessions/`, `archived_sessions/`; `.jsonl`, and the `.jsonl.zst` Codex CLI 0.163+ writes once a transcript is about a week old, read through `decompress_zstd`: Python 3.14's `compression.zstd`, else the `zstandard` dependency, else the `zstd` command, else a limitation naming the file; a record's ID and hash do not depend on the file's path, so a transcript compressed after its analysis is not analysed again, and `jsonl_files` reads the plain copy while both exist) and Claude (`CLAUDE_CONFIG_DIR`/`~/.claude` `projects/`) JSONL into `model.SourceRecord`s, attributing each record to the scope by recorded `cwd`/`workdir` only — never by keyword guessing. `sources/opencode.py` does the same for opencode's SQLite database (`--opencode-home`, else `$XDG_DATA_HOME/opencode`, else `~/.local/share/opencode`; every `opencode*.db`, plus `OPENCODE_DB` only when the data directory is opencode's own), opened `mode=ro` + `query_only`, reading only `session`/`message`/`part` (the file also holds credential tables); a session is in scope by `session.directory` (a bash `workdir` overrides per call), `parent_id` plus the parent's `task` call give sub-agent lineage, a `compaction` part is the unit boundary and the `summary: true` assistant message after it is the summary, `synthetic`/`ignored` user text is metadata, reasoning is never collected, and `patch` parts become a metadata list of changed files. Its tool names are lowercase (`edit`/`write`/`read`/`bash`/`task`), so `EDIT_TOOL_NAMES`, `READ_TOOLS`, `DELEGATE_TOOLS` and the `filePath` key cover them. Tests build a synthetic `opencode.db`; the suite points `XDG_DATA_HOME` at a temp dir so no test opens a real one. Out-of-scope content is never sent to the LLM. A transcript too large to hold (over `MAX_FILE_BYTES`, 256 MiB, on disk or once decompressed; Codex or Claude Code) is read through line by line instead (`_streamed_rows`, up to `STREAM_MAX_BYTES`, the same line numbers, warnings and digest; `parse_codex` and `parse_claude` make one pass over the rows and take the session, entrypoint and sidechain mark from the first `SESSION_META_ROWS`, `_head`/`_session_meta`; a read cut short says so even for another project's file, `partial`), so another project's huge session is left out instead of reported unread; a check on a byte budget (`freshness.check` for `find`, the headers, the hook) does not stream (`stream_large=False`) and counts a file it did not read as not parsed (`since_scan.not_read`, `parsed` false; not kept in `freshness_cache`), so `status` reads it and the hook does not take the count as exact; a read to the cap is indexed by the file's size; the sub-agent link scan (`_claude_subagent_links`) parses only the rows that can carry a call or a launch result (`_jsonl(only=…)`). zstd is read frame by frame, every frame, from `ZSTD_INPUT_CHUNK` (4 KiB) of input at a time, which bounds what one piece unpacks to (about 128 MiB at zstd's highest ratio), and a file that ends inside a frame is refused (`_zstd_chunks`). `Engine.scan` passes a `ScanCache` (meta `scan_cache`): a transcript file that gave the project no records by its own content (not a Claude Code sub-agent awaiting its parent's link, `unlinked_subagent`; not a read an error cut short) and has the same size and mtime is not read again, its limitations and manifest replayed (`reused`; `scan`'s `transcript_files_reused`), unless a path it was attributed by (`paths`, noted by `_AskedScope`; a Codex tool workdir as the log wrote it, not only where a link pointed then) now falls in the scope; the whole cache is dropped when the reading code (`local.py`, `git_context.py`, `util.py`) or the scope's roots change (`scan_cache_key`, not the folder a worktree was opened from); on priceimpact the second scan took 18.5 s instead of 75.2 (743 of 819 files reused). Long records are split into ≤32k-char fragments (`segment_record`), binary payloads (including Codex `input_image` data URLs) replaced by digest markers. Every reader's records pass through `segment_record`, which first masks credential-shaped values as `[secret hidden]` (`util.mask_record`/`mask_secrets`: `sk-`/`ghp_`/`AKIA`/`xox`/`AIza` tokens, `Bearer` tokens, private key blocks, the value of `NAME_KEY=value`-style assignments, found from the name; a token right after a JSON escape `\n`/`\t`/`\r` starts a word) in the content and in the strings of `lineage` and `git` (both in the content hash); eval fixture records too (`evaluation.fixture_records`): line for line (citations keep their numbers), idempotent, never breaking a JSON string of a tool call's arguments, linear in the text (possessive value runs, `PRIVATE_KEY_MAX` 16 KB to an END line, else `PRIVATE_KEY_LINES` 100); so the scan, `freshness`, `note` (`journal.session_records`), the store, the model input and the exports read the same content and content hash. What an earlier version stored is masked as the store gives it out: `Store.graph` (`util.mask_data`; the masked text of the last version read is kept, `_shown`) and `Store.evidence`/`evidence_many` (`util.mask_evidence`: IDs and hashes as stored, `masked: true` and no `focus` when the quote changed), so every screen, export, session memory and the model's context read masked text without masking of their own; stored evidence rows are never rewritten, and the next published version stores the masked graph; `_rehydrate` masks the joined lines once more; `docs/SECURITY.md`. A forked Codex sub-agent's rows before `subagent_history_start_ordinal` are its parent's history and are skipped; a mid-file Codex compaction keeps its summary but not its `replacement_history` copy. Each record keeps who wrote it as its log says, `SourceRecord.authoring` (`model`, `effort`, `provider`; never guessed, empty when the log says nothing): Codex `turn_context` (`_codex_authoring`: the latest context before the record; Codex writes it before the person's prompt of that turn, so only the instructions injected before the first context stay empty) plus `session_meta.model_provider`, Claude Code assistant `message.model` with `perTurnEffort`/`effort` (a `<synthetic>` message has none; a tool result follows its call), opencode `providerID`/`modelID`/`variant` (a person's message from its `model`). It is outside the content hash (a later scan fills it in without re-sending a unit; `ingest` compares metadata) and in `HIDDEN_RECORD_FIELDS`, so the model never sees it. A session run with no person (`codex exec`: `session_meta` `originator: codex_exec`/`source: exec`; `claude -p` or an SDK: rows with `entrypoint: sdk-*`) gets `lineage.kind = unattended` with the tool as `agent_type`, so its user-role messages are not the person's (`is_user_prompt`); when its session ID appears in another session's tool call or result (`thread.started`, `session_id`), `_link_called_tools` (end of `collect_logs`) turns it into that call's sub-agent (`kind = subagent`, parent ids, `agent_type` kept). Lineage is in the content hash, so records newly read this way are analysed once more. A Claude Code session forked from another (`--fork-session`, resume) starts with a copy of the parent's recent rows (same `uuid`, the new session ID written over them): `_drop_forked_copies` (end of `collect_logs`, before `_link_called_tools`) drops a copy whose original is present (the parent is the session whose unshared rows start first; a fork with no parent here keeps its copies) and sets `SourceRecord.fork` (`from_session_id`, `point_at`: the last copied row's time) on the fork's own records, outside the content hash and hidden from the model. At publish, `schema.link_forks` hangs the fork's first request under the parent's last request before the fork point as a structural `follows` of origin `fork` with `fork_point_at` (drawn and listed as `갈라짐`/forked, never a cause). In the flow, when both the parent and the fork went on, the story up to the fork is one column and then the sides are drawn next to each other under a splitter (`diagram.branches_of`, `lanes_for`, `splitter`; a side has no margin rails, cross-side links are notes); with room for boxes at least `WIDE_BOX` (30) cells wide beside a side, results and sub-agent stacks stand beside its steps, else they fold into the step's box (status line, one magenta line per sub-agent event). Codex person-made forks copy nothing (`history_base`); Codex sub-agent forks skip the inherited rows.
3. `analysis.Engine` plans WorkUnits (by session/worktree, split on compaction, ≥3h gaps, window bounded by `unit_cost` and an estimated assembled payload (`estimated_payload`, 60% of `task_chars`), cut at the best safe boundary: after a successful commit result > before a person's message > after a run/test/commit/vcs result, never inside a tool call/result pair, so edit → run → result stay in one piece; stored `parsed` units with no result are re-cut under the current rule and the old ones marked `superseded`, `extracted` never; an integrated unit is re-planned only when one of its own records changed, never for context it merely saw), and reads each unit with **one model call, the story** (since 2026-10-20; the extract, integrate, review and light calls of pipeline v1 are gone, `docs/plans/PIPELINE_V2.md`). Code records the work first (`light.py`): the edits, checks and commits it finds in the tool calls (`light.skeleton(split_at_runs=True)`, from `tool_steps`) the tasks handed to other agents (`light.delegation_items`, `D1`…: each call of `analysis.DELEGATION_CALLS` — Codex `spawn_agent`/`followup_task`, Claude Code `Agent`/`Task`, opencode `task` — that was not refused, shown as `kind: delegation` with `delegated_to` and a one-line `task`; the story names it and a decision may point at it; since 2026-10-20), the other runs (`light.run_items`), and a structural `verifies` from an edit to a later check only when the check names every edited file (`light.covers`). `Engine.story_input` builds the story request (`light.story_request`): no tool output, only what the person and the assistant wrote cut into evidence blocks (`blocks.py`, `light.written_blocks`; the model cites `B12`, code turns it into exact lines with `light.cite`), the person's requests as `Q1`… (`light.request_items`; the session's last request before the stretch, whose turn it continues, as an open request `E…`, `light.open_requests`), the work outline (each item with `next_written`, the first block the assistant wrote after it; each edit with `later_runs`; the runs right after an edit with their `command` and last lines (a check fails on any nonzero exit status of its call, and a test run also on a failure count in its last lines, `light.check_failed`; a Codex-encrypted delegation message is no task text, `light.ENCRYPTED_TASK`), `light.readable_output` unwrapping Codex's `{"exit_code", "output"}` line; a Codex run returned still running settled by its later polls, also from a call that does more, `light._follow_polls`/`_poll_result`), and the existing events and edges (`Harness.context`, the graph-shaped lean context). `Engine._read_story` sends it (`Harness.task("story", …, schema=light.STORY_SCHEMA)`), and `light.story_extraction` turns the answer into an ordinary extraction: work named by the model (else `light.code_title` in the output language), story events (goal, decision with a reason only where a block gives one, proposal, finding/outcome, revision; no `actor`, every one is the assistant's; an ID that names a request, work item, block or existing event is refused), `checked_by` per edit read as claimed `verifies` kept only when `light.claimed_check` agrees (a run with a known result, after the edit in its session, a report block after the run), `requests[].answered_by` per request read as claimed `answers` kept only when `light.claimed_answer` agrees (a reply block of the assistant after the request in its session, before the session's next request for an open request, `light.turn_end`; never to a delegation item, which is the work, not the answer; answers of one request resting on the same reply blocks are one answer: the story event among them, else the last work item), a link written the wrong way round read the other way (`light.reversed_link`), and the turn summary (`graph["unit_summaries"]`) and the assistant blocks no story event cites (`graph["unclaimed_reports"]`). Before the checks, a candidate with the same kind and exactly the same cited records as one existing event becomes its duplicate (`match_existing_duplicates`: a unit read again after a record changed adds nothing twice). The extraction is published by code, with no model call (`Engine._integrate_unit`: `schema.draft_delta` through `apply_delta`), then **request turns** (code, no model; see below). `Harness.task` sends the Runner short IDs (`IdAliases`: `E3` for `ev_…`, whole string values only) and maps the reply back before any check, so everything stored uses full IDs. Every shown line longer than `LINE_CHARS` (1,500) keeps its head and its last `LINE_TAIL_CHARS` (400) with a note between (`shown_line`). `extract_request_data` (shared with the input preview) fills what the story is shown (`Harness.provide`, the ranges `light.cite` may cut from) and the person's requests; the selection audit (`context_selection`) stays with the ledger and preview. `tool_steps` outlines each tool call with an edit/read/run hint (run is refined to commit/test/vcs from the command line, `analysis.command_kind`, which leaves a heredoc's body out as data but reads the commands after its terminator, `drop_heredoc_bodies`; agent-coordination tools are `delegate`, a Codex `exec` that only calls `write_stdin` is `poll`, `web__run` is read). Every certain file edit (`hint=edit`, not failed) must be cited by some event, via `required_citations` (the work items cite them).
4. `schema.py` holds the JSON contracts, verifies that every cited quote actually exists in source (a citation is a line range; `quote` is optional, and `EvidenceValidator.fill_cut_quotes` keeps the shown lines within the range, at most `CUT_QUOTE_LINES`, as the quote when it is left out, `quote_cut_by_code`, so a wrongly copied quote is no longer a repair cause), and applies GraphDelta. Model output must pass this validation before it is stored or rendered. Only slips with a single possible reading are corrected in code and audited (`normalizations`): an exact quote at the wrong lines within lines the model was shown, a quote with one extra layer of escaping, event provenance fields (`recorded_at`, session/worktree ids) read from the cited sources, a `verifies`/`answers` written in reverse, a person's `goal`/`proposal` that an `answers` edge leaves (→ `question`/asked), an `actor=user` event resting only on user-role messages a calling agent wrote (a sub-agent's instructions, an unattended run's prompt; removed with its relations, `drop_caller_instructions`), a quote under `SHORT_QUOTE_CHARS` that appears exactly once in its cited lines, a quote off by whitespace, `...`-joined pieces or a run past a line end (each only when it has one reading in the cited lines), a quote repeated within 3 lines of the lines the model itself cited (stored as the lines holding every copy, `REPEAT_SPAN_MAX_LINES`; repeats farther apart are rejected with their line numbers for the repair), an integrated event whose `tool_record`/`observed_*`/`git_artifact` claim lost the tool or Git citation its own candidate carried (`restore_tool_evidence`), and a candidate resolved as `duplicate`/`updated` of items the same delta adds (→ `added`, `settle_in_delta_duplicates`). One claim is removed rather than repaired: a `verifies` between a documentation-only change and a run whose command never names that file (`drop_unchecked_doc_verifies`, noted in limitations); `tool_steps` flags such edits with `doc: true`. Claims a candidate's own citations do not back are read as the weaker claim they back (`settle_unbacked_claims`: unbacked `applied`/`observed_*` → `reported_complete`, unbacked `tool_record` basis → `git_artifact`/`explicit_statement`), and an extracted relation that breaks a `check_relation` rule is dropped into limitations (`drop_rule_breaking_relations`), both to save a whole-unit repair. The story's repair round sees only its answer's shape (`light.story_check`); an extraction the checks still refuse is salvaged: `salvage_extraction` keeps the candidates that pass on their own, names the dropped ones in limitations, and waives a required edit citation only when a dropped event had cited it.
5. `store.py` (SQLite in WAL mode, so the screen and browser keep reading during an analysis, + lock) publishes a new consistent graph version atomically (each version a whole graph, zlib-compressed behind `GRAPH_MARK` since state schema 2; text versions of schema 1 are packed once on open) and keeps the `llm_calls` ledger. Every publish first reads the code-derived fields again over the whole graph, from the cited records as stored now (`store.derive`: `fill_authoring`, `fill_steps`, `link_forks`, `link_delegations`, `fold_delegate_reports`; `Store.derived` gives that copy without writing). Completed units (including empty extractions) are never re-sent; re-running with no new records is a no-op with 0 runner calls, and `ingest` writes only rows that changed.

**A failing unit is skipped, not fatal.** A story answer that still fails its checks after the one repair round leaves the work code found on its own (`light.STORY_FALLBACK_LIMITATION`); a unit fails when nothing of its extraction passes the checks even after `salvage_extraction` ("story: nothing of this unit passed the checks"), when its draft fails the checks ("draft failed its checks"), or when its request is over `task_chars` (`InputBudgetExceeded`). In a CLI run `studio_graph._skippable` wraps the unit-level nodes: such a `TaskValidationError` or `InputBudgetExceeded` records the unit in the `unit_failures` meta (`_skip_unit`: kind, message, `Engine.failure_input` = routing signature + record hashes, integrated-unit count), the unit's remaining nodes pass, and `advance_unit` moves on; the run ends `partial`, or `failed` if no unit completed. `Engine._hold_back_failed` (at the end of both planners) leaves out a unit with the same signature and hashes unless `retry_failed`, and supersedes one whose session has notes; a retried unit joins `out_of_order_events` when other units were integrated since. Runner errors (`FlowError`), `CallLimitReached`, `Cancelled` and unknown exceptions are not skippable and stop the run; `BrokenOutput` (unreadable final JSON) is retried once inside `Harness.task`; any other exception a check raises on an answer is that answer's refusal (`answer check failed in code (<type>): …`, recorded with the call, repair round), never a stopped run. The calls of one `Harness.task` share the runner's conversation (`runner.thread()`: Codex persists the `exec` session in the run's temporary home instead of `--ephemeral` and the repair runs `codex exec resume`; Claude runs the first call with `--session-id` instead of `--no-session-persistence` and the repair with `--resume`; a follow-up carries only the `repair`, `Thread.follow_up`; a failed call resets it; usage of a resumed Codex call is the difference from the session's running total, a Claude call's is its own). On Linux the sandbox binds `<temp>/sessions` to `/pf-home/.codex/sessions` for this. `_can_start` (the routers) refuses a unit when the calls left are fewer than `MIN_UNIT_CALLS` (1; none if its saved extraction is valid); with no unit completed the status is `call_limit` (exit 2). The runner's `preflight` runs after the consent, before the first unit. `freshness` reports `failed_units` apart from `pending`. Messages: `skipped_unit_message`/`held_back_message`, English, in the `informational` list.

**Orchestration is a LangGraph graph.** `Engine.analyze()` delegates to `studio_graph.run_engine`, so the terminal CLI, `contexttrail eval`, and LangGraph Studio (`langgraph.json` → `studio_graph.py:graph`) all execute the same compiled node sequence (`prepare_run → scan_sources → classify_steps → plan_work_units → select_unit → prepare_extract_input → extract_model_and_validate → validate_candidates → publish_draft → link_request_turns → summarize_graph_changes → publish_result → advance_unit → finish_run`; `prepare_extract_input` shows the exact story request). Extraction runs side by side up to `--workers`. Changes to analysis flow usually touch both `analysis.py` (primitives) and `studio_graph.py` (node wiring/state).

**Runners** (`runners/cli_runner.py`): wrap the user's installed `codex`/`claude` CLI inside an isolation sandbox — bubblewrap on Linux, a deny-default `sandbox-exec` profile with a temp HOME on macOS. Only file-based auth (`auth.json`, `.credentials.json`) is bind-mounted read-only (opencode is a log source only, never a runner); if the sandbox or required CLI flags are unavailable the runner refuses to run (no unsandboxed fallback). `routing.py` provides the per-role runner pool and the host call budget (`--max-calls`, default 30; with a unit count it is `CALLS_PER_UNIT`×units unless `--max-calls` was given; per run, never saved). Before sending, a run shows `plan_summary`/`plan_text`/`plan_choices_text` (units, calls, tokens and minutes for 5/15/30 units; a quarter of the character estimate, `_TYPICAL_RATIO`, or calibrated from ≥3 past units read by the story call in the ledger) and asks via the `consent(snapshot, plan)` callback, which may answer with a unit count; the TUI asks from the analysis thread through `TerminalApp.confirm`/`ask_units`. Settings given as flags (runner, model, homes, budgets, language) are checked and saved for the project only by `analyze` (`cli._options(persist=…)`); `view`, `serve` and `scan` use them for that run, and a home flag naming no directory is refused. `--units N` fixes the count; `--session <id>|current` plans only that session and its sub-agents (events land in the graph's `out_of_order_events`). `--recent N` / `--since WHEN` (`AnalysisConfig.recent`/`since`, `analysis.recent_sessions`, `since_cutoff`; per run, never saved) widen that to several sessions through the same `family`/`in_scope` in `_plan_units` (`Engine._select_sessions`): the N most recent (latest record of the session and its sub-agents; a sub-agent follows its parent) of those without notes (sessions in `journal_sessions` are neither candidates nor counted), planned oldest first, and refused together with `--session`, `--audit` and `--trigger hook`; an empty selection is a `FlowError`. `Engine.ahead_of_order` (set by `_plan_units`: a record outside the chosen sessions still waits) decides `out_of_order_events` in `publish_result` for all three options, and `Engine.plan_fields` adds `plan.selection` (and the first line of `plan_text`) naming the sessions taken first. No model-visible text changes (`docs/plans/RECENT_SESSIONS_FIRST.md`). `scan` prints the plan without a model (`Engine.preview_plan`), with `reading transcript files N/M` on stderr when that is a terminal (`Engine.scan_progress`; counts only). A run always names its model (`DEFAULT_MODELS` in `cli_runner.py`; the sandbox hides the user's CLI config; Codex's default `gpt-luna` (Claude's `haiku`; the light models since 2026-10-17, measured against `gpt-sol`/`sonnet`), like any `gpt-<family>` without a version, is resolved in `preflight` to the newest listed `gpt-<version>-<family>` of `codex debug models --bundled` run in the sandbox, `newest_in_family`, and refused if none is found) and passes the reasoning effort (`--extract-effort`, default medium); both are recorded per call. `--extract-model`/`--extract-effort` set the story call's model and effort (saved per project; the names are those of the extract call they used to steer); never silently switch model or provider on failure. The story reads the graph-shaped lean context (`Harness.context`: `existing_*`, cited lines ±3 (a block over `CITED_BLOCK_CHARS` keeps only the cited lines), a few nearby records shown head and tail within `LEAN_CONTEXT_CHARS` (8,000), 6 related events and a 30-event index; every shown record leaves out the fields only code uses, `HIDDEN_RECORD_FIELDS`, `record_for_model`); a request over `task_chars` fails the unit. The saved settings of the retired calls (`cli.RETIRED_OPTIONS`: integrate/escalation models and efforts, context mode, unit thread, integrate evidence/output, review output, economy, light) are dropped from a project's options on the next write and read nowhere. Plan and measurements: `docs/plans/PIPELINE_V2.md` (§8), `docs/plans/REQUEST_ANSWERS.md`, `docs/plans/PERFORMANCE_PLAN.md`. `analysis.classify_steps` (node `classify_steps`, `scan` → `steps`) counts code-classified tool calls and the share of unplaced `run`s; no model call. `demo.py`'s Mock/Fixture runner (it answers only the story call, over the synthetic story of `demo.story_steps`) is only for synthetic fixtures and must not be selectable for real projects.

**Prompts** are Markdown in `src/contexttrail/prompts/` (`story.md`, the story call's system prompt; `repair.md`, the one repair round; `audit.md`, appended to the story's system prompt only in an audit), written in English, loaded via `analysis.prompt()`/`build_task()`. They ship as package data along with `assets/`. The story names each work item code found and writes only what code cannot see: goals, decisions (a reason only when a block states it), proposals, findings and conclusions the assistant stated (`reported_complete`), changes of course; a message that only restates recorded results is not an event, a finding that interprets them is. `light.skeleton` folds a same-turn repeat of the same check command with no edit between into one result. Every task carries `output_language` (`Engine.resolve_language`: `--language`, else saved per project, else `detect_language` from the person's messages, else the locale's language; a detected language is saved only after the consent, when units are about to be sent, and only when a message of the person's voted for it, so a `scan` preview or a declined run decides nothing): titles and summaries are written in it, quotes and identifiers stay as written. Everything else the model reads is English too, since 2026-10-06: validation messages (the repair round quotes them; `evaluation.error_kinds` counts the code-written head before the first `:`, so a message keeps a short, distinct English head) and the text code writes into the graph (dialog-turn rationales, unit warnings, dropped-candidate notes, `story:` limitations). The limitation and warning strings of a run are matched by the `informational` tuple in `analysis.py` to decide whether a run is complete. Changing any model-visible text is a model-input change.

**Session memory** (`session_context.py`, `contexttrail context`): the saved graph's summary given to the agent when a session starts, with no model call. Per project and opt-in (`context --enable`/`--disable`, meta `session_context`; `context [folder]` previews the text). `context --hook` is the entry point of the host's start hook (Claude Code and Codex `SessionStart`, answer `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": …}}`, the same shape for both; opencode's plugin posts it on `session.created` for top-level sessions through `client.session.prompt` with `noReply: true`); `install-hooks` merges it beside the Stop hooks with `auto_update._merge_hooks` (marker `CONTEXT_MARKER`, synchronous, `timeout` 10), `plugin_files` puts it into the plugin bundle. It prints nothing, creates nothing and exits 0 unless the project is opened and has it on. It opens the state with `store.ReadOnlyStore` (`mode=ro`, `immutable` when no `-wal`/`-shm` exists so no side file is left), never parses a transcript or reads every record: `freshness.lag` counts pending records in SQL (same number as `freshness.stored`, tested) and `freshness.cached_since_scan` adds the since-scan count an earlier `find`/`status` left in `freshness_cache` for the same scan. Choice and order reuse `agent_view.newest_first`/`event_row` and `render.status_labels`/`status_tones`: recent decision/action/revision events, open items, failed attempts without a later `revises`; at most `MAX_CHARS` (2,000) characters, English whatever the screen language (`session_context.english`). The text starts with `model.SESSION_CONTEXT_HEAD` (also in `HARNESS_TEXT`, since opencode posts it as a user message), then `agent_view.memory_note`, then a fenced data block; model-written titles are one quoted JSON string each and a status label that names a check is cut before that check's title (`docs/SECURITY.md`). Two copies of the hook (`install-hooks` plus the plugin) give a session its memory once (`first_time`, a lock and a mark in the state directory for 120 s). `source` is read for that key only; resumed sessions are not skipped (unverified). Plan and the record of what was checked in each tool: `docs/plans/SESSION_START_CONTEXT.md`.

**Host contract** (`contract.py`, `docs/HOST.md`, English): what a program driving the CLI relies on. Every JSON output carries `"schema": "contexttrail.<command>.v1"` (`SCHEMAS`: scan, status, find, show, note, note-list, doctor (on each array entry), ops, analyze, capabilities; `export` keeps `format`, and `export --since-version N` writes `contexttrail.export-delta.v1` from `render.graph_changes`/`export_delta`: events/edges/open items added, updated, invalidated (event `withdrawn`, edge made inactive, open item resolved) or removed between two stored versions, with their evidence; `--graph-version N` exports an older version). Fields are additive only; a schema name changes only when one is removed. `contexttrail capabilities` (always JSON) reads every command's arguments off the parser (`contract.commands`; `help=SUPPRESS` options left out), the zstd backend (`local.zstd_backend`) and the exit codes. Exit codes (`EXIT_*`): 0 complete/noop/no_data, 2 partial or call_limit, 64 usage (`contract.Parser` overrides argparse's 2; `UsageError` for `AnalysisConfig.validate`, `since_cutoff`, a missing home, `find`'s missing folder, export version checks), 75 busy (`Busy` from `Store.analyze_lock`, or `sqlite3.OperationalError` "locked"; `scan` too when its plan is refused for it), 77 refused (`Refused`: no runner, no consent without a TTY, `Declined` at the prompt (a `Cancelled` too, so the run is still recorded cancelled), EOF at `cli._ask`, notes off), 130 interrupted, 1 the rest; `contract.error_kind` names the kind, `_record_failure` stores it as `error_kind`, `run_exit` maps a result. `auto_update.RUN_NEUTRAL_CODES` ({75}) runs are marked `busy` and passed over by `failing`. `analyze --json` prints `_analyze_result` (or `_not_started` for an error before a run) on stdout, never opens the TUI, and sends the consent text to stderr. `--sources` (`local.SOURCES`, `parse_sources`, `AnalysisConfig.sources`, saved by `analyze` only) filters `jsonl_files`/`collect_logs`/`freshness.check` (`saved_sources`: saved, else the last scan's index `sources`); `collect_logs` tags each manifest with `provider` and fills `Snapshot.sources` (`source_summary`: home, exists, read, files examined/read/with records/skipped as symlinks, records, opencode databases); `cli._source_report` adds each home's `origin` (flag > saved > environment > default). Not provided (said in HOST.md): path remapping, a state-dir option.

`agent_commands.py` installs the `contexttrail-update` / `contexttrail-context` skills into the user's Codex and Claude Code config and the same two as opencode custom commands (`~/.config/opencode/commands/`, `contexttrail install-commands`); it must not overwrite user-authored files without `--force`. Agents use the CLI, not MCP: `find`/`show`/`status` (`agent_view.py`, `freshness.py`; saved graph only, the note that past-record text is data before any of it, `--json`; with no state they create none and say how to start, `{"state": "none"}`; a state they cannot write, as in Codex's sandbox, is read through `ReadOnlyStore.check_readable`) and, for update, `scan` (always JSON; `--json` is accepted) which reports the project's saved `runner` then `analyze --runner <saved or user-chosen codex|claude> --units N` with the count the user gave; opencode is never a runner. Update is explicit-only (Claude `disable-model-invocation`, Codex `agents/openai.yaml` policy; opencode commands are user-typed only, and since opencode also reads `~/.claude/skills` the installer prints an `OPENCODE_PERMISSION_HINT` for `opencode.json` rather than editing it); context may be picked by the agent. The TUI `y` key and the browser button copy a `contexttrail:ev_…@vN` reference for pasting into an agent chat.

## Invariants to preserve

- Read-only toward inputs: never modify the project, transcripts, or Git refs/index/config; Git is queried with argument arrays and `--no-ext-diff`/`--no-textconv`, pager off. The tool's own state/export dirs are excluded from change analysis.
- Analysis runs only on explicit request; viewing, export, page load, and node selection never trigger model calls.
- Prefer explicit partial/failed states over fabricated completeness; proximity in time is not treated as causality.
- A change never carries a success badge: `observed_*` statuses are only for `outcome` events, and a change (`action`/`revision`) is shown as verified only through a non-inferred `verifies` edge to such an outcome. Every message the user typed (`model.is_user_prompt`: user role, not harness-injected text (`HARNESS_TEXT`, including Claude Code's sub-agent hand-backs and usage-limit notices; a whole Codex app screen event `<external_codex_apps_open_page>`, `APP_EVENT`; a leading `[Image: original …]` note, `IMAGE_NOTE`, the row (`isMeta`) Claude Code writes after the agent reads an image file, not an image the person attached, is set aside) or a sub-agent, and not a message a program sent through the tool's queue: Codex `task_started` `turn_attribution.turn_trigger: "queue"`, what `codex queue` sends (a monitor's hourly report the agent set up), read by `_codex_queued` into `SourceRecord.authoring.trigger` (outside the content hash; `schema.authoring_of` leaves it out), `model.is_queued_message`, which ends the turn before it but makes no request) is a user event; the person's answer to the agent's own question (Codex `<send_user_message_question_reply>`, `model.question_reply`) is theirs but neither a request nor a turn boundary: it stays a written block, and `link_request_turns` makes it a user `decision` (adopted) only when the answer is one of the options the agent's `request_user_input` call offered (`offered_options`); questions and requests are `question`/`asked` (shown as 요청), answered via `answers` edges; a person's event `refresh` set aside (`schema.retired`: `withdrawn` with an `invalidation`) is no request anywhere (`is_request`, `story_view`, `request_turns`, the browser's request list, `link_forks`, `light.open_requests`, the labels). Code makes them, not the model (`light.request_items` in the story extraction; `link_request_turns` after publishing). `link_request_turns` also hangs each new event that no relation reaches from the user message of its turn in the same session (a sub-agent's work: the parent session's message just before it), as `follows` with basis `structural` and `origin: "dialog_turn"` (not drawn in the flow, where the column's order says it; labelled 대화 순서 in details): dialog structure, never a cause. A sub-agent's event that only such a link reaches hangs instead under the delegation event that gave its agent the task (`schema.link_delegations` at every publish, graph-wide since the parent's and the sub-agent's units publish in either order: a `follows` of origin `delegation`, 위임 in details, the turn links set inactive with `invalidation.replaced_by`); a delegation event (`step: delegate`, an `action` citing only delegation calls) reads `위임` with `위임함 · 하위 작업 N건`, not as an unverified change, and `graph_summary` does not count it as a change. Display labels are derived from these edges (`render.status_labels`).
- State dirs are `0700`, DB/exports `0600`. Transcripts, evidence exports, and browser access links are sensitive. Credential masking at reading (`util.mask_secrets`) covers known formats only; it is not a guarantee. Read `docs/SECURITY.md` before touching CLI isolation, auth handling, or browser endpoints.
