# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ContextTrail (PyPI package, import name and command `contexttrail`, short alias `ct`; the earlier working name `projectflow` survives only in compatibility identifiers: an existing `.git/projectflow/` state directory is still used, `projectflow-eval-v1` fixtures still load, and the tool's own `projectflow-run-` runner sessions stay excluded) reads local Codex, Claude Code and opencode transcripts plus Git history for one project, and uses an LLM (via the installed Codex or Claude CLI, sandboxed) to reconstruct an evidence-linked graph of goals, attempts, failures, and decisions. It is a development alpha (`0.1.0a6`). The README is English; most `docs/` are Korean. Console entry points `project`, `contexttrail`, and `contexttrail` all map to `contexttrail.cli:main`. With no command (or with a folder as the first argument) the CLI runs `view` on the current (or given) folder (`cli._default_command`); it never defaults to `analyze`.

## Commands

```bash
python -m pip install -e '.[dev]'          # add ,studio or ,langsmith extras as needed
scripts/test.sh -q                          # full suite; sets PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
scripts/test.sh tests/test_engine.py -q     # one file
scripts/test.sh tests/test_engine.py::test_name -q   # one test
scripts/contexttrail demo --path /tmp/contexttrail-demo --no-tui   # source-tree launcher; synthetic data + Mock Runner, no AI
scripts/contexttrail view /tmp/contexttrail-demo/sample-project
scripts/contexttrail scan /path/to/project       # input selection diagnostics, zero runner calls
scripts/contexttrail eval --fixture demo --runner mock --output /tmp/pf-eval   # offline eval, writes review.html
python scripts/prelive_walkthrough.py --output /tmp/pf-prelive-walkthrough
```

There is no linter/formatter configured. Tests use synthetic transcripts in temp dirs, loopback HTTP, and PTYs; they never call real AI accounts. Keep it that way — do not run `analyze`, `eval --runner codex|claude`, or `doctor --smoke` against real accounts without the user's explicit consent (they send data to a model service). Write any output/demo artifacts outside the repo.

## Architecture

**Pipeline (one engine, three log sources, two runners):**

1. `git_context.Scope.resolve()` normalizes the target folder, finds the Git common dir and linked worktrees. Path containment is by path components (`/app` ≠ `/app-backup`). State lives at `<git-common-dir>/contexttrail/<scope-key>/` (or `<folder>/.contexttrail/` without Git).
2. `sources/local.py` parses Codex (`CODEX_HOME`/`~/.codex` `sessions/`, `archived_sessions/`) and Claude (`CLAUDE_CONFIG_DIR`/`~/.claude` `projects/`) JSONL into `model.SourceRecord`s, attributing each record to the scope by recorded `cwd`/`workdir` only — never by keyword guessing. `sources/opencode.py` does the same for opencode's SQLite database (`--opencode-home`, else `$XDG_DATA_HOME/opencode`, else `~/.local/share/opencode`; every `opencode*.db` plus `OPENCODE_DB`), opened `mode=ro` + `query_only`, reading only `session`/`message`/`part` (the file also holds credential tables); a session is in scope by `session.directory` (a bash `workdir` overrides per call), `parent_id` plus the parent's `task` call give sub-agent lineage, a `compaction` part is the unit boundary and the `summary: true` assistant message after it is the summary, `synthetic`/`ignored` user text is metadata, reasoning is never collected, and `patch` parts become a metadata list of changed files. Its tool names are lowercase (`edit`/`write`/`read`/`bash`/`task`), so `EDIT_TOOL_NAMES`, `READ_TOOLS`, `DELEGATE_TOOLS` and the `filePath` key cover them. Tests build a synthetic `opencode.db`; the suite points `XDG_DATA_HOME` at a temp dir so no test opens a real one. Out-of-scope content is never sent to the LLM. Long records are split into ≤32k-char fragments (`segment_record`), binary payloads (including Codex `input_image` data URLs) replaced by digest markers. A forked Codex sub-agent's rows before `subagent_history_start_ordinal` are its parent's history and are skipped; a mid-file Codex compaction keeps its summary but not its `replacement_history` copy.
3. `analysis.Engine` plans WorkUnits (by session/worktree, split on compaction, ≥3h gaps, window bounded by `unit_cost` and an estimated assembled payload (`estimated_payload`, 60% of `task_chars`), cut at the best safe boundary: after a successful commit result > before a person's message > after a run/test/commit/vcs result, never inside a tool call/result pair, so edit → run → result stay in one piece; stored `parsed` units with no result are re-cut under the current rule and the old ones marked `superseded`, `draft`/`extracted` never; an integrated unit is re-planned only when one of its own records changed, never for context it merely saw), and `analysis.Harness` builds tasks, serves model `ReadRequest`s for extra evidence, and runs bounded repair. Stages: **extract** (candidates + quoted evidence per unit, parallelizable up to `workers`; with one worker the next unit is extracted in the background while the current one integrates, `studio_graph._prefetch_next`, skipped for a shared runner or a nearly spent budget) → **integrate** (serial, produces a GraphDelta against the current graph) → optional **semantic review** only when the delta raises `review_issues` (an `unlinked_observed_outcome` issue is settled in code, `resolved_in_code`, when the delta adds no `CHANGE_KINDS` event, since the answer is then always "nothing to link") → **request turns** (code, no model; see below). `Harness.task` sends the Runner short IDs (`IdAliases`: `S12` for `src_…`, `E3` for `ev_…`, whole string values only) and maps the reply back before any check, so everything stored uses full IDs. Long tool results, injected text and summaries go into the extract input as head and tail only (`_view`, `omitted` range readable via `read_records`; results of read-only calls get a 400/200-char head and tail); the person's messages, assistant text and tool calls always go whole, but every shown line is cut at `LINE_CHARS` (1,500) with a note (`shown_line`, counted by `unit_cost`). A saved quote is the whole cited lines with the cited part as `focus`; the model is shown that part within `SHOWN_QUOTE_CHARS` (300) (`shown_quote` in `_prompt_evidence`, marked `quote_is_part_of_lines`, and in the candidates the integrator sees, `candidates_for_model`), and a quote copied from it resolves to the same lines. The extract input also carries `user_requests` and `tool_steps` (`extract_request_data`, shared with the input preview): an outline of each tool call with an edit/read/run hint (run is refined to commit/test/vcs from the command line, `analysis.command_kind`; agent-coordination tools are `delegate`, a Codex `exec` that only calls `write_stdin` is `poll`, `web__run` is read). The selection audit (`context_selection`) stays with the ledger and preview; `model_context` keeps it out of the model payload. Every certain file edit (`hint=edit`, not failed) must be cited by some extracted event, via `required_citations`.
4. `schema.py` holds the JSON contracts, verifies that every cited quote actually exists in source, and applies GraphDelta. Model output must pass this validation before it is stored or rendered. Only slips with a single possible reading are corrected in code and audited (`normalizations`): an exact quote at the wrong lines within lines the model was shown, a quote with one extra layer of escaping, event provenance fields (`recorded_at`, session/worktree ids) read from the cited sources, a `verifies`/`answers` written in reverse, a person's `goal`/`proposal` that an `answers` edge leaves (→ `question`/asked), a quote under `SHORT_QUOTE_CHARS` that appears exactly once in its cited lines, a quote off by whitespace, `...`-joined pieces or a run past a line end (each only when it has one reading in the cited lines), a quote repeated within 3 lines of the lines the model itself cited (stored as the lines holding every copy, `REPEAT_SPAN_MAX_LINES`; repeats farther apart are rejected with their line numbers for the repair), an integrated event whose `tool_record`/`observed_*`/`git_artifact` claim lost the tool or Git citation its own candidate carried (`restore_tool_evidence`), and a candidate resolved as `duplicate`/`updated` of items the same delta adds (→ `added`, `settle_in_delta_duplicates`). One claim is removed rather than repaired: a `verifies` between a documentation-only change and a run whose command never names that file (`drop_unchecked_doc_verifies`, noted in limitations); `tool_steps` flags such edits with `doc: true`. Everything else is rejected into the one repair round; if the repaired extraction still fails, `salvage_extraction` keeps the candidates that pass on their own, names the dropped ones in limitations, and waives a required edit citation only when a dropped event had cited it.
5. `store.py` (SQLite in WAL mode, so the screen and browser keep reading during an analysis, + lock) publishes a new consistent graph version atomically and keeps the `llm_calls` ledger. Completed units (including empty extractions) are never re-sent; re-running with no new records is a no-op with 0 runner calls, and `ingest` writes only rows that changed.

**Orchestration is a LangGraph graph.** `Engine.analyze()` delegates to `studio_graph.run_engine`, so the terminal CLI, `contexttrail eval`, and LangGraph Studio (`langgraph.json` → `studio_graph.py:graph`) all execute the same compiled node sequence (`prepare_run → scan_sources → classify_steps → plan_work_units → select_unit → prepare_extract_input → extract_model_and_validate → validate_candidates → prepare_integrate_input → integrate_model_and_validate → route_semantic_review → [semantic_review_model_validate] → link_request_turns → summarize_graph_changes → publish_result → advance_unit → finish_run`). Changes to analysis flow usually touch both `analysis.py` (primitives) and `studio_graph.py` (node wiring/state).

**Runners** (`runners/cli_runner.py`): wrap the user's installed `codex`/`claude` CLI inside an isolation sandbox — bubblewrap on Linux, a deny-default `sandbox-exec` profile with a temp HOME on macOS. Only file-based auth (`auth.json`, `.credentials.json`) is bind-mounted read-only (opencode is a log source only, never a runner); if the sandbox or required CLI flags are unavailable the runner refuses to run (no unsandboxed fallback). `routing.py` provides the per-role runner pool and the host call budget (`--max-calls`, default 30; with a unit count it is `CALLS_PER_UNIT`×units unless `--max-calls` was given; per run, never saved). Before sending, a run shows `plan_summary`/`plan_text`/`plan_choices_text` (units, calls, tokens and minutes for 5/15/30 units; ×3 of the character estimate, or calibrated from ≥3 past units in the ledger) and asks via the `consent(snapshot, plan)` callback, which may answer with a unit count; the TUI asks from the analysis thread through `TerminalApp.confirm`/`ask_units`. `--units N` fixes the count; `--session <id>|current` plans only that session and its sub-agents (events land in the graph's `out_of_order_events`). `scan` prints the plan without a model (`Engine.preview_plan`). A run always names its model (`DEFAULT_MODELS` in `cli_runner.py`; the sandbox hides the user's CLI config) and passes a per-role reasoning effort (`--extract-effort`/`--integrate-effort`/`--escalation-effort`); both are recorded per call. Stage models are chosen via `--extract-model`/`--integrate-model`/`--escalation-model`; never silently switch model or provider on failure. Delta review runs by default on code signals (`analysis.REVIEW_SIGNALS`); `--no-review` skips it for one run. `--context-mode` (hidden; default `lean`, `full` restores the old input) shrinks the extract context to a graph-shaped view (`existing_*`) plus cited lines ±3 (a block over `CITED_BLOCK_CHARS` keeps only the cited lines), 2 preceding records and up to 3 nearby records of the other source type shown head and tail (`CONTEXT_HEAD_CHARS`/`CONTEXT_TAIL_CHARS`), within `LEAN_CONTEXT_CHARS`, and a small manifest; a wired request still over `task_chars` is trimmed step by step (`trim_step`, recorded as `input_trimmed`) and fails only when nothing is left to cut; `_routing_signature` includes the mode only when it is not the default, so finished units are not resent. Two more hidden options change only the integrate/review requests: `--integrate-evidence reuse` (opt-in) lets the integrator leave out evidence an input candidate already carries (`EvidenceValidator.reuse_candidate_evidence` fills it before every check), and `--review-output patch` (default since 2026-09-29; `full` restores the rewrite-the-whole-delta review) makes the delta review answer only its changes (`schema.merge_review_patch` folds them into the proposal, then the unchanged `apply_delta` runs). `--integrate-output` (hidden; default `draft` since 2026-10-02, `full` restores the old request) does the same for integration: `patch` sends a code-built `draft_graph_delta` (`schema.draft_delta`: every candidate added as extracted, a candidate matched to exactly one existing event as its duplicate) and the integrator answers only its changes; `draft` publishes that draft with no integrate call while the graph is still empty (falling back to `patch` if the draft fails the checks). In both patch requests the model sees the delta through `schema.delta_for_model`: an added item that is its candidate unchanged is named (`{"id", "candidate": "unchanged"}`), and a candidate resolution or change attribution whose evidence is exactly its candidate's own is shown without that copy (the candidates are already in the request; `candidate_evidence` marks a quote a candidate carries as `quote_in_candidates`, `candidate_quotes`), which is what kept a dozen-candidate unit under `task_chars`; the full delta stays in code for the merge and the checks (`expand_for_model_view` is only for the fixture runner), and the patch schema still requires evidence on anything the model writes. The patch-mode review request is the integrate request without `context_only` and `manifest` (`REVIEW_OMITTED`); full mode is unchanged. Plan and measurements: `docs/plans/PERFORMANCE_PLAN.md`. `analysis.classify_steps` (node `classify_steps`, `scan` → `steps`) counts code-classified tool calls and the share of unplaced `run`s; no model call. `demo.py`'s Mock/Fixture runner is only for synthetic fixtures and must not be selectable for real projects.

**Prompts** are Markdown in `src/contexttrail/prompts/` (`common.md` + stage files `extract.md`, `integrate.md`, `repair.md`), written in English, loaded via `analysis.prompt()`/`build_task()`. They ship as package data along with `assets/`. Every task carries `output_language` (`Engine.resolve_language`: `--language`, else saved per project, else `detect_language` from the person's messages): titles and summaries are written in it, quotes and identifiers stay as written. Everything else the model reads is English too, since 2026-10-06: validation messages (the repair step matches them by pattern, `schema.QUOTE_MISMATCH_HEADS` and the mismatch regex in `Harness.task`; `evaluation.error_kinds` counts the code-written head before the first `:`, so a message keeps a short, distinct English head), the limitation and warning strings that enter the extract input as `input_limitations` (matched by the `informational` tuple in `analysis.py` to decide whether a re-run is a no-op), read-request `denied` reasons, review questions, and the text code writes into the graph (dialog-turn rationales, unit warnings, dropped-candidate notes). Changing any of them is a model-input change.

**Screen language** (`i18n.py`): everything the person reads on the terminal, in the TUI, in the browser view and in `find`/`show` output is Korean or English, chosen once per process by `i18n.resolve`: `--language`, else `CONTEXTTRAIL_LANGUAGE`, else the project's saved output language, else the locale (`LC_ALL`/`LC_MESSAGES`/`LANG`), else English. Code calls `tr(ko, en)` at use time (never at import); label tables are `i18n.Labels`, which pick the language on each lookup. The test suite pins Korean (`conftest.korean_screen`), and a test of the English screen sets `i18n.set_language("en")` itself. Text the model reads and text written into the graph (titles, summaries, rationales, limitations) do not follow the screen language.

**Output surfaces** all read the stored graph and never call AI: `render.py` (internal safe Mermaid subset → text graph, own SVG layout, md/mmd/json export), `ui.py` (stdlib `curses` TUI; `R` is the only analysis trigger), `webview.py` + `assets/` (loopback-only server with an access token in the URL; no external CDNs), `eval_review.py`/`input_preview.py` (local HTML review of eval calls and exact model inputs). `ui.py`'s `FlowPanels` is shared by `contexttrail view/analyze` (`TerminalApp`) and `contexttrail graph` (`GraphApp`); it draws `diagram.flow_diagram` (boxes and labelled arrows; a result that leads nowhere sits beside the change it checks, others stay in the story column; margin rails arrive as `[02] 동기 ▶` naming the source box; unrelated sessions are separate flows; text is wrapped, never cut) and falls back to `render.terminal_graph` when the panel is too narrow. When the graph has user messages it shows one request's turn at a time (`diagram.request_turns`, `flow_diagram(only=…)`; `[` `]` move, `A` toggles the whole flow) with a request list on the left at ≥180 columns. Each `Cell` records the edge ids it draws (`Cell.edges`) so the selected box's links are lit and unlinked boxes dimmed. Event detail text comes from `render.event_detail` (`keys=True` numbers links 1–9 in `render.linked_events` order for number-key jumps, Backspace goes back), which non-TTY `contexttrail graph` output also prints without keys. All panel keys live in `FlowPanels.handle` and are listed by `?` (`ui.HELP`); keys typed in Korean input mode are mapped to their Latin key (`ui.latin`), and while help or a `/` search prompt is open `FlowPanels.modal()` routes every key to the panels before the screen's own R/B/Q. The mouse (off with `--no-mouse`) is clicks and wheel only; clicking a line or note follows its edge via `Cell.edges`. `langsmith_trace.py` (`--langsmith`, `--langsmith-content`) is a developer-only design aid, hidden from `--help`; it is not a user/deployment feature.

**Freshness** (`freshness.py`): `Engine.scan` saves a `source_index` (every transcript file's size and mtime as read, every in-scope opencode session's `time_updated`); `freshness.check` counts records the last scan ingested but no analysis processed (from the store) and, by parsing only new or changed files against that index, records written since the scan (`since_scan`: sessions, records, newest time, per source). `contexttrail status [--json]` prints it; `find`'s first line ends with `freshness.summary` (changed files parsed up to `FIND_BUDGET_BYTES`, else counted as "not parsed"); the TUI header and the browser status line show the same phrase once per graph version. The per-file counts of one check are kept in `freshness_cache`, keyed on the scan time and a digest of the stored records' hashes, so the next check re-reads only files that changed again (on this repository: 2.0 s → 0.3 s). Only counts, never estimates; a full re-parse of this repository's logs takes about 47 s, which is why the index exists.

**Automatic analysis** (`auto_update.py`): opt-in per project. `contexttrail auto-update --enable --runner codex|claude --units N [--cooldown 15m] [--max-runs-per-day K]` saves `auto_update` meta and the runner consent; every host hook runs `contexttrail auto-update` (folder from `--folder` or the hook's stdin JSON `cwd`), which always exits 0, never creates state for a project without one, and spawns a detached child `auto-update --run --folder F` (new session, stdin closed, log `auto-update.log` 0600) only when enabled, unlocked, pending, past the cooldown, under the daily cap and not `failing`; the child runs `analyze … --yes --no-tui --brief --units N --trigger hook` in-process and records its exit in `auto_update_state.runs` (exit 0 and 2 are fine: `--units N` always leaves a partial run), so after `FAILURE_STOP` (3) failed runs in a row the hook starts nothing until `--enable` is run again (which clears the run history, not the day's start count); `AnalysisConfig.trigger` lands in the run manifest. `install-hooks --claude|--codex|--opencode` merges a `Stop` hook into `~/.claude/settings.json` (`async: true`) and `~/.codex/hooks.json`, and writes the `session.idle` plugin `~/.config/opencode/plugins/contexttrail.ts`; user entries are kept, ContextTrail's own are replaced only with `--force`.

**Notes** (`journal.py`, `contexttrail note`): the agent that did the work writes one event of its own session, with no model call. Each `--quote` is found in the current session's records only (`session_records`: the transcript file named by the session ID, or that opencode session, `parse_opencode(session=…)`; `quotable` drops the note calls and their output), as the most recent record holding it, and the event goes through `check_extraction` → `draft_delta` → `apply_delta` → `link_request_turns` → `publish` under the analysis lock (refused at once, never waiting, while an analysis runs). Events and relations it writes carry `origin: "note"`; `--verifies/--revises/--answers/--motivates EVENT` add an explicit relation from that earlier event to the note. Records are stored with `Store.ingest(partial=True)`, which does not mark the project's other records unavailable. The session comes from `journal.current_session` (`CLAUDE_CODE_SESSION_ID` when `CLAUDECODE` is set, else the one of `CODEX_THREAD_ID`/`CLAUDE_CODE_SESSION_ID`/`OPENCODE_SESSION_ID` present), which `--session current` of `analyze` uses too. Plan and the remaining stages (skills, end-of-session hooks, keeping noted sessions out of analysis): `docs/plans/LIVE_JOURNAL.md`.

`agent_commands.py` installs the `contexttrail-update` / `contexttrail-context` skills into the user's Codex and Claude Code config and the same two as opencode custom commands (`~/.config/opencode/commands/`, `contexttrail install-commands`); it must not overwrite user-authored files without `--force`. Agents use the CLI, not MCP: `find`/`show`/`status` (`agent_view.py`, `freshness.py`; saved graph only, quotes fenced as data, `--json`) and, for update, `scan` (always JSON; `--json` is accepted) which reports the project's saved `runner` then `analyze --runner <saved or user-chosen codex|claude> --units N` with the count the user gave; opencode is never a runner. Update is explicit-only (Claude `disable-model-invocation`, Codex `agents/openai.yaml` policy; opencode commands are user-typed only, and since opencode also reads `~/.claude/skills` the installer prints an `OPENCODE_PERMISSION_HINT` for `opencode.json` rather than editing it); context may be picked by the agent. The TUI `y` key and the browser button copy a `contexttrail:ev_…@vN` reference for pasting into an agent chat.

## Invariants to preserve

- Read-only toward inputs: never modify the project, transcripts, or Git refs/index/config; Git is queried with argument arrays and `--no-ext-diff`/`--no-textconv`, pager off. The tool's own state/export dirs are excluded from change analysis.
- Analysis runs only on explicit request; viewing, export, page load, and node selection never trigger model calls.
- Prefer explicit partial/failed states over fabricated completeness; proximity in time is not treated as causality.
- A change never carries a success badge: `observed_*` statuses are only for `outcome` events, and a change (`action`/`revision`) is shown as verified only through a non-inferred `verifies` edge to such an outcome. Every message the user typed (`model.is_user_prompt`: user role, not harness-injected text or a sub-agent) is a user event; questions and requests are `question`/`asked` (shown as 요청), answered via `answers` edges. When the model skips one, code adds it (`add_user_requests` before integration, `link_request_turns` after). `link_request_turns` also hangs each new event that no relation reaches from the user message of its turn in the same session (a sub-agent's work: the parent session's message just before it), as `follows` with basis `structural` and `origin: "dialog_turn"` (drawn as one bracket per message, labelled 대화 순서 in details): dialog structure, never a cause. Display labels are derived from these edges (`render.status_labels`).
- State dirs are `0700`, DB/exports `0600`. Transcripts, evidence exports, and browser access links are sensitive. Read `docs/SECURITY.md` before touching CLI isolation, auth handling, or browser endpoints.
