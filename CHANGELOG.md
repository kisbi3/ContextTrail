# Changelog

All notable changes to ContextTrail are listed here, newest first. Dates are the dates the change landed on `main`. Measurements behind each entry are in `docs/plans/PERFORMANCE_PLAN.md` and `docs/DECISIONS.md`.

## Unreleased

### Added
- **`--recent N` and `--since WHEN`: analyze the latest sessions first.** For the first analysis of a big project: only the units of the N most recent sessions (or those that ended after an age such as `7d` or a date) and their sub-agents are planned, oldest first within them, and what they add is marked out of order while other records still wait; the project stays `partial` and a later ordinary run fills in the rest oldest first. A session is as recent as the latest record of it and its sub-agents (a Claude Code sub-agent's records, kept under its parent's session ID, do not make that session look like someone else's sub-agent); sessions with notes are not candidates and are not counted. The consent screen and `scan` (`plan.selection`) name the sessions taken first and how many units each has. The options are refused together with `--session`, `--audit` and `--trigger hook`, and an empty selection is an error, not a silent run. `--units`, `--max-calls`, skipped-unit hold-back and the call cap work as with `--session`. No model input changes. Design and decisions: `docs/plans/RECENT_SESSIONS_FIRST.md`.
- **`contexttrail note`: the agent that did the work writes an event itself.** No model is called. The agent gives the kind (`decision`, `proposal`, `goal`, `action`, `revision`, `outcome`), the status, a title, a summary and one or more `--quote`s copied from what it saw; code finds each quote in the current session's own records (one transcript file, or one opencode session; this repository's 3,790-record session parses in under a second), so the agent never names line numbers, and the note's own command line is never a source. The event then takes the analysis path unchanged: the candidate check, the code-built draft delta, `apply_delta` with every evidence, status and relation rule (an `observed_*` status still needs a quoted tool result), the dialog-turn links that also add the person's requests, and one `publish`. `--verifies`, `--revises`, `--answers` and `--motivates` name an earlier event (an ID, a prefix or a copied `contexttrail:ev_…@vN`) and add an explicit relation from it to the note. A note that fails a check stores nothing and says why, with the closest lines when a quote was not found; while an analysis holds the project's lock it is refused at once rather than waiting. `--list` shows the notes of the session, `--json` the stored event. Records are stored with a partial ingest that leaves the rest of the project's records as they were. Plan: `docs/plans/LIVE_JOURNAL.md` (stage A).
- **Notes are per project, with a skill and an end-of-turn reminder.** `contexttrail note --enable` turns them on (a note is refused while they are off). The `contexttrail-note` skill, installed with the other two into Claude Code and Codex and picked by the agent itself, says when and how to note. A synchronous `Stop` hook, `contexttrail note --hook` (installed by `install-hooks` next to the asynchronous auto-update hook), sends the agent back once when a turn edited files or ran tests, commits or Git changes after its last note; Claude Code's `stop_hook_active` and the time of the last reminder keep it to once, and in a project without notes it does nothing. The opencode plugin puts the session's ID into the tool shell (`OPENCODE_SESSION_ID`) and sends the same reminder on `session.idle`. The reminder text is never taken for a person's request.
- **Notes in a sandbox are queued.** Codex's default sandbox keeps `.git` read-only, where the project's state lives; `note` then checks its quotes and queues the note in the per-user temp directory with a `q_…` ID that later notes can link to, and the end-of-turn hook (outside the sandbox) stores the queue with every check, sending the agent back once with the reasons for any it refused (also shown by `note --list`).
- **Note checks found on first use in opencode and Codex.** `--session current` takes `OPENCODE_SESSION_ID` first (the plugin sets it per tool call) and, among the sessions the environment names, the first with records in the project, so a variable inherited from the shell that started the tool is passed over; a short output (`5`, `ok`) is quotable as its whole line; an `observed_*` quote is looked up in tool output before a message that repeats it; `--verifies` on a note that is not an observed outcome is refused at once with what to do; the observed-status error says where the quote was found.
- **A session with notes leaves analysis.** A note marks its session's records processed, every scan does the same for records the session writes later (and for its sub-agents), a stored unit with no result and nothing left pending is superseded instead of sent, and the freshness count leaves them out. Past sessions without notes are analyzed as before.
- **Claude Code plugin.** The repository is a plugin marketplace (`.claude-plugin/marketplace.json`, `plugins/contexttrail/`: skills `note`, `context`, `update` and both hooks), generated from the same skill text as `install-commands` (`scripts/build_plugin.py`; a test keeps them equal). `claude plugin validate` passes for both manifests, and installing it from GitHub (`claude plugin marketplace add kisbi3/ContextTrail`, then `claude plugin install contexttrail@contexttrail`) was checked live: the skills load as `contexttrail:note` and the others, and its reminder leads Claude to note.
- **Note checks found on first use of the plugin.** A shell command that writes a file (output sent to a file, `sed -i`, `tee`, `mv`, `rm`, `git apply` and the like; quoted code is not read as shell) counts as work to note, so an agent editing through the shell is reminded too; a change's quote is looked up in tool calls and results before a message that repeats the code, so the default `applied` status holds; and the hook runs one at a time per project, so with both `install-hooks` and the plugin the reminder is sent once and the queue stored once.
- **A unit that fails for its own reasons no longer stops the run.** Only failures that are the unit's are skipped: an answer that still fails validation after the repair round (`TaskValidationError`) and a request over the input budget with nothing left to trim (`InputBudgetExceeded`). The failure is saved (`unit_failures`) with the `_routing_signature` and the hash of each record, the run goes on with the next unit and ends `partial`, or `failed` when no unit completed. A skipped unit is not planned again while it is the same input (same signature, same record hashes), so a rerun with nothing else to do ends `noop` with no calls; a changed record, a changed setting or the new `analyze --retry-failed` sends it again, and then, if other units were integrated since, its events are marked in `out_of_order_events`. A runner error, the call cap and any unknown error still stop the run. An unreadable final JSON (`BrokenOutput`, Codex and Claude) is asked for once more as a call of its own. If the session has notes by the time a skipped unit would be sent, the unit is superseded and its failure forgotten. `status` and `find` count skipped units apart (`failed_units`; their records are no longer counted as waiting) and say how to send them again. **Calls:** a unit is not started when the calls left cannot carry it (an extraction and an integration; one when its saved extraction is still valid); a run that completed no unit ends with the new status `call_limit` (exit 2, like `partial`, so the automatic hook does not count it as a failed run) and a `stop_reason`. The runner's CLI, sandbox and login (`preflight`, no model call) are checked once after the consent and before the first unit. **Model input:** the new limitation lines (`skipped unit <id>: …`, `skipped units held back: N. …`, English, listed in `informational` so a rerun ends as a no-op) enter later units' `input_limitations` in a run that skipped a unit, and in every request of a run that holds one back; extractions already saved are not resent (`input_limitations` is not part of the context digest or the routing signature). Mock runner only; design record in `docs/plans/PERFORMANCE_PLAN.md` §16.
- **`analyze --audit`: check a noted session for what the agent left out.** It re-reads the records of sessions that have notes (and their sub-agents) that no analysis has covered, shows the model the existing notes, and adds only events, relations and open items they do not record; it never changes an existing event (`audit_guard` rejects an update, an invalidation or a resolve), and what it adds carries `origin: "audit"`. Units are cut like any session but stored as `audit_` units the ordinary plan and the cost calibration ignore; an edit no event cites is still required to be cited, one a note cites is not; a candidate with a note's kind and exactly its cited lines is settled as that note's duplicate in code; the semantic review is off; the run leaves `analysis_status` and `coverage` alone and is `complete` when no audit unit is left. `scan --audit` previews it with no model call, the usual consent and unit choice apply (the plan line says it is an audit), and the automatic hook never runs one. **Model input:** `prompts/audit.md` and `journal_audit.note_event_ids` ride on extract and integrate requests only in an audit; an ordinary request is byte for byte what it was. Tested with the mock runner only; a run with a real model is still to be checked locally. Design: `docs/plans/LIVE_JOURNAL.md` §11.
- **`status` and `find` say when noted sessions have not been audited.** `freshness.check` returns `unaudited` (`sessions`, `records`), counted from the store alone: stored records of sessions with notes (and their sub-agents) that no integrated unit covers, i.e. what `analyze --audit` would read. The header phrase adds "N noted sessions not audited", and `status` prints the `analyze --audit --units N` and `scan --audit` commands; the count is 0 after an audit. A record too large to send stays in the count.
- **Note checks found on first use of the plugin (2).** A `git fetch` that only refreshes remote-tracking refs (no refspec writing a local ref, no `--update-head-ok`) no longer counts as work to note, so a turn that only checked the remote is not sent back for a note; the filter lives in `journal.py`, and the analyzer's `tool_steps` still classify the call as `vcs` (no model input changes).

### Changed
- The note skill asks for one quote per edited file in a change note: a note that quoted only the commit line left its edits uncited, and a real-model audit of this repository wrote those changes a second time (3–4 of 125 added events).
- **Notes account for a session only from when they were turned on.** A noted session's records from before the earlier of the first `note --enable` and the oldest record a note cites (kept as `journal.since`, unchanged by `--disable`/`--enable`) stay with ordinary analysis, and records an earlier version marked processed are given back at the next scan unless an analysis covered them; `--audit` reads only the part since then, and a note adds request events only for that part. Found on this repository, where a session open since 2026-09-26 got its first note on 2026-10-07: about 105 units of earlier history had left ordinary analysis (108 → 213 units pending, audit 124 → 16).
- The audit prompt says the agent's `contexttrail note` calls, their output and the note reminders are bookkeeping of the graph, not project work (a real-model audit had written refused and retried notes as events). Model input change, audit requests only.
- Codex's wrapper for a Stop hook's message (`<hook_prompt …>`, Codex 0.16x) and the skill body Claude Code puts in the user role (`Base directory for this skill:`) are harness text, not a person's request; seen on the Codex re-check, where the note reminder had become a request event. Model input change: these messages no longer enter `user_requests`.
- Events are marked out-of-order (`out_of_order_events`) only while records outside the chosen session still wait. `--session` used to mark them always, also when nothing else was left to analyze.
- `--session current` reads `OPENCODE_SESSION_ID` too, and inside Claude Code (`CLAUDECODE` set) takes the Claude Code session even when a `CODEX_THREAD_ID` was inherited from the shell that started it.

### Fixed
- **The plan's token estimate counts Claude's cached input.** Calibrated from past runs, it summed only `input_tokens`, which the Claude CLI reports apart from the cached part (`cache_creation_input_tokens`, `cache_read_input_tokens`; often 2), so on a project analyzed with Claude it showed about a thousandth of the real input (on this repository: 114 tokens for 15 units, now about 4.5 million). The eval review and the LangSmith trace count the same way.
- **`file-history-delta` no longer warns as an unsupported Claude record type.** The parser skipped it but neither registry listed it, so every scan of a Claude log that had one reported an "unsupported record" gap. It is now in `IGNORED_NO_ANALYSIS_VALUE` next to `file-history-snapshot` (the edits themselves are the tool calls). The shape was not checked against a real log from this environment.

## 0.1.0a6 – 2026-10-07

### Changed
- **A request over the input budget is trimmed before it fails.** `Harness.task` now cuts, one step at a time and only while the wired request exceeds `task_chars`: background context records, then the quotes of existing evidence (marked `quote_omitted_for_budget`), then the cited-line context, then the manifest index (`trim_step`, `TRIM_STEPS`); the steps taken are recorded with the call as `input_trimmed`, and the unit fails only when nothing is left to cut. A request under the budget is unchanged.
- **Lean context is bounded.** A context-only record (the turn before, a commit near in time) is shown head and tail whatever its role (`CONTEXT_HEAD_CHARS`/`CONTEXT_TAIL_CHARS`; one 39,000-character commit record went into four units whole), the lines around a cited quote are 3 instead of 5 and a block over `CITED_BLOCK_CHARS` keeps only the cited lines, nearby records of the other source type are 3 instead of 4, and lean mode's context budget is `LEAN_CONTEXT_CHARS` (24,000) instead of `read_chars` (36,000). Full mode is unchanged. On this repository's 20 stored units the largest extract context went from 58k to 44k characters; the median stays near the budget, since the cited lines of the selected existing events fill it.
- **An observed result with no change to verify no longer goes to review.** The `unlinked_observed_outcome` signal asks whether a new observed result should be linked to a change with `verifies`; when the delta adds no change event (`action`/`revision`) the review's answer was always "nothing to link, noted in limitations" (5 of 16 reviews on this repository, none changing anything), so code now settles those issues (`origin: code`, audit status `resolved_in_code`) and writes the limitation itself. The review still runs for an unlinked revision, an update or an invalidation, and for an unlinked result when the delta does add a change.
- The manifest's event index sent with every extract and integrate request is the 60 most relevant events (`LEAN_INDEX_EVENTS`, was 100), so it stops growing with the graph, and an evidence entry's source metadata leaves out empty values and the default derivation.
- **Long lines and long quotes are shown cut.** A saved quote is the whole cited lines (partial quotes are canonicalized, the cited part kept as `focus`), so one 8,000-character line cited once was sent whole in every later request that showed that evidence; of this repository's 159 saved quotes, 30 were over 1,000 characters and the longest 14,474. The model is now shown the cited part (or the head) within 300 characters (`shown_quote`, marked `quote_is_part_of_lines`; the candidates the integrator sees carry the same short quotes, `candidates_for_model`), and a record line is cut at 1,500 characters with a note (`shown_line`; a minified file or a one-line JSON result slipped past the head/tail view whole, one 6-line record was 16,900 characters). The canonical quote stays in the store, a quote copied from the shown part still resolves to the same lines, and the unit planner counts the cut length. Together with the dedupe below, measured on this repository: the unit that overflowed went from extract 153k / integrate 259k / review 228k characters to 110k / 73k / 59k; another unit 187k / 168k / 159k to 159k / 113k / 70k.
- **The integrate and review requests stop repeating the candidates.** In the draft the model is sent, an added item that is its candidate unchanged is named (`{"id", "candidate": "unchanged"}`) instead of copied, and a `candidate_evidence` entry whose quote a candidate already carries is marked `quote_in_candidates` instead of quoted again; the patch-mode review (the default) no longer receives the records' context (`context_only`) and the manifest, which the integration already read, and judges on the candidates, their evidence and the existing events. Measured on this repository's units: the integrate request of a 12-candidate unit 196k → 128k characters, its review 228k → 113k; a live 9-candidate unit integrated at 126k (the ledger's median before was 168k). The review ran on 13 of 14 units here and changed items in 3, so its size was a third of every unit's cost. Model-input change; mock eval and live units checked.

### Fixed
- **A unit of a dozen candidates no longer overflows the integrate and review requests.** The code-built draft delta carried every candidate's evidence three times (in the item, its resolution and its attribution), and the integrated delta sent to the review did the same; on this repository one hook-started unit failed with "the analysis input budget was exceeded" at 259k characters against the 240k budget, before any integrate call. The model now sees a resolution or attribution whose evidence is exactly its candidate's own without that copy (`schema.delta_for_model`; the full delta stays in code for the merge and every check), and the patch instructions say so. The same unit's integrate request is 196k characters and its review 228k, and the run completes (graph v13 of this repository). Model-input change; mock eval and the live unit checked.

### Added
- **The hooks stop after repeated failures.** The detached process a hook starts is now `contexttrail auto-update --run`, which runs the analysis and records how it ended; after three failed runs in a row the hooks start nothing more, `contexttrail auto-update --status` shows the last result and the log path, and `--enable` again restarts them. A partial run (units left, which `--units N` always leaves) counts as fine.
- **`find` and `status` keep what they already counted.** The per-file counts of a freshness check are cached under the scan and the stored records they were measured against, so a second check re-reads only files that changed in between: on this repository 2.0 s → 0.3 s for the one growing session file.
- `scan` accepts `--json` (its output was already JSON), since the update skill and the docs say `scan . --json`; on 0.1.0a5 that flag was rejected.
- **Opt-in automatic analysis from the tools' hooks.** (All three hooks verified live on this repository on 2026-10-06; Codex's `hooks.json` uses the documented `{"hooks": {...}}` top-level object and Codex asks for trust before running a new hooks file.) `contexttrail auto-update --enable --runner codex|claude --units N` turns it on for one project (and records the consent); `contexttrail install-hooks --claude --codex --opencode` merges a `Stop` hook into Claude Code's settings (`async`) and Codex's `hooks.json`, and writes an opencode `session.idle` plugin. The hook command always exits 0 at once and starts a detached `analyze` only where enabled, unlocked, pending, past the cooldown and under the daily cap; runs carry `trigger: hook` in the ledger. Analysis still never runs without an explicit request: enabling is that request.
- The synthetic eval fixture now spans the three tools (Codex → opencode → Claude Code), so the mock pipeline exercises a cross-tool `motivates` relation. One real opencode session of this repository was analyzed live with the Claude runner (4 units, 11 calls, 2.5 min, one repair) and read back from Claude Code with `find`.
- **opencode commands and a saved runner.** `install-commands` also writes `~/.config/opencode/commands/contexttrail-update.md` and `contexttrail-context.md` (opencode runs custom commands only when the user types them) and prints the `permission.skill` line for `opencode.json` that makes the update skill, which opencode also sees in `~/.claude/skills`, need approval there. The update skill no longer says "Codex only": `scan --json` reports the project's saved `runner`, the skill uses it, and asks the user for Codex or Claude when none is saved. The context skill says the graph holds the work done in every tool and that an unanalyzed period is not answered from the graph.
- **The graph says how far it lags.** `contexttrail status` counts the records the last scan ingested but no analysis has processed, and the sessions and records written since that scan, per source, with the newest time; `find`'s first line ends with the same phrase (`up to date`, or the counts), as do the TUI header and the browser status line, and the `contexttrail-context` skill tells the agent to say so before answering and not to answer from the graph about the unanalyzed period. The check parses only files that are new or changed since the scan's `source_index` (size, mtime; opencode session update times), because a full re-parse of this repository's logs takes about 47 s; `find` stops parsing above 128 MB of changed files and reports the file count instead. Counts only, no estimates.
- **opencode as a third log source.** `sources/opencode.py` reads the opencode SQLite database (`$XDG_DATA_HOME/opencode` or `~/.local/share/opencode`, override with `--opencode-home`; every `opencode*.db` and `OPENCODE_DB`) read-only, from the `session`, `message` and `part` tables only. Sessions are attributed by their recorded directory, sub-agent sessions keep their parent and the `task` call that started them, a compaction becomes a work-unit boundary followed by its summary, `synthetic`/`ignored` text and attachments are metadata, reasoning is never collected. `scan` counts records per source. On this repository the real database (4 of 11 sessions in scope, 1,936 records) parsed in 0.4 s and its files were unchanged afterwards.

## 0.1.0a5 – 2026-10-06

First release under the `contexttrail` name on PyPI.

### Changed
- **One name: ContextTrail.** The PyPI package, the import name and the command are `contexttrail`, with `ct` as a short alias; the `project` and `projectflow` commands and the "Project Flow" product name are gone. Version `0.1.0a5`. Compatibility kept: an existing `.git/projectflow/` (or `.projectflow/`) state directory is still used, `projectflow-eval-v1` fixtures and `projectflow-eval-report-v1` reports still load, and the tool's own `projectflow-run-` runner sessions stay excluded from analysis. `install.sh` links `ct` and removes `project`/`projectflow` links that pointed at this install.

### Added
- **English screen text.** The terminal output, TUI, browser view, CLI help, `find`/`show` output, eval review and input preview are in English or Korean, chosen once per process (`i18n.resolve`): `--language`, else `CONTEXTTRAIL_LANGUAGE`, else the project's saved output language, else the locale, else English. Korean output is byte-identical to before. Text the model reads is now English in one language, no switch: validation messages returned for repair, the input-scope limitations and log-parser warnings that enter the extract input, read-request denials, review questions, and the text code writes into the graph (dialog-turn rationales, unit warnings, dropped-candidate notes). Message shapes and the matchers over them (`QUOTE_MISMATCH_HEADS`, the `informational` tuple, `error_kinds`) changed together. This is a model-input change; the owner's evaluation is pending. The synthetic demo's content is still Korean.
- The synthetic demo has an English story, chosen by the screen language (`demo.cases()`); the mock runner recognises both.
- README rewritten for a first-time reader: what goes in and what comes out on the demo, the same on a real stretch of this repository's own logs, what the tool does and does not do, then install; the measured-numbers table moved to its own section. A TUI screenshot (`docs/images/tui-demo-en.png`) is drawn without a terminal by `scripts/tui_screenshot.py`.
- `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, root `SECURITY.md`, issue and pull-request templates, a `publish` workflow (PyPI Trusted Publishing on a `v*` tag) and `docs/guides/RELEASING.md`.

### Changed

## 2026-10-02 – 2026-10-03

### Changed
- **Integration publishes a code-built draft by default** (`--integrate-output draft`). While the graph is empty the draft is published with no integrate call; against an existing graph the model answers only its changes to the draft (`patch`). On the `repairfix-v2` fixture with Claude Sonnet this halved time and tokens at the same score (`PERFORMANCE_PLAN.md` §12–14). `full` restores the old whole-delta request.
- Relation `basis` is defined in the prompts (explicit / structural / inferred) and `verifies` must be explicit or structural with a covering quote; the repair prompt asks for the quote or removal. `verifies…inferred` rejections went from 4 of 5 runs to 0.
- A quote inside one line is asked to cite exactly that line, not neighbouring lines.
- The integrate prompt states that a resolution targets items of the candidate's own kind and that a new event closing an old open item goes through `open_items_to_resolve`.

### Fixed
- Bookkeeping slips with a single reading are now settled in code and audited instead of costing a repair call: a candidate marked `duplicate` of an item the same delta adds becomes `added`; a relation no candidate names is attributed to the event candidates at its ends; a review patch that removed an item no longer leaves dangling resolutions or attributions; a new event may close an open item it was not opened on.
- A quote repeated within three cited lines is stored as the lines holding every copy; repeats farther apart are rejected with their line numbers so the repair can pick one.
- A `verifies` between a documentation-only change and a run whose command never names that file is dropped and noted in limitations.
- Tool and Git citations a candidate carried are restored when the integrator leaves them out.

### Eval and ops
- `report.json` splits the score by cause (events missing / split / merged; relations scored / unverifiable), sums every token kind the provider reports (including Claude cache tokens), and records where repeated quotes sat. Hidden `eval --unit-records N` splits a fixture into several work units.

## 2026-09-30
