# Changelog

All notable changes to ContextTrail are listed here, newest first. Dates are the dates the change landed on `main`. Measurements behind each entry are in `docs/plans/PERFORMANCE_PLAN.md` and `docs/DECISIONS.md`.

## Unreleased

### Fixed
- **A note written while an analysis runs waits instead of being refused.** The end-of-turn hooks start an automatic analysis and ask for a note at the same moment, and the analysis held the project for about a minute, so the note the reminder asked for was refused ("an analysis is running … Run the same note again in a minute"). `contexttrail note` now queues it (the same queue a read-only sandbox uses) and the next end-of-turn hook stores it once the analysis is done; while it waits the reminder counts it as written.
- **Writing outside the project is not work to note.** The reminder counted every shell line that writes a file, so a turn that only wrote to a scratch folder or `/tmp` was sent back for a note. With the project known, `journal.writes_files` places each write (`write_targets`: redirects and `rm`/`mkdir`/`touch`/`truncate`/`tee`/`cp`/`mv`/`sed -i`, variables set earlier on the line and `~` expanded, the body of a heredoc fed to `cat`/`tee` read as data) and leaves out a line whose every write lands on an absolute path outside the project; an edit of an absolute path outside it is left out too. A write it cannot place (a relative or quoted path, code that writes) still counts.

## 0.1.0a8 – 2026-10-16

### Added
- **A forked conversation is drawn as two sides.** When a story holds a fork (`schema.link_forks`, the edge carries `fork_point_at`) and both the parent and the fork went on, the flow draws the story up to the fork in one column, then a splitter line (`├────┐ 갈라짐`, each column captioned with its session: `세션 e263… 이어짐`, `갈라진 세션 d790…`) and the parent's continuation and each forked session side by side, each in its own column in time order (`diagram.branches_of`, `lanes_for`, `splitter`). A link between two sides is written inside both boxes; a side has no margin rails, its turn links are its order. When each side has room for boxes at least 30 cells wide beside it (`WIDE_BOX`), results and sub-agent stacks stand beside the side's steps as usual; otherwise they fold into the step's box: a result stays in the status line (`검증: pytest 496 passed`) and a sub-agent's work becomes one magenta line (`→ 하위 Explore · 로그 조사`). When only one side went on, or the sides would not fit at all, the fork is a `갈라짐` link in one column as before. The owner's sketches and the mocks are in `docs/DECISIONS.md` (2026-10-15).
- **A forked Claude Code session is one conversation, not two.** `--fork-session` and resume write a new session file that begins with a copy of the parent's recent rows (same `uuid`, the new session ID written over them, slug and prompt IDs regenerated) before the session's own rows; those copies were read as new records and analysed again (this repository's graph had nine parent rows with duplicate events in two sessions). Now `_drop_forked_copies` drops a copy whose original is present (the parent is the session whose unshared rows start first; a fork whose parent is gone keeps its copies, the only text of that history) and sets `SourceRecord.fork` on the fork's own records: the parent session and the time of the last copied row (`point_at`), outside the content hash (no unit is sent again) and hidden from the model. When a graph is published, `schema.link_forks` hangs the fork's first request under the parent's last request before the fork point as a structural `follows` of origin `fork`, so the fork joins the parent's flow; the flow and the detail call that line `갈라짐`/forked and never a cause. Copies ingested earlier become unavailable records, as a Codex fork's inherited rows did; their old duplicate events stay. Codex: a person's fork copies nothing (`history_base`), a sub-agent's fork already skipped its inherited rows.
- **A sub-agent's box, and a tool another session's call ran, say so.** A run with no person at the terminal is read off its own log: Codex `session_meta` `originator: codex_exec`/`source: exec`, Claude Code rows with `entrypoint: sdk-*` (`claude -p`, an SDK). Its records carry `lineage.kind = unattended` with the tool's name as `agent_type`, so its user-role messages are no longer the person's requests (`is_user_prompt`); before, a review prompt Claude Code sent to `codex exec` became a request box. When that session's ID appears in another session's tool call or result (`codex exec --json` prints `thread.started`, `claude -p --output-format json` a `session_id`), `_link_called_tools` makes it that call's sub-agent (`kind = subagent`, parent session and call, `agent_type` kept), so it is planned, hung under the parent's message and shown like one; nothing is matched by time. An event's `authoring` now carries the `role` (`subagent`/`unattended`) and the sub-agent's name as each tool records it (Claude Code `agent_type`, Codex `agent_nickname`/`agent_role`, opencode `agent`). In the flow, such a box's header names whose work it is (`[05] 결과 · 하위 Explore`, `[07] 결과 · codex exec`), its border is magenta (`sub` style) whatever its status, and it stands beside the parent's next story step as a stack of boxes on the right joined by one line into that box (`◀──┬─Explore───┤`; the owner's sketch), so the story column keeps only the session's own steps — layout, never a relation, a relation to or from such a box is a note in both boxes; the agent line reads `claude › Explore · sonnet-5-5 · high`, or `codex exec · 사람 없음 · gpt-6.1-sol` when the caller was not found; a model's name drops the tool's own prefix. **Model input:** `common.md` explains `lineage.kind=unattended` and the called-tool case of `subagent`; the records of a session newly read as unattended change their lineage, so their units are analysed once more (`docs/DECISIONS.md` 2026-10-15).
- **Each event names the agent that did the work.** Every record now keeps who wrote it as its log says (`SourceRecord.authoring`): Codex's `turn_context` model and effort (and the session's `model_provider`), Claude Code's assistant `message.model` with the turn's effort (`perTurnEffort`, else `effort`; a `<synthetic>` message has none, and a tool result follows the call that model made), opencode's `providerID`/`modelID`/`variant` (an assistant message's own, a person's message from its chosen `model`). Nothing is guessed: a record whose log says nothing stays empty. The field is outside the content hash, so filling it in for stored records does not send their units again (the next scan writes it, as `ingest` compares metadata), and it is hidden from the model (`HIDDEN_RECORD_FIELDS`), so model input is unchanged. When a graph is published, code reads each event's `authoring` off the records its evidence cites (`schema.fill_authoring` in `Store.publish`: the tool, then the model, effort and provider; unique, sorted; Git records have none), for new events and for every older event whose records have been read again. Shown in the flow box under the status (`codex · gpt-6.1-sol · high`; a person's box names only the tool), in the event detail and `show` as `에이전트:`/`agent:`, in the browser detail, and in `find`/`show --json` as `authoring`. Separately, each event a unit adds is stamped with the analysis model that wrote it (`analysis`: runner, model, effort from the call ledger; `studio_graph._analysis_of`), shown only in the detail and `--json` as `분석:`/`analysed by:`, never in the flow (`docs/plans/OPENCODE_SOURCE.md` §2, `docs/DECISIONS.md` 2026-10-15).
- **The flow reads as one line in time.** In the terminal flow, two neighbouring boxes of the story column with no relation between them are now joined by a dotted, unlabelled line (`┊ ▽`, ASCII `:`), so the story reads from the first event to the last; a relation keeps its solid, labelled line, and results checking a change still sit beside it. The dotted line is order only, never a cause, carries no link (selecting a box does not light it) and never joins two separate flows.
- **`--light`: one model call per unit, evidence linked by record ID (saved per project).** Code builds the skeleton from the tool steps: a change per run of edits in a turn, an observed result per test run (failed by its exit status, else by a failure count; `light.check_failed`), a change per commit, and a structural `verifies` from the turn's last code edit to a test run after it. One model call gets the unit's records and that skeleton and answers with a title and summary per skeleton item and the events code cannot see (decisions and reasons, proposals, goals, explained failures), each naming its records by ID and, optionally, a line range. Code cuts the cited lines itself (`light.cite`, at most 20 lines of what was shown), so a citation is always source text and never fails to match; no quote matching, no repair round, no integrate or review call (`prompts/light.md`, `light.LIGHT_SCHEMA`; an audit still uses the full extraction). Repair-fix fixture, Codex `gpt-6.1-sol`, 2 runs: 10 and 10 of 18 (events 7/9 each, no expected relation), 2 calls, about 2 model minutes and $0.13 each, against the default's 13·14·13, 5–6 calls, 7–12 minutes and $0.46–0.71 (`docs/plans/PERFORMANCE_PLAN.md` §19).
- **Project memory at session start: `contexttrail context --hook`.** With `contexttrail context --enable` (per project, off by default) the host's start-of-session hook puts a summary of the saved graph into the agent's context, with no model call: the most recent decisions and changes, the open items, the latest failed attempts that no later revision fixed, the number of records the last scan left unanalyzed (plus the since-scan count an earlier `find`/`status` kept), and how to look further (`find`, `show`); at most 2,000 characters, English, every item with a `contexttrail:ev_…@vN` reference. `contexttrail context` previews the text. What the graph holds was written by a model from past records, so it is treated as data: each title is one quoted JSON string inside a fenced block announced as past records, not instructions, and summaries and quotes are left out (`docs/SECURITY.md`). The text begins with a fixed phrase listed in `model.HARNESS_TEXT`, so opencode, which posts it as a user message, does not make it a request event. In a project where it is off or that was never opened, the hook prints nothing, creates nothing and exits 0; it reads the state through the new `store.ReadOnlyStore` (no write, no `-wal`/`-shm` left behind) and counts records in SQL (`freshness.lag`, the same number as `freshness.stored`; 60,000 synthetic records: 0.04–0.07 s against 1.2 s), never parsing a transcript. `install-hooks --claude|--codex` merges a synchronous `SessionStart` hook beside the Stop hooks (user entries kept, `--force` replaces ours), `--opencode` adds a `session.created` branch to the plugin (`session.prompt` with `noReply`, top-level sessions only), and the Claude Code plugin bundle includes the hook (`scripts/build_plugin.py`); a project given the memory by both gets it once. Formats: Claude Code from its hooks documentation, Codex from the schemas inside the 0.162.1 binary, opencode from the `@opencode-ai/plugin` 1.19.0 types; none has been run in the real tool yet. Plan, reasons for the name and for opencode's `noReply` over its system-prompt hook, and the local checks: `docs/plans/SESSION_START_CONTEXT.md`. **Model input:** the phrase added to `HARNESS_TEXT` removes user messages that start with it from `user_requests`; no such message existed before, so existing requests are unchanged byte for byte.
- **The extract request carries the code-built skeleton.** The steps code sees in the unit's tool calls (`light.skeleton`: a change per run of edits in a turn, a result per test run with its pass or fail, a change per commit, each with its record IDs) go with every full extraction as `skeleton`; `extract.md` asks the model to make them its candidates, regroup only where the records show the grouping is wrong, and add what code cannot see. The structure of a unit then rests on the tool calls rather than on the model's reading of them, which is where the run-to-run swings came from (Luna 8–20 of 22 on one input). **Model input:** a new request key and an `extract.md` paragraph.
- **Claude calls keep a session too.** A task's calls on the Claude CLI now share one conversation like Codex's: the first call runs with `--session-id` (an ID of ours) instead of `--no-session-persistence`, kept in the run's temporary home, and a follow-up (an evidence round, a repair) runs `--resume` with only what is new (`CLIRunner.thread` for both CLIs; Claude reports each call's own usage, so no difference is taken). Measured before: Claude Haiku cache hits of 30–52%.

### Changed
- **A transcript is held in memory once while it is checked for a concurrent rewrite.** `_jsonl` read every file twice in full to compare the two reads (up to 2 x 256 MB for the largest); the second pass now compares 4 MB pieces against the first read (`REREAD_CHUNK`), with the same refusal when they differ.
- **Graph versions are stored compressed (state schema 2).** Every publish kept a whole copy of the graph as text, and old versions are read (the browser's version view, pasted `@vN` references), so on this repository 171 versions took 163.5 MB of a 209 MB state. Versions are now zlib-compressed (`store.pack_text`/`unpack_graph`, about 5x smaller: 34.2 MB on a copy of that state); text versions an older release wrote are packed once when the state is first opened (3.8 s there), and the freed pages are reused by later writes rather than given back (no `VACUUM` under readers). An older release refuses the new state with "Unsupported DB schema: 2" instead of misreading it.
- **A sub-agent's report is one box, not two.** The parent's result that rests only on the delegation's own call and result (the report the sub-agent or a called `codex exec` sent back) repeated the called agent's own conclusion, so the flow drew the same report twice. At publish `schema.fold_delegate_reports` marks such an outcome `folded_into` the called agent's last outcome (recomputed every time; nothing is deleted), and the terminal flow, `contexttrail graph` and the browser view draw the graph through `schema.folded_view`: the parent's copy is left out, its relations move to the called agent's box, and that box's detail names the report as its caller received it. A Codex sub-agent's records name no call, so its parent's results stay as they are.
- **`contexttrail eval` runs what `analyze` runs by default.** Eval now uses economy too (extraction calls only), so its numbers are the default's; `eval --no-economy` runs the integrate and review calls as before. The demo's mock runner proposes the story's links in the extraction when no integrate call follows. An eval is graded on the graph as the views draw it (`folded_view`).
- **Economy is the default: the graph is built from extraction alone.** The code-built draft is published with no integrate call and no delta review, and one evidence round (`integrate_output=draft_only`, `semantic_review=False`, `read_rounds=1`), which the measurements of 2026-10-09 (§17) and since showed scores the same as the full pipeline at a third of the tokens; the integrate and review calls were half of a unit's calls and more than half of its input. `--no-economy` restores them (saved for the project, like `--economy` was); `--light` still implies economy.
- **A citation is a line range; the quote is optional and cut by code when left out.** The extract, integrate and review answers may cite `source_id`, `start_line` and `end_line` alone: `EvidenceValidator.fill_cut_quotes` keeps the cited lines themselves as the quote (the shown lines within the range, at most `CUT_QUOTE_LINES` 20; normalization `quote_cut_by_code`), so a citation can no longer fail for a quote copied wrongly — the cause of 6 of the 14 validation errors in the last 13 eval runs, each of which resent the whole unit as a repair. A quote the model does give is checked as before and names what the lines show. **Model input:** `common.md` [Output] asks for the line range first and makes null the rule for `quote` (a quote that does not match still costs a repair round, as before); the citation schema keeps `quote` required but nullable, since OpenAI's strict structured output refuses an optional key (the first attempt with an optional key failed every Codex call).
- **`--unit-thread` (hidden, off): a unit's stages share one Codex conversation.** The extract, integrate and delta-review calls of one unit can go into the same `codex exec` session when they go to the same adapter (tool and model; `Engine.unit_thread`, closed in `advance_unit`): a later stage is sent as a follow-up under `STAGE_FOLLOW_UP` with the parts of its data the session's first request already holds named instead of repeated (`already_in_conversation`), an evidence round or repair still sends only what is new, and the same stage asked differently or other instructions (the light reading) start a new session. Measured on 2026-10-16 before the slimming (`docs/plans/PERFORMANCE_PLAN.md` §21): the integrate call did resume (Sol 48%, Luna 46% cached) but its input grew about three times and it took twice as long, the review did not report cached tokens, and scores stayed within each model's variance (Sol 12/18, Luna 6/18 and 20/22). So it is off by default; the flag is for measuring the slimmed form.
- **A unit whose answer still fails validation after the repair round is read the light way, not held back.** When nothing of the repaired answer can be kept (`salvage_extraction` refuses it too), the same unit is read as `--light` does: code builds the skeleton, one more call names it and adds the events code cannot see, and the citations are cut by code, so nothing is asked again (`Engine._extract_unit`, `read_light`; the unit's limitations say so, `LIGHT_FALLBACK_LIMITATION`, and the ledger shows the `light` call). The unit is held back only when that reading is refused as well. Smaller retry units were considered and dropped: a smaller unit cuts a step (change and the check that settled it) apart and multiplies boxes. An audit keeps the full extraction. The fixture runner now answers the light stage; a light answer is checked for shape before it is read.
- **The event grain is a step: the edits one check settled plus that check.** The prompts asked for an outcome event per test or command result and an event per completion report, so a nine-event fixture came back as 21–26 events, half of them results (`docs/plans/PERFORMANCE_PLAN.md` §20). Now `common.md` keeps as outcome events the failure that changed what was done next, the run that finally confirmed a change, and a run the user asked for; a repeated run of the same check, or one a later run confirms again, goes into that later outcome's summary, and a report that only restates recorded results is not an event (the user's question is answered by the result itself). A change is still shown as checked only through a `verifies` to an observed outcome; one is enough. `light.skeleton` folds a same-turn repeat of the same check command with no edit between into one result. Repairfix fixture, two runs each: Sol 18·12 of 18 with 19·16 events against 14 with 26 the same morning, Haiku 11·10 with 18·17 events against 13 with 24; no repair calls in the four runs. The fixture's `live6_complete` (an `observed_success` from the sixth live run) was missed in three of four runs, but every run cited that record: the run both completed the repaired extraction and failed three expectation checks, and the model made it one `observed_failure` with the repair's success in its summary, which is what the new rule asks for; that check and the separate regression-test change assume the old grain. Integrated units are not resent; new units use the new grain.
- **Fewer tokens per unit.** Measured on an outside project analyzed with Codex (`gpt-6.1-sol`): about 145k input tokens per unit, prompt cache hits 3%, a fifth of the tokens in repair rounds. Four changes, all model input:
  - A record shown to the model leaves out what the code alone uses (`analysis.HIDDEN_RECORD_FIELDS`: content hash, source version, native and parent record IDs, worktree, folder) and empty or default values (`record_for_model`); event provenance was already read off the citations. This was about 40% of a shown record there.
  - Lean context is smaller: context-only text 8,000 characters instead of 24,000 (`LEAN_CONTEXT_CHARS`), 6 related events instead of 12 (`LEAN_CONTEXT_EVENTS`), an event index of 30 instead of 60 (`LEAN_INDEX_EVENTS`). With the item above, that project's extract requests went from 1.17M to 0.84M characters for 8 units (−28%).
  - Claims a candidate's own citations do not back are read as the weaker claim they back instead of costing a repair round with the whole unit resent (`EvidenceValidator.settle_unbacked_claims`): `applied` on a change with no tool or Git evidence and `observed_*` on an outcome with no tool result become `reported_complete`, and a `tool_record` basis with no tool citation becomes `git_artifact` or `explicit_statement` (audited as `applied_without_patch_as_reported`, `observed_without_result_as_reported`, `tool_basis_without_tool_record`).
  - An extracted relation that breaks a relation rule (a verifies that does not lead from a change to an observed outcome or rests on inference, an answers that does not leave a question) is left out and named in limitations instead of repaired (`drop_rule_breaking_relations`, `relation_dropped_by_rule`). A delta from integration still reports it.
  - Repairfix fixture, Codex `gpt-6.1-sol`, 3 runs: 13·14·13 of 18 against 16·14·13·13 before; input tokens 171k–232k against 146k–330k, API-rate cost $0.46–0.71 against $0.44–0.92 (`docs/plans/PERFORMANCE_PLAN.md` §18).
- **`--economy` (saved per project):** the graph is built from extraction alone: the code-built draft is published with no integrate call (`--integrate-output draft_only`) and no delta review, so links across units are only those the extraction proposes (it sees the related existing events). Same fixture, 3 runs: 13·13·12 of 18, 2–3 calls, 56k–93k input tokens, $0.18–0.39 — about a third of the default's tokens. `--no-economy` turns it off.
- **The note reminder names the calls it is about.** When a turn ends with edits, commits, tests, Git changes or file-writing commands after the last note, the message sent back to the agent now lists up to five of them (the newest distinct ones, each a kind — edit, test, commit, vcs or run — and a short target: the file edited or the first 80 characters of the command; never their output) and how many more there were. The 2026-10-10 audit of this repository found 125 events next to 28 notes, mostly intermediate test failures, fixes and doc updates the note had skipped. The first sentence (`ContextTrail notes are on for this project`) is unchanged because `HARNESS_TEXT` matches it; the opencode plugin posts the hook's message as it is, so it carries the list too. The reminder is stored in transcripts as a user message, so a record holding a new one is longer; those sessions are read only by `analyze --audit`.
- `Store.units(results=False)` skips the stored extraction results, and `freshness.stored` (the store-only part of `freshness.check`, now its own function) uses it: `find`, `status` and the hooks no longer read tens of megabytes of results to count units.

### Fixed
- **With economy, the next unit's extraction sees the unit before it.** The next unit used to be extracted in the background before the current one was published (`studio_graph._prefetch_next`), to overlap the current unit's integrate call. With no integrate call (`draft_only`, the economy default) there was nothing to overlap, and the extraction, now the only call that can link a unit to the events before it, was sent without them: on the demo fixture the one link between units was lost. Prefetch is off when no integrate call follows. With `--workers` above one, units are still extracted side by side and do not see each other.
- **A sub-agent's instructions are not the person's request.** A model wrote the prompt a parent agent gave its Explore sub-agent as a `question` of `actor=user`; the sub-agent's work then hung under that false request and the flow drew it apart from the parent's story. `schema.drop_caller_instructions` removes from an extraction an `actor=user` event citing only user-role messages a calling agent wrote (`lineage.kind` subagent or unattended), with its relations (normalization `caller_instructions_not_user`); `link_request_turns` then hangs the sub-agent's work under the parent's message.
- **A unit's new events are listed in the order they happened.** The graph kept the order the model listed them in, so a change could be numbered and drawn before the request that asked for it; `apply_delta` now sorts the events a delta adds by `recorded_at` (stable; no time last).
- **Listing tags or branches with a sort or format option is no longer a vcs step, and an annotated tag is.** `git tag --sort=-creatordate` was read as a change of history (`analysis._vcs_mutates`), so the note reminder asked for a note after a read-only listing; `git tag -a v2` was read as a listing because `-a` lists for `branch`. A tag or branch command now changes state when it names something or carries a changing flag (`-d`, `-m`, `-a` for tags, ...), and lists otherwise.
- **README and CONTRIBUTING follow the code.** The README described economy as an option to turn on (it is the default) and the change re-review as part of every run (only with `--no-economy`); CONTRIBUTING said the validation messages the model reads are Korean (English since 2026-10-06).
- **A person's message written as a goal or proposal is read as a question.** `retype_answered_user_goals` no longer waits for an `answers` relation: any `actor=user` goal/proposal resting on the person's own words becomes `question`/`asked` (normalization `user_goal_as_question`). On the synthetic sub-agent/fork fixture Luna wrote all three requests as goals, which lost them from the request views and left the forked session's first request unlinked.
- **A sub-agent's stack stands beside the step that followed it in time.** Events of different sessions are listed in the order they were analysed, so a sub-agent analysed after its parent stood beside the parent's last step; the step after it by `recorded_at` is used now.
- **A transcript over 64 MiB silently dropped its session from analysis.** A day of Claude Code work with large tool outputs produced a 73 MB session file; the parser refused it, its records were marked unavailable, and the limitation read only `log file not read: … (FlowError)`. The limit is now 256 MiB (`sources.local.MAX_FILE_BYTES`; the file is held in memory twice while parsed) and the limitation names the reason, in English like every limitation the model reads.
- **A Codex follow-up call continues the same session, so what was sent before is cached.** Each call was a new `codex exec --ephemeral` session, and Codex keys its prompt cache by session, so an evidence round, a repair or the final answer resent the whole request (about 50k tokens on an outside project) with no cache hit. Now the calls of one task share a conversation (`CLIRunner.thread`, `Thread`): the first call keeps its session in the run's temporary home, and a follow-up runs `codex exec resume <id>` with only what is new (`new_evidence_rounds`, `repair`, `evidence_requests`; anything else changed, such as a trimmed request, starts a new session). The resumed call gets the same tool and sandbox settings (`sandbox_mode="read-only"` by config, since `exec resume` has no `--sandbox`). Codex reports a resumed session's running total, so a follow-up's usage is recorded as the difference (`usage.continued_session` marks it). Live, `gpt-6-luna`, a 21.6k-token request: follow-ups cached 21,248 of 21,707 and 21,775 input tokens, against 0 before. Claude runs are unchanged (`--no-session-persistence`).
- **A unit whose model keeps asking for evidence ends with an answer, not a failure.** After the last evidence round (`read_rounds`, 2; 1 with `--economy`; `--light` asks for none) the next call's schema allows only `status: complete` and the request says so (`evidence_requests`, `analysis.final_schema`), so the model answers from what it has and names the rest in limitations. Before, a third request failed the unit after a repair call: on an outside project four calls and about 250k tokens left nothing. `--economy` allows one.
- **The end-of-turn note reminder leaves runs with no person alone.** A `codex exec` session (`session_meta` `originator: codex_exec`/`source: exec`) or a `claude -p`/SDK session (`entrypoint` `sdk-*`) is not sent back to write a note (`journal.unattended`, read from the hook's `transcript_path` or the session's transcript): the reminder replaced the answer `codex exec -o` was waiting for with a note attempt.
- **A note written by Codex that Claude Code started in the same project goes to the Codex session.** The Codex shell inherits `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID`, so `--session current` picked the outer Claude Code session and the quotes were "not found" (the closest lines were that session's test output). The session is now the one of the nearest Codex, Claude Code or opencode process (`journal.host_tool`, from `ps`), and where that cannot be read (Codex's sandbox refuses `ps`) the first session in the project whose records hold every quote (`current_in_project(quotes=…)`).
- **Claude Code's records of a session-start hook no longer warn as unsupported.** `attachment:hook_success` (the hook ran, its JSON answer as stdout) and `attachment:hook_additional_context` (the context it added) are in `IGNORED_NO_ANALYSIS_VALUE`, and so is `attachment:hook_blocking_error`, a Stop hook's block whose text is already read from the `Stop hook feedback` user message; seen when `contexttrail context --hook` was checked live in Claude Code, Codex and opencode (`docs/plans/SESSION_START_CONTEXT.md` §8).

## 0.1.0a7 – 2026-10-11

### Added
- **`--recent N` and `--since WHEN`: analyze the latest sessions first.** For the first analysis of a big project: only the units of the N most recent sessions (or those that ended after an age such as `7d` or a date) and their sub-agents are planned, oldest first within them, and what they add is marked out of order while other records still wait; the project stays `partial` and a later ordinary run fills in the rest oldest first. A session is as recent as the latest record of it and its sub-agents (a Claude Code sub-agent's records, kept under its parent's session ID, do not make that session look like someone else's sub-agent); sessions with notes are not candidates and are not counted. The consent screen and `scan` (`plan.selection`) name the sessions taken first and how many units each has. The options are refused together with `--session`, `--audit` and `--trigger hook`, and an empty selection is an error, not a silent run. `--units`, `--max-calls`, skipped-unit hold-back and the call cap work as with `--session`. No model input changes. Design and decisions: `docs/plans/RECENT_SESSIONS_FIRST.md`.
- **`contexttrail note`: the agent that did the work writes an event itself.** No model is called. The agent gives the kind (`decision`, `proposal`, `goal`, `action`, `revision`, `outcome`), the status, a title, a summary and one or more `--quote`s copied from what it saw; code finds each quote in the current session's own records (one transcript file, or one opencode session; this repository's 3,790-record session parses in under a second), so the agent never names line numbers, and the note's own command line is never a source. The event then takes the analysis path unchanged: the candidate check, the code-built draft delta, `apply_delta` with every evidence, status and relation rule (an `observed_*` status still needs a quoted tool result), the dialog-turn links that also add the person's requests, and one `publish`. `--verifies`, `--revises`, `--answers` and `--motivates` name an earlier event (an ID, a prefix or a copied `contexttrail:ev_…@vN`) and add an explicit relation from it to the note. A note that fails a check stores nothing and says why, with the closest lines when a quote was not found; while an analysis holds the project's lock it is refused at once rather than waiting. `--list` shows the notes of the session, `--json` the stored event. Records are stored with a partial ingest that leaves the rest of the project's records as they were. Plan: `docs/plans/LIVE_JOURNAL.md` (stage A).
- **Notes are per project, with a skill and an end-of-turn reminder.** `contexttrail note --enable` turns them on (a note is refused while they are off). The `contexttrail-note` skill, installed with the other two into Claude Code and Codex and picked by the agent itself, says when and how to note. A synchronous `Stop` hook, `contexttrail note --hook` (installed by `install-hooks` next to the asynchronous auto-update hook), sends the agent back once when a turn edited files or ran tests, commits or Git changes after its last note; Claude Code's `stop_hook_active` and the time of the last reminder keep it to once, and in a project without notes it does nothing. The opencode plugin puts the session's ID into the tool shell (`OPENCODE_SESSION_ID`) and sends the same reminder on `session.idle`. The reminder text is never taken for a person's request.
- **Notes in a sandbox are queued.** Codex's default sandbox keeps `.git` read-only, where the project's state lives; `note` then checks its quotes and queues the note in the per-user temp directory with a `q_…` ID that later notes can link to, and the end-of-turn hook (outside the sandbox) stores the queue with every check, sending the agent back once with the reasons for any it refused (also shown by `note --list`).
- **Note checks found on first use in opencode and Codex.** `--session current` takes `OPENCODE_SESSION_ID` first (the plugin sets it per tool call) and, among the sessions the environment names, the first with records in the project, so a variable inherited from the shell that started the tool is passed over; a short output (`5`, `ok`) is quotable as its whole line; an `observed_*` quote is looked up in tool output before a message that repeats it; `--verifies` on a note that is not an observed outcome is refused at once with what to do; the observed-status error says where the quote was found.
- **A session with notes leaves analysis.** A note marks its session's records processed, every scan does the same for records the session writes later (and for its sub-agents), a stored unit with no result and nothing left pending is superseded instead of sent, and the freshness count leaves them out. Past sessions without notes are analyzed as before.
- **Claude Code plugin.** The repository is a plugin marketplace (`.claude-plugin/marketplace.json`, `plugins/contexttrail/`: skills `note`, `context`, `update` and both hooks), generated from the same skill text as `install-commands` (`scripts/build_plugin.py`; a test keeps them equal). `claude plugin validate` passes for both manifests, and installing it from GitHub (`claude plugin marketplace add kisbi3/ContextTrail`, then `claude plugin install contexttrail@contexttrail`) was checked live: the skills load as `contexttrail:note` and the others, and its reminder leads Claude to note.
- **Note checks found on first use of the plugin.** A shell command that writes a file (output sent to a file, `sed -i`, `tee`, `mv`, `rm`, `git apply` and the like; quoted code is not read as shell) counts as work to note, so an agent editing through the shell is reminded too; a change's quote is looked up in tool calls and results before a message that repeats the code, so the default `applied` status holds; and the hook runs one at a time per project, so with both `install-hooks` and the plugin the reminder is sent once and the queue stored once.
- **A unit that fails for its own reasons no longer stops the run.** Only failures that are the unit's are skipped: an answer that still fails validation after the repair round (`TaskValidationError`) and a request over the input budget with nothing left to trim (`InputBudgetExceeded`). The failure is saved (`unit_failures`) with the `_routing_signature` and the hash of each record, the run goes on with the next unit and ends `partial`, or `failed` when no unit completed. A skipped unit is not planned again while it is the same input (same signature, same record hashes), so a rerun with nothing else to do ends `noop` with no calls; a changed record, a changed setting or the new `analyze --retry-failed` sends it again, and then, if other units were integrated since, its events are marked in `out_of_order_events`. A runner error, the call cap and any unknown error still stop the run. An unreadable final JSON (`BrokenOutput`, Codex and Claude) is asked for once more as a call of its own. If the session has notes by the time a skipped unit would be sent, the unit is superseded and its failure forgotten. `status` and `find` count skipped units apart (`failed_units`; their records are no longer counted as waiting) and say how to send them again. **Calls:** a unit is not started when the calls left cannot carry it (an extraction and an integration; one when its saved extraction is still valid); a run that completed no unit ends with the new status `call_limit` (exit 2, like `partial`, so the automatic hook does not count it as a failed run) and a `stop_reason`. The runner's CLI, sandbox and login (`preflight`, no model call) are checked once after the consent and before the first unit. **Model input:** the new limitation lines (`skipped unit <id>: …`, `skipped units held back: N. …`, English, listed in `informational` so a rerun ends as a no-op) enter later units' `input_limitations` in a run that skipped a unit, and in every request of a run that holds one back; extractions already saved are not resent (`input_limitations` is not part of the context digest or the routing signature). Mock runner only; design record in `docs/plans/PERFORMANCE_PLAN.md` §16.
- **`analyze --audit`: check a noted session for what the agent left out.** It re-reads the records of sessions that have notes (and their sub-agents) that no analysis has covered, shows the model the existing notes, and adds only events, relations and open items they do not record; it never changes an existing event (`audit_guard` rejects an update, an invalidation or a resolve), and what it adds carries `origin: "audit"`. Units are cut like any session but stored as `audit_` units the ordinary plan and the cost calibration ignore; an edit no event cites is still required to be cited, one a note cites is not; a candidate with a note's kind and exactly its cited lines is settled as that note's duplicate in code; the semantic review is off; the run leaves `analysis_status` and `coverage` alone and is `complete` when no audit unit is left. `scan --audit` previews it with no model call, the usual consent and unit choice apply (the plan line says it is an audit), and the automatic hook never runs one. **Model input:** `prompts/audit.md` and `journal_audit.note_event_ids` ride on extract and integrate requests only in an audit; an ordinary request is byte for byte what it was. Tested with the mock runner only; a run with a real model is still to be checked locally. Design: `docs/plans/LIVE_JOURNAL.md` §11.
- **`status` and `find` say when noted sessions have not been audited.** `freshness.check` returns `unaudited` (`sessions`, `records`), counted from the store alone: stored records of sessions with notes (and their sub-agents) that no integrated unit covers, i.e. what `analyze --audit` would read. The header phrase adds "N noted sessions not audited", and `status` prints the `analyze --audit --units N` and `scan --audit` commands; the count is 0 after an audit. A record too large to send stays in the count.
- **Note checks found on first use of the plugin (2).** A `git fetch` that only refreshes remote-tracking refs (no refspec writing a local ref, no `--update-head-ok`) no longer counts as work to note, so a turn that only checked the remote is not sent back for a note; the filter lives in `journal.py`, and the analyzer's `tool_steps` still classify the call as `vcs` (no model input changes).

### Changed
- **Codex's default model is the newest Sol of the installed Codex.** The default is now `gpt-sol`: Codex takes only versioned names, so before the first call the runner reads the model list shipped with the installed Codex (`codex debug models --bundled`, inside the sandbox) and names the listed `gpt-<version>-sol` with the highest version (today `gpt-6.1-sol`, which scored 16·14·13 of 18 against `gpt-6-sol`'s 13·15·12 on the repairfix fixture). Any `gpt-<family>` without a version works the same way. Calls record the resolved name; if none is found the run stops rather than picking another model. Finished units are not resent.
- The note skill asks for one quote per edited file in a change note: a note that quoted only the commit line left its edits uncited, and a real-model audit of this repository wrote those changes a second time (3–4 of 125 added events).
- **Notes account for a session only from when they were turned on.** A noted session's records from before the earlier of the first `note --enable` and the oldest record a note cites (kept as `journal.since`, unchanged by `--disable`/`--enable`) stay with ordinary analysis, and records an earlier version marked processed are given back at the next scan unless an analysis covered them; `--audit` reads only the part since then, and a note adds request events only for that part. Found on this repository, where a session open since 2026-09-26 got its first note on 2026-10-07: about 105 units of earlier history had left ordinary analysis (108 → 213 units pending, audit 124 → 16).
- The audit prompt says the agent's `contexttrail note` calls, their output and the note reminders are bookkeeping of the graph, not project work (a real-model audit had written refused and retried notes as events). Model input change, audit requests only.
- Codex's wrapper for a Stop hook's message (`<hook_prompt …>`, Codex 0.16x) and the skill body Claude Code puts in the user role (`Base directory for this skill:`) are harness text, not a person's request; seen on the Codex re-check, where the note reminder had become a request event. Model input change: these messages no longer enter `user_requests`.
- Events are marked out-of-order (`out_of_order_events`) only while records outside the chosen session still wait. `--session` used to mark them always, also when nothing else was left to analyze.
- `--session current` reads `OPENCODE_SESSION_ID` too, and inside Claude Code (`CLAUDECODE` set) takes the Claude Code session even when a `CODEX_THREAD_ID` was inherited from the shell that started it.

### Fixed
- **The plan's token estimate counts Claude's cached input.** Calibrated from past runs, it summed only `input_tokens`, which the Claude CLI reports apart from the cached part (`cache_creation_input_tokens`, `cache_read_input_tokens`; often 2), so on a project analyzed with Claude it showed about a thousandth of the real input (on this repository: 114 tokens for 15 units, now about 4.5 million). The eval review and the LangSmith trace count the same way.
- **`file-history-delta` no longer warns as an unsupported Claude record type.** The parser skipped it but neither registry listed it, so every scan of a Claude log that had one reported an "unsupported record" gap. It is now in `IGNORED_NO_ANALYSIS_VALUE` next to `file-history-snapshot` (the edits themselves are the tool calls). The shape was not checked against a real log from this environment.

## 0.1.0a6 – 2026-10-07

### Changed
- **A request over the input budget is trimmed before it fails.** `Harness.task` now cuts, one step at a time and only while the wired request exceeds `task_chars`: background context records, then the quotes of existing evidence (marked `quote_omitted_for_budget`), then the cited-line context, then the manifest index (`trim_step`, `TRIM_STEPS`); the steps taken are recorded with the call as `input_trimmed`, and the unit fails only when nothing is left to cut. A request under the budget is unchanged.
- **Lean context is bounded.** A context-only record (the turn before, a commit near in time) is shown head and tail whatever its role (`CONTEXT_HEAD_CHARS`/`CONTEXT_TAIL_CHARS`; one 39,000-character commit record went into four units whole), the lines around a cited quote are 3 instead of 5 and a block over `CITED_BLOCK_CHARS` keeps only the cited lines, nearby records of the other source type are 3 instead of 4, and lean mode's context budget is `LEAN_CONTEXT_CHARS` (24,000) instead of `read_chars` (36,000). Full mode is unchanged. On this repository's 20 stored units the largest extract context went from 58k to 44k characters; the median stays near the budget, since the cited lines of the selected existing events fill it.
- **An observed result with no change to verify no longer goes to review.** The `unlinked_observed_outcome` signal asks whether a new observed result should be linked to a change with `verifies`; when the delta adds no change event (`action`/`revision`) the review's answer was always "nothing to link, noted in limitations" (5 of 16 reviews on this repository, none changing anything), so code now settles those issues (`origin: code`, audit status `resolved_in_code`) and writes the limitation itself. The review still runs for an unlinked revision, an update or an invalidation, and for an unlinked result when the delta does add a change.
- The manifest's event index sent with every extract and integrate request is the 60 most relevant events (`LEAN_INDEX_EVENTS`, was 100), so it stops growing with the graph, and an evidence entry's source metadata leaves out empty values and the default derivation.
- **Long lines and long quotes are shown cut.** A saved quote is the whole cited lines (partial quotes are canonicalized, the cited part kept as `focus`), so one 8,000-character line cited once was sent whole in every later request that showed that evidence; of this repository's 159 saved quotes, 30 were over 1,000 characters and the longest 14,474. The model is now shown the cited part (or the head) within 300 characters (`shown_quote`, marked `quote_is_part_of_lines`; the candidates the integrator sees carry the same short quotes, `candidates_for_model`), and a record line is cut at 1,500 characters with a note (`shown_line`; a minified file or a one-line JSON result slipped past the head/tail view whole, one 6-line record was 16,900 characters). The canonical quote stays in the store, a quote copied from the shown part still resolves to the same lines, and the unit planner counts the cut length. Together with the dedupe below, measured on this repository: the unit that overflowed went from extract 153k / integrate 259k / review 228k characters to 110k / 73k / 59k; another unit 187k / 168k / 159k to 159k / 113k / 70k.
- **The integrate and review requests stop repeating the candidates.** In the draft the model is sent, an added item that is its candidate unchanged is named (`{"id", "candidate": "unchanged"}`) instead of copied, and a `candidate_evidence` entry whose quote a candidate already carries is marked `quote_in_candidates` instead of quoted again; the patch-mode review (the default) no longer receives the records' context (`context_only`) and the manifest, which the integration already read, and judges on the candidates, their evidence and the existing events. The review ran on 13 of 14 units here and changed items in 3, so its size was a third of every unit's cost. Model-input change; mock eval and live units checked.

### Fixed
- **A unit of a dozen candidates no longer overflows the integrate and review requests.** The code-built draft delta carried every candidate's evidence three times (in the item, its resolution and its attribution), and the integrated delta sent to the review did the same; on this repository one hook-started unit failed with "the analysis input budget was exceeded" at 259k characters against the 240k budget, before any integrate call. The model now sees a resolution or attribution whose evidence is exactly its candidate's own without that copy (`schema.delta_for_model`; the full delta stays in code for the merge and every check), and the patch instructions say so.
