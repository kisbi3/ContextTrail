# 파이프라인 v2: 작업 기록은 코드가, 이야기는 모델이

**상태: 설계(2026-10-18), 검수 반영. §6의 1·2단계와 5단계의 첫 시험 경로(`--pipeline v2`, light 확장) 구현. 3·4단계(코드 사건 표시 `origin: "code"`, 단위 간 연결)는 남음.** 소유자: "단순하게 생각할 것이 아닐 것 같아. 파이프라인을 재정비 해야 할 것 같은데?", "진행해줘. 너가 알아서 진행해도 될듯". 기존 원칙(2026-09-29, `TARGET_PIPELINE.md`: 코드가 결정적인 뼈대를 만들고 모델은 묶기·이름 붙이기·관계 맺기를 한다)을 끝까지 밀고, 계획만 있던 `seed_code_nodes`를 대신한다.

## 0. 왜 바꾸나 (측정)

priceimpact(연구 저장소, Codex Desktop 다중 에이전트 + Claude Code) 실제 기록으로 잰 것:

- **모델 한 번에 너무 많은 일.** 지금 추출 호출은 사건 찾기, 종류, 원문 줄 번호와 인용, 관계를 한 번에 엄격한 검증 아래 낸다. 같은 5단위에서 Luna는 처음 통과 0~1/5, 실패의 대부분이 인용문·줄 범위 같은 형식이었다(`PERFORMANCE_PLAN.md` §24). Haiku도 실행마다 무엇을 뽑는지가 크게 달라졌다.
- **관계가 비어 있다.** 새 두 줄기 화면에서 "관계 기록 없음"으로 놓인 상자들을 원문과 대조하니 대부분 실제로 관계가 있었다(문서 기록 ↔ 그 결정, 실행 ↔ 그 산출물을 검사한 결과, 테스트 ↔ 다른 구간 하위 에이전트의 변경).
- **코드가 이미 아는 것을 모델이 다시 추측한다.** priceimpact 전체(도구 호출 3,320개, 그중 하위 에이전트 924개)에서 코드만으로: 테스트 161개 중 131개(81%)를 그 테스트가 다룬 편집에 묶을 수 있고(109개는 명령이 파일·모듈을 지목, 22개는 전체 실행), 1,180개 명령이 앞선 명령이 쓴 경로를 읽는다(418개는 다른 세션의 산출물). 지금은 이것이 모델에게 주는 참고(skeleton)일 뿐이다.
- **단위가 이야기와 맞지 않는다.** 단위는 시간·글자 수 조각이다. 이 프로젝트의 본 세션은 5단위에 위임 호출 41개로 대부분 지휘만 하고, 실제 편집·실행은 하위 에이전트 세션(다른 단위)에 있다. 조각 경계를 넘는 관계가 끊긴다.
- **결론을 놓친다.** "BTC 현물은 a*가 범위 끝이라 가설을 지지하지 않는다"는 보고는 Haiku 3회, Sol 1회 모두 사건이 되지 않았다. 프롬프트 지시로도 바뀌지 않았다.
- **읽는 사람 테스트.** 흐름도 글자만 보고 5문항에 답하게 했을 때 옛 화면·두 줄기·제목 규칙 모두 3.5/5(Haiku), Luna 1.5/5. 화면만 고쳐서는 오르지 않았다.

## 1. 방향 (검수 뒤 확정)

처음 안은 그래프를 세 층(코드의 작업 기록 / 모델의 이야기 / 코드의 판정)으로 **저장 형식까지** 나누는 것이었다. Gemini 4 Argon과 gpt-6-astra가 서로 모르게 검수했고(2026-10-18), 둘 다 같은 결론을 냈다: 역할은 그렇게 나누되 **저장 형식은 지금의 그래프(schema 2) 그대로** 두어야 한다. 사건과 따로 저장하면 `find`/`show`/`context`, note, 감사, eval이 한꺼번에 깨지고, 같은 그래프를 v1 writer(note·자동 분석)와 v2가 번갈아 쓰게 된다. 그래서:

- **코드가 아는 것은 코드가 먼저 사건과 관계로 넣는다**(`origin: "code"`): 편집 묶음, 검사 실행과 그 결과, 커밋, 위임, 그리고 증명되는 관계. 지금 `light.skeleton`을 넓히는 일이고, 계획만 있던 `seed_code_nodes`다. 모델이 실패해도 이것은 게시된다.
- **모델은 이야기만 쓴다**: 목표, 결정과 (기록에 있을 때만) 그 이유, 결론·발견, 방향 전환, 남은 질문, 그리고 코드 사건과의 연결.
- **근거는 블록 ID로**(Astra): 코드가 각 기록을 문단·명령 단위 블록으로 미리 나누고(`B12`: source, 줄 범위, 정확한 발췌), 모델은 블록 ID만 고른다. 인용문도 줄 번호도 모델이 쓰지 않으므로 형식 실패가 사라지고(Luna 실패의 대부분), 근거는 지금처럼 줄 단위로 남는다. 어떤 이야기에도 쓰이지 않은 보고 블록을 셀 수 있어, 결론 누락을 표시할 수 있다(`unclaimed_report`).
- **단위를 넘는 관계는 게시할 때 코드가 잇는다**: `link_forks`, `fold_delegate_reports`처럼 그래프 전체 위에서. Codex 하위 에이전트는 위임 호출 ID가 없고 부모 스레드만 있으므로(`_codex_lineage`) 그것으로 잇는다.

## 2. 코드가 맺어도 되는 관계 (거짓 연결을 막는 규칙)

| 관계 | 조건 | 아님 |
| --- | --- | --- |
| 편집 → 검사 `verifies` (structural) | 검사 명령의 대상이 **고친 파일 모두**를 이름째 지목(파일 자체 또는 그 모듈의 테스트 파일, `light.covers`) | 전체 실행·`-k`/`-m` 선택 실행·일부 파일만 지목·글자 일부 일치(`base`⊄`test_database`) |
| 위임 → 하위 에이전트 작업 | 계보(`parent_tool_call_id`, Codex는 `parent_thread_id`) | 시간 근접 |
| 실행 → 앞선 산출물 `uses` | 명령이 앞선 작업이 쓴 경로를 대상으로 지목, 같은 worktree, 생산자가 하나로 정해질 때 | "검사함"이 아니다(읽기는 소비일 뿐). 비교·판정이 있는 실행만 따로 "산출물 검사"가 된다 |
| 커밋 → 편집 | 커밋 diff가 그 편집 범위와 맞을 때 | 파일 이름만 같을 때 |
| 같은 파일의 다음 편집 | `previous_write`(배치용)일 뿐 | `revises` 아님(의미상 수정은 모델 몫) |

검사 결과는 `passed/failed/running/unknown`을 구분한다(`check_failed`는 실행 중을 통과로 보지 않도록, 복합 명령은 마지막 상태가 앞 실패를 가리지 않도록). 통과가 확인된 완료 실행만 ✓의 근거가 된다.

## 3. 모델의 이야기 단위와 입력

- 단위: 사람의 요청 한 번(본 세션 + 그 턴의 위임 보고), 사람 없는 실행 세션 하나, Git만 있는 변경 묶음. 큰 턴은 지금 예산 규칙으로 나누고 앞 조각의 이야기 노드를 이어받는다. 같은 하위 에이전트에 다음 턴에 다시 맡긴 일, 늦게 도착한 보고는 활동은 하나로 두고 "맡김/후속 지시/받음"을 따로 기록한다.
- 입력: 사람 메시지, 어시스턴트 글(블록 ID 붙여서), 코드 사건 개요(ID와 한 줄), **실패한 실행의 마지막 몇 줄**(Argon: 이유를 알 수 없으면 모델이 지어낸다), 하위 에이전트 최종 보고, 앞선 이야기 노드와 열린 질문.
- 출력: 이야기 노드(`kind`, `title`, `why`: 이유 블록이 있을 때만, 없으면 null과 "이유 기록 없음", `evidence_blocks`, 코드 사건과의 연결은 역할을 나눠 `caused`(이 결정이 낳은 작업) / `based_on`(근거로 삼은 결과)), 관계(관계마다 근거 블록), 턴 요약 한 줄. 상태(제안·채택·철회, 답변됨·미해결)도 출력한다.
- 프롬프트: "기록된 결과를 반복하는 보고는 사건이 아니다"(§20)가 연구 결론까지 지우고 있었다. 실행 상태의 복창만 빼고 해석·가설 판단·원인 진단은 결론으로 남긴다.

## 4. 판정과 화면

- 변경의 ✓는 §2의 `verifies`(코드)나 근거가 명시된 모델 `verifies`로만. 결정·결론에는 전파하지 않는다. 일부 파일만 검사됐으면 검사된 파일을 밝힌다.
- 화면: 왼쪽은 이야기와 코드 변경, 오른쪽은 검사·문서·위임(지금 두 줄기 그대로), 코드가 증명한 선과 모델이 주장한 선을 구분해 그린다.
- 실패 경로: 코드 사건은 모델과 따로 원자적으로 게시하고, 이야기만 실패·재시도 상태를 가진다. 이야기 실패를 이유로 원문을 "처리 완료"로 표시하지 않는다.

## 5. 전환 기준 (Astra)

같은 원문 snapshot·요청 범위로 v1과 비교하되, 설계에 쓴 5단위만이 아니라 **다른 프로젝트나 떼어 둔 요청**에서도:

| 축 | 측정 |
| --- | --- |
| 관계 | 종류별 정밀도/재현율(거짓 연결이 많을수록 점수가 오르는 "관계 없음 비율"만으로 판단하지 않는다) |
| 판정 | 고정 반례에서 거짓 ✓ 0건, 실행 중·부분 검사의 과대 표시 0건 |
| 이야기 | 결론 재현율과 근거 없는 이유·결론의 비율 |
| 독해 | 미리 고정한 문항·정답표로 블라인드 비교(틀린 확신 감점) |
| 비용 | 같은 원문 전체의 호출·토큰·시간 |
| 증분·운영 | 무변경 재실행 0호출, note·감사·자동 분석·find/show/context 호환 |

## 6. 구현 순서

1. **`light.covers` 바로잡기**(완료, 이 문서와 같은 커밋): 이름 전체 비교, 전체·선택 실행 제외, 고친 파일 모두를 지목할 때만.
2. 블록 ID(완료, `blocks.py`): 기록을 블록으로 나누는 코드(글은 문단, 도구 호출은 통째, 결과는 앞·끝·실패 줄), 블록 → 증거 변환(`fill_cut_quotes`가 정확한 줄을 남김). 모델 입력은 아직 그대로. 같은 5단위에서 단위당 블록 58~98개. 사람·어시스턴트가 쓴 글은 단위 원문의 0.5~7.6%(563~5,071자 / 66,904~177,178자)뿐이다: 이야기를 쓰는 데 필요한 글은 작고, 나머지는 코드가 읽는 도구 기록이다.
3. 코드 사건 시드(`origin: "code"`)와 실패 시에도 남는 게시 경로, 활동 조회(find/show).
4. 게시 시점의 단위 간 연결(위임·검사).
5. 이야기 호출(블록 ID 출력, 실패 실행 발췌, 결론 프롬프트), `--pipeline v2` 실험 경로 — 첫 판 구현: `light.skeleton`이 작업 기록(편집·검사·커밋, `covers`로 검증 관계), `story_request`는 도구 출력 없이 쓴 글 블록·작업 개요·실패 실행의 마지막 줄만, 모델은 `STORY_SCHEMA`(작업 이름, 이야기 사건과 블록 ID, 연결, 턴 요약), `story_extraction`이 일반 추출 결과로 바꾼다(블록은 `light.cite`로 정확한 줄). 이야기 호출이 실패하면 작업 기록만 게시하고 `STORY_FALLBACK_LIMITATION`. 어떤 이야기에도 쓰이지 않은 어시스턴트 블록은 `graph["unclaimed_reports"]`. 통합·검토 호출 없음.
6. §5 비교 뒤 기본값 결정, note·감사 맞추기.

## 7. 검수 기록

- Argon: 기록 ID만으로는 긴 보고의 결론 줄을 잃는다(→ 블록 ID), 저장 분리는 하위 기능을 깨뜨린다(→ schema 2 유지), `reads`·전체 실행·같은 파일 편집의 거짓 연결, Codex 하위 에이전트는 부모 스레드로, 실패 원인 발췌가 필요, 5단위 과적합.
- Astra: `covers` 반례 셋(메모리에서 실행해 확인), `check_failed`의 실행 중 처리, `reads`는 검사가 아님, 블록 ID 제안, 단위 소유권(후속 지시·늦은 보고·재위임), 실패해도 남는 게시 경로, `why` 강제 금지, 전환 기준표, 더 작은 대안(schema 2 + light 확장)과 비교하라.

## 8. 떼어 둔 단위 비교 (2026-10-18)

priceimpact에서 설계에 쓴 5단위 다음 10단위(같은 기준 state 복사본, `compare_models.py --base`). 질문·정답표는 실행 전에 단위의 쓴 글만 보고 고정했다(4단위·10문항, 하위 에이전트 1단위 포함). 읽는 모델(Sonnet)은 그림만, 채점 모델은 정답표와 답만 본다(변형 이름 모름). 한 번씩 잰 값이라 ±1점 정도는 잡음으로 본다.

| | v1 Haiku | v2 Haiku | v2 Luna(추론 high) |
| --- | --- | --- | --- |
| 단위 게시 | 10/10 (검사 실패 4회) | 10/10 (0) | 10/10 (0) |
| 단위당 시간 | 118초 | 35초 | 29초 |
| 단위당 입력 토큰 | 123,103 | 8,070 | 15,361 |
| 사건/단위 | 10.8 | 7.8 | 10.2 |
| ✓ 변경 | 27/36 | 1/12 | 1/10 |
| 독해: 흐름도만 | 4.5/10 | 4.0/10 | 3.0/10 |
| 독해: 흐름도 + 상자 상세(요약) | 7.5/10 | **9.0/10** | 7.5/10 |
| 독해: 이야기 상자에 요약 첫 문장 | 4.5/10 | 6.5/10 | 4.5/10 |

- **내용은 v2가 v1 이상, 화면이 병목.** 정답(δ 값, 거래자 ID가 없어 원자료 재현 불가, 기존 log OLS가 논문 추정법과 다름)은 v2 그래프의 요약에 있었지만 상자에는 제목만 보였다. 이야기 열의 결과 상자도 결정처럼 요약 첫 문장을 보이게 했다(`diagram`, 오른쪽 검사 상자는 제목만).
- **✓는 v1이 훨씬 많다.** v1 모델은 빌드·실행 출력을 읽고 `verifies`를 썼고(13건 확인: 대부분 타당, README 갱신까지 빌드가 검증했다고 본 1건은 과대), v2는 도구 출력을 보지 않고 코드 규칙(`covers`: 테스트가 고친 파일을 지목)만 쓴다. 이 프로젝트의 검사는 대개 테스트가 아니라 고친 스크립트를 실행한 빌드다. 다음 일: 고친 파일 자체를 실행해 성공한 실행을 코드가 증명할 수 있는 검사로 넓히기(§2 규칙 안에서).
- **관계 정밀도(직접 판정).** v2 Haiku 고유 관계 21개 중 틀림 3(빌드가 재적합 결과를 낳았다 등), 애매 3. v2 Luna는 약 45개로 한 결과에 점검 6개를 묶는 식의 부채꼴 연결이 많고 틀림 약 8(다운로드 보고 요청 → LaTeX 보고서 `answers` 등). v1 Haiku 19개는 대체로 타당.
- **같은 관계가 두 번 그려졌다**: 이야기 사건의 `work`와 `links`가 같은 관계를 각각 만들었다(`→ [03] 동기`가 두 줄). 하나로 합치고 블록이 있으면 `explicit`(`story_extraction`).
- **v2가 놓친 것**: 요청에 `answers`를 거의 쓰지 않아 "요청 · 답변 없음"이 남는다. 사람의 요청을 `goal`로 쓰기도 한다. Luna는 하위 에이전트 단위(93d4b65f)에서 사건 2개만 썼다.
- Luna는 추론 high에서 상세 포함 7.5로 v1 Haiku와 같았다(설계 단위에서는 1.5/5). 토큰은 v1의 1/8.

전환 판단: 아직 기본값으로 바꾸지 않는다. 남은 조건은 빌드 실행 검사(✓), 요청 `answers`, 관계 정밀도 재측정, note·감사 호환.

### 8.1 변경의 ✓ 넓히기 (같은 10단위)

- **코드만으로 증명되는 실행 검사는 드물다.** 프로젝트 전체에서 편집 370건 중 고친 파일 자체를 실행한 실행은 29건(통과 24), 그 편집 묶음의 파일을 모두 실행한 것은 4건. 규칙으로 넣지 않았다.
- **이야기가 주장하는 검사(`verifies`), 코드가 거른다**(`claimed_check`): 편집 항목에서 결과가 알려진 실행·검사로, 실행이 편집의 마지막 기록 뒤·같은 세션, 그리고 실행이 끝난 뒤 어시스턴트가 쓴 보고 블록을 인용할 때만 `explicit`으로 남는다(근거: 그 블록 + 실행 결과). 거른 주장은 단위 한계에 이유와 함께 남고, 거른 주장이 가리킨 실행은 사건이 되지 않는다. Claude Code 실행은 실패할 때만 종료 코드를 쓰므로 끝난 실행은 통과(`run_status`, 백그라운드 실행은 unknown).
- v2는 한 턴의 편집을 모두 한 변경으로 묶어 10단위에 변경이 10~12개였다(v1은 36). v2에서만 다른 실행이 끼면 편집 묶음을 끊는다(`skeleton(split_at_runs=True)`: 10 → 21개).
- 편집 직후 실행·검사 3개는 마지막 줄을 보여 준다(`output_tail`, 단위당 입력 +~800 토큰).

| v2 Haiku | ✓ 변경 | 남긴 주장 / 거른 주장 | 입력 토큰/단위 |
| --- | --- | --- | --- |
| 주장 없음(§8) | 1/12 | – | 8,070 |
| 주장 + 거름 | 2/12 | 1 / 4 | 8,166 |
| + 묶음 끊기 | 1/22 | 0 / 1 | 8,243 |
| + 실행 마지막 줄 | **3/21** | 2 / 10 | 9,043 |

남긴 ✓ 3개는 모두 타당했다(직접 확인, 거짓 ✓ 0). 하나는 pytest 4건 통과 뒤 같은 명령의 확인 스크립트가 모듈 오류로 끝나 "검사 실패"로 이어졌다(종료 코드는 명령 전체의 것). 거른 주장은 대부분 편집보다 앞선 실행을 가리키거나 실행을 보고하지 않은 블록을 인용했다. Luna(추론 high)는 실행 → 이야기 사건처럼 `verifies`를 잘못 쓰는 주장이 9건이었고 모두 걸러졌다(1/15, 7/8단위에서 Codex 크레딧 소진으로 중단).

결론: 정밀도는 지키지만 ✓는 여전히 v1(27/36, 대부분 타당)보다 훨씬 적다. v1은 모델이 실행 출력 전체를 읽고 판단한다. v2에서 ✓를 늘리려면 더 많은 출력을 보여 주는 수밖에 없고, 그만큼 v2의 비용 이점이 줄어든다.

### 8.2 다시 재기 (2026-10-19, 지금 코드)

같은 10단위·같은 질문과 정답표. v1은 §8의 결과를 그대로 다시 채점했고, v2는 지금 코드로 다시 분석했다. 그림만 보고 답하기는 같은 출력을 두 번 채점했다. 같은 그림인데도 v1이 3.0~5.0으로 갈려, 한 번 잰 점수의 잡음은 ±1점이다. 채점 답을 읽지 못한 2건은 다시 채점했다.

| | v1 Haiku | v2 Haiku | v2 Luna(추론 high) |
| --- | --- | --- | --- |
| 단위당 시간 / 입력 토큰 | 118초 / 123,103 | 36초 / 9,043 | 35초 / 15,730 |
| ✓ 변경 (거짓 ✓) | 27/36 (과대 1) | 3/21 (0) | 1/22 (0) |
| 독해: 흐름도만 (2회 평균) | 4.5/10 | **5.5/10** | 3.25/10 |
| 독해: 흐름도 + 상세 | 6.5/10 | 7.0/10 | 6.0/10 |

- v2 Haiku의 관계가 §8(21개 중 틀림 3)보다 나아졌다: 이야기가 블록을 인용한 `explicit` 연결이 대부분이다(25개 중 20). 애매한 것은 글꼴 설치 확인이 PDF 확인을 "낳았다"는 식의 선행 조건 연결이다.
- Luna는 `produces`를 한 결과에 점검·편집 여러 개를 묶는 데 쓰고(23개 모두 inferred), 요청 `answers`를 엉뚱한 요청에 붙였다(재현 요청 → δ 누락 인정).
- 상세 점수가 §8(v2 Haiku 9.0)보다 낮은 것은 분석 자체를 다시 돌린 결과다. 같은 모델이라도 단위마다 요약에 담는 수치가 달라진다(예: d4b74cbe의 매도 δ).
- 남은 것: 요청 `answers`(v2 Haiku는 0개, 그래서 요청이 "답변 없음"으로 남는다), ✓의 수.

### 8.3 ✓를 v1 수준으로 (2026-10-19)

같은 수정 기록을 분모로 다시 셌다(사건 수는 실행마다 달라 비교가 안 된다, Astra). priceimpact 새 10단위의 확실한 파일 수정 43개 중 "검증됨"으로 보이는 것: v1 Haiku 30(다시 돌린 값 25), v2 Haiku 7~22. v1의 연결 38개를 하나씩 보니 대부분 맞고 의심스러운 것은 2~3개였다. 즉 v2가 실제로 놓치고 있었다. 놓친 수정 22개의 원인:
- 13개: 그 수정을 시험한 실행이 통과로 목록에 있었는데 이야기 모델이 검증을 주장하지 않았다. 모델은 그 실행이 무엇을 했는지 볼 수 없었다. Codex는 실행 출력을 `{"chunk_id": …, "exit_code": 0, "output": "…"}` 한 줄에 담는데 v2는 줄마다 앞 300자만 보여 줘서 실제 출력이 늘 잘렸고, 명령도 앞 80자(인라인 스크립트는 무엇을 여는지 안 보임)만 보였다.
- 7개: Codex `exec` 한 호출이 `apply_patch` 뒤에 `exec_command`(테스트)를 돌렸는데 v2는 그 호출을 수정으로만 봤다.

고친 것(v2 입력과 코드 판정만, 모델 호출 수는 그대로):
- `light.readable_output`: Codex의 출력 묶음을 풀어 실제로 찍힌 마지막 줄을 `output_tail`/`failure_tail`로 보인다. 수정 직후의 실행·검사에는 호출에서 읽은 명령 전체를 400자까지 `command`로 보인다.
- `light.inline_run`: 패치 뒤에 명령을 돌린 호출의 그 명령을 실행 항목(R, `inline`)으로 올리고, 수정 묶음은 그 호출에서 끊는다. `claimed_check`는 같은 호출 안의 실행을 그 수정 뒤로 본다.
- `light._follow_polls`: 1초 안에 안 끝나 `session_id`만 돌려준 Codex 실행에 같은 세션의 뒤 `write_stdin` 확인을 이어 붙이고, 종료 코드가 나온 마지막 결과로 상태와 출력을 정한다(새 10단위에서 결과를 모르던 실행 24개 중 8개가 정해짐).
- 보이는 것만 늘렸을 때는 ✓가 13, 17로 그대로였다. 모델이 검증 연결을 "있으면 쓰는" 것으로 다뤘기 때문이다(10단위에 주장 4~9개). 그래서 이야기 답의 `work` 항목마다 `checked_by`(그 수정을 시험한 뒤 실행과 결과를 보고한 블록, 없으면 [])를 필수로 두었다. 모든 K 항목에 이름을 쓰는 자리에서 정하게 한 것이다. 코드는 이를 지금과 같은 `claimed_check`로 거른다(결과를 아는 실행, 수정 뒤, 실행 뒤의 보고 블록).

결과(새 10단위, 수정 43개):

| | ✓ | 사람 요청 14개 중 완료 답 | 단위당 입력 |
| --- | --- | --- | --- |
| v1 Haiku (두 번) | 30, 25 | 9, 8 | 146k |
| v2 Haiku, 이전 | 7~22 | 11~12 | 11~12k |
| v2, 출력·명령 보이기만 | 13, 17 | 11, 10 | 12k |
| v2, + 한 호출 안의 실행, `checked_by` | 19, 18 | 12, 12 | 12~14k |
| v2, + 세션 이어 붙이기 | **24, 19** | **12, 11** | 12k |

- 받아들여진 이야기 검증 주장이 10단위에 4~9개에서 19~23개로 늘었다. v2i의 검증 연결 23개를 하나씩 보니 대부분 그 수정을 시험한 실행이고, 의심스러운 것은 v1과 같은 종류(README 문구 정정 → PDF 문구 검사)로 한두 개다.
- 아직 거절되는 주장: 결과를 모르는 실행(이 단위 안에서 끝난 확인이 없음), 실행 전의 블록을 보고로 인용한 것. 코드가 대신 블록을 고르지는 않는다.
- ContextTrail 20단위(Claude Code, 수정 13개)는 v1 5, v2 3~4로 수가 작아 판단하기 어렵다.
