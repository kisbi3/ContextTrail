# 요청과 답변 연결 (v2)

상태: 계획, 검수 반영(2026-10-19, gpt-6-astra · Gemini 4 Argon). 관련: `PIPELINE_V2.md` §8.2.

## 0. 왜 (측정과 원인)

- holdout 10단위(priceimpact)에서 v2 Haiku가 만든 `answers`는 0개, v1 Haiku는 4개. 요청 상자가 "요청 · 답변 없음"으로 남아, 그림 맨 위에서 "질문이 무시됐다"는 틀린 신호가 된다.
- **원인(좁혀서): 이 단위의 요청에는 모델이 가리킬 사건 ID가 없다.** `light.story_request`는 `user_requests`를 원문 ID로만 보내고, 요청 사건은 이야기 호출 뒤 `add_user_requests`(`tmp:user_request_N`)가 만든다. `story.md`는 "요청은 사건으로 만들지 말 것"이라고 한다. 앞선 단위의 요청(E)은 가리킬 수 있지만 상한에 밀리면 보이지 않는다. 이것이 0개의 전부라는 증거는 아직 없다: Q만 준 실험으로 먼저 확인한다(§7).
- Luna는 요청을 자기 이야기 사건(actor user, goal)으로 다시 만들었다. `schema.retype_answered_user_goals`는 `answers`와 상관없이 사람 메시지만 인용한 사람의 goal·proposal을 question으로 바꾼다. 그래서 그 사건이 요청이 되어 연결됐고, 엉뚱한 연결이 생겼다("논문 재현 요청" → "δ 추정 누락 인정").
- **요청이 아닌 사람 메시지.** priceimpact 전체에서 사람 메시지 189개 중 래퍼가 붙은 것은 두 종류:
  - `<external_codex_apps_open_page>{"page_id":null}</…>` 7개: Codex 앱 화면 이벤트
  - `<send_user_message_question_reply>[{"questionItemId","question","answer"}]` 3개: 에이전트의 질문(`request_user_input`, 선택지는 그 호출의 `options`)에 사람이 답한 것. 선택지 그대로인 답도, 자유 서술(최대 179자)도 있다.

  holdout에서 이 4개가 "요청 · 답변 없음"으로 보인다. 또 질문 답이 새 턴을 열어, 원래 요청(10:51 논문 재현)의 최종 보고(11:07)가 답의 턴에 들어간다.

## 1. 정답표 먼저 (완료)

`scratchpad/holdout/requests_key.json`: holdout 사람 메시지 10개마다 요청인지, 어디서 무엇으로 답했는지(원문 시각과 문장). 실제 요청 4, 자동 진행 보고 지시 2, 화면 이벤트 3, 질문 답 1. 진행 발언만 있는 턴, 다른 요청의 늦은 답, 중간 사용자 응답을 표시했다. holdout은 설계에 여러 번 쓰였으므로 **최종 판단은 새 단위로 한다**(§7).

## 2. 사람 메시지 분류 (코드, 모든 파이프라인)

판정을 나눈다: 사람이 쓴 글인가(`is_user_prompt`), 요청인가, 에이전트 질문에 대한 답인가, 턴 경계인가.

- `<external_codex_apps_open_page>`: 메시지 전체가 이 래퍼일 때만 `HARNESS_TEXT`로(래퍼 뒤에 사람 글이 붙으면 그 글은 남긴다). 확인하지 않은 다른 래퍼는 넣지 않는다.
- `<send_user_message_question_reply>`(`model.question_reply(record)` → 질문·답 목록):
  - 요청이 아니고 **턴 경계도 아니다**: 원래 요청의 턴이 이어진다(`light._turns`, `link_request_turns`의 차례 계산).
  - 글 블록에는 남는다(`written_blocks`가 명시적으로 넣는다), 이야기 모델이 사람이 무엇을 답했는지 본다.
  - 답이 그 질문 호출의 선택지 중 하나와 같을 때만 사람의 `decision`(adopted, "사용자 선택: …", 요약은 질문과 답, 래퍼 원문은 화면에 내지 않는다). 자유 서술은 사건을 만들지 않고 블록으로만 남긴다("모르겠다"·경로·오류 같은 답을 결정으로 기록하지 않는다).
  - `add_user_requests`와 `link_request_turns`는 같은 분류 함수를 쓴다(두 경로가 서로 다른 사건을 만들지 않게).
- 해시: 분류 함수만 바꾸면 내용 해시는 그대로다. 그래서 **이미 분석된 그래프의 잘못된 요청 상자는 저절로 고쳐지지 않는다**. 아직 분석 전인 단위만 새 분류로 나뉜다. 기존 그래프 보정은 별도 계획(§8).

## 3. 요청에 ID (v2 이야기 입력)

- 모델 호출 **전에** 이 단위의 요청 사건을 코드가 정한다: `Q1, Q2, …` ↔ 원문 ↔ `tmp:Q1…`(question, user, asked, `record_evidence` 근거). 이 매핑을 요청·추출 변환에 그대로 넘기고, `add_user_requests`는 덮인 원문을 건너뛴다.
- 같은 세션의 앞선 미답변 요청(E)은 그래프 전체에서 고르고(잘린 `existing_edges`로 판단하지 않는다), 원문 ID·세션과 함께 `existing_events`에 넣는다. 상한에 밀리지 않게 `Harness.context`의 단서(`clues`)로 넣는다(감사 경로의 `keep_events`와 같은 방식). 개수 상한을 둔다(가장 최근 5개).
- `STORY_SCHEMA`의 이야기 사건에서 `actor`를 없앤다: 모델이 쓰는 사건은 모두 어시스턴트 것이다. 사람 사건은 코드만 만든다(Q와 질문 답). 모델이 쓴 이야기 ID가 Q·K·R과 겹치면 그 사건은 거절한다.
- `story.md`: "각 요청(Q, 또는 kind question인 E)에 대해, 어시스턴트가 그 요청에 답하거나 결과를 전달한 이야기 사건이나 작업 항목으로 `answers`를 잇고, 답한 내용이 있는 블록을 인용할 것. 계획만 말하거나 되묻는 블록은 답이 아니다. 이 구간에서 답하지 않았으면 잇지 말 것. 요청 자체를 사건으로 만들지 말 것."

## 4. 모델이 단 답변을 코드가 거르기 (`claimed_answer`)

남기는 조건(`answers`, explicit, 근거는 인용 블록만. 블록이 없을 때 양 끝 근거로 대신하지 않는다):

- 출발이 요청: Q, 또는 §3에서 넘긴 미답변 E
- 도착이 요청이 아닌 이야기 사건이나 작업 항목
- 보존된 인용 블록 중 어시스턴트가 쓴 것이 있고, 그 블록이 요청과 같은 세션(같은 provider·session)에서 **요청 뒤**에 있다. 순서는 시각 문자열이 아니라 단위 안 기록 순서로 본다(같은 시각·시각 없음에도 맞게). 앞선 단위의 E는 이 단위의 어떤 블록보다 앞선다.
- "다음 사람 메시지 전" 상한은 두지 않는다: 보충 요청이 끼어도 최종 보고가 둘 다에 답할 수 있다.

거른 주장은 이유와 함께 단위 한계에 남기고(`story: answer not kept: …`), 거른 연결이 가리킨 실행(R)은 사건이 되지 않는다(`refusals`에 합친다). 같은 순서 규칙을 `claimed_check`에도 적용한다(지금은 시각 문자열 비교).

남는 위험(검수): 같은 세션에서 Q2 뒤에 Q1에 대한 설명이 이어지면 "Q2 → Q1의 답"도 조건을 통과한다. 코드는 명백한 모순만 거르고 의미는 모델 몫이다. 측정에서 이 경우를 따로 센다.

## 5. 코드가 답변을 지어 붙이지 않는다

초안의 `answer_turns`(같은 턴의 답글을 인용한 사건에 코드가 `answers`)는 **버린다**. 계획만 말하고 멈춘 턴, 되묻는 턴, 단위를 넘는 긴 턴에서 거짓 "답변됨"을 만들고, 단위 1의 계획이 답으로 고정되면 단위 2의 진짜 결론이 연결되지 않는다. 대화 구조는 지금처럼 `follows`(대화 순서)만 코드가 만든다.

## 6. 화면: "답변 없음"을 정직하게

`render.status_labels`/`status_tones`, 모든 파이프라인:

- `answers`가 있으면 `✓ 요청 · 답변됨`(지금 그대로)
- `answers`는 없지만 그 턴에 이어진 사건(`follows`, 대화 순서)이 있으면 `요청 · 답변 연결 없음`(기본 톤, 경고 아님)
- 이어진 사건도 없으면 `! 요청 · 답변 없음`(경고)

## 7. 측정

- holdout 10단위(정답표 §1): (a) Q만 + 거르기, (b) (a) + 분류(§2). 지표: 놓침, 틀림(다른 요청의 답 포함), 요청이 아닌데 요청으로 보이는 메시지, 거른 주장의 이유.
- **새 단위로 최종 판단**: priceimpact의 다음 10단위(설계에 쓰지 않은 것)에서 정답표를 먼저 쓰고 같은 지표. 목표: 틀림 0, 요청 아닌 요청 0. 놓침은 v1 수준 이하.
- 읽기 테스트 한 번(점수가 떨어지지 않는지).
- v2 Haiku, v2 Luna(high). 같은 세션의 단위를 병렬 추출하면 앞 단위의 요청이 아직 없다: 단위 간 답변은 순차 실행(기본 workers=1)에서만 보장한다고 적는다.

## 8. 범위 밖(따로)

- 기존 그래프 보정: 이미 게시된 화면 이벤트 요청 상자, 질문 답 요청 상자. 내용 해시가 그대로라 재분석으로는 고쳐지지 않는다. 게시 시점 정리(그 원문이 이제 사람 메시지가 아닌 요청 사건을 숨김)를 버전 있는 보정으로 따로 설계한다.
- 하위 에이전트 단위에서 부모의 지시문이 글 블록에서 빠진다(`written_blocks`가 사람 메시지만 넣고, 하위 에이전트의 user 메시지는 부모 지시라 빠진다). 요청(Q)이 아닌 "부모 지시" 블록으로 보여 주는 일은 따로(§8.2의 하위 에이전트 단위가 빈약했던 원인 후보).
- 자동 매시간 보고 지시: 형식은 요청, 사람이 친 것은 아니다. 지금은 요청으로 둔다.
- Codex의 턴 시작·끝(`task_started`/`task_complete`)과 어시스턴트 commentary/final 구분은 `SourceRecord`에 없다. 코드가 "최종 답글"을 고르지 않으므로(§5) 이번 계획에는 필요 없다.

## 9. 테스트 (합성 자료)

- Q ID ↔ 요청 사건, `add_user_requests`가 두 번째 사건을 만들지 않음, 모델의 사람 사건·ID 충돌 거절.
- `claimed_answer`: 같은 세션 요청 뒤 블록 → 남김. 요청 앞 블록·다른 세션·블록 없음·요청끼리 → 거름. 보충 요청이 끼어도 남김. 같은 시각 기록의 순서.
- 앞선 단위의 미답변 E로의 연결, 상한에 밀리지 않음.
- 질문 답: 턴 경계 아님, 블록에 남음, 선택지와 같으면 사람 결정, 자유 서술은 사건 없음. 화면 이벤트 래퍼 전체만 제외(뒤에 글이 붙으면 남김).
- 화면 세 가지 상태.
- v1 요청 생성 기존 테스트 그대로, note·audit 경로 회귀.

순서: §2 → §3·§4 → §6 → §9 → §7.

  - 초안이 검사에서 떨어지면 v2도 통합 호출(입력 약 6만 자)로 넘어간다. 이번에 단위당 입력 토큰이 9k → 23~28k로 오른 원인. 위 두 버그를 고친 뒤 같은 단위의 초안은 통과한다. v2에서 초안 실패 시 통합 대신 작업 기록만 게시할지는 따로 정한다.
- 남은 일: 기존 그래프 보정(§8), 하위 에이전트의 부모 지시 블록(§8), 같은 턴의 반복 보고를 하나로 묶은 사건의 요청 연결.
