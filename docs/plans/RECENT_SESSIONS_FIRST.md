# 최근 세션 먼저 분석 (`--recent`, `--since`)

상태: 구현됨, Mock·합성 데이터로만 확인 (2026-10-09). 실제 모델로 돌려 보는 일은 로컬 확인 대기(`NEXT_STEPS.md` 1절).

## 1. 왜

소유자 결정(2026-10-09): 전체 이력 분석의 기본은 **오래된 것부터**로 둔다. 관계는 앞 사건에서 뒤 사건으로 가고(`prompts/common.md`), 단위는 그 시점의 그래프에 한 번만 통합된다. 최신부터 하면 수정이 고친 대상, 검증이 확인한 변경이 아직 없어 관계가 끊긴다.

대신 큰 프로젝트를 처음 분석할 때는 수십 시간을 기다리지 않고 **최근 세션부터** 보고 싶다. note를 켠 뒤의 새 작업은 에이전트가 직접 적으므로, 이 기능의 대상은 "note를 켜기 직전의 최근 세션들"이다. 이미 있는 `--session <id>`(세션 하나와 그 sub-agent)를 세션 여러 개로 넓힌 것이다. 새 파이프라인은 없다.

## 2. 명령

```
contexttrail scan    . --recent 5            # 계획만 (모델 없음)
contexttrail analyze . --recent 5 --units 8
contexttrail analyze . --since 7d            # 최근 7일 안에 끝난 세션
contexttrail analyze . --since 2026-10-01 --recent 10
```

- `--recent N`: 가장 최근 N개 세션. `--since WHEN`: 그 시각 이후에 끝난 세션. 둘을 함께 주면 `--since`를 만족하는 것 중 최근 N개.
- `WHEN`은 기간(`36h`, `7d`, `2w`, 지금부터 거꾸로)이나 날짜·시각(`2026-10-01`, `2026-10-01T09:00:00+09:00`; 시간대가 없으면 UTC). 명령줄이 UTC 시각으로 바꿔 `AnalysisConfig.since`에 넣으므로 엔진은 시계를 읽지 않는다.
- 이름: `--session`이 "이 세션"이므로 복수형 질문("최근 몇 개")은 `--recent N`, 기간은 `--since`가 자연스럽다. `--last`는 `--recent`와 뜻이 같아 하나만 둔다. 두 값 모두 이번 실행에만 쓰이고 저장하지 않는다(`--units`, `--max-calls`, `--session`과 같다).
- `analyze`, `scan`, `view`, `serve`가 `--session`과 같은 자리에서 받는다(터미널 화면의 `R`도 같은 설정으로 돈다).

## 3. 정한 것

| 질문 | 결정 | 이유 |
| --- | --- | --- |
| "세션"의 단위 | 같은 프로젝트의 transcript 세션 중, 다른 세션이 띄우지 않은 것(Codex·Claude·opencode). 부모가 이 프로젝트 기록에 없는 sub-agent는 자기 자신이 한 세션이다. | 사용자가 말하는 "세션"은 대화 하나이고, sub-agent는 그 대화의 일부다. |
| "최근"의 기준 | 세션과 그 sub-agent(깊이 제한 없음)의 기록 중 **가장 늦은 `recorded_at`**. 시각 없는 기록은 무시하고, 시각이 하나도 없는 세션은 가장 오래된 것으로 센다. 동률은 세션 ID. | 시작 시각이면 오래 열어 둔 세션이 낡아 보이고, 지금 하고 있는 일이 빠진다. sub-agent가 부모보다 늦게 끝날 수 있어 부모는 가족의 마지막 기록을 따른다. |
| `--since` | 위 "가장 늦은 기록"이 기준 시각 이상인 세션. | 같은 기준을 쓴다. |
| note가 있는 세션 | 후보에서 **뺀다**(개수에도 넣지 않는다). 그 기록은 이미 처리된 것으로 표시돼 있어(`acknowledge_journaled`) 단위도 나오지 않는다. | 세지 않으면 note를 켠 직후 `--recent 5`가 note 세션 5개를 고르고 아무것도 하지 않는다. 계획 문구와 `scan`이 몇 개를 뺐는지 알려 준다. |
| 이미 다 처리된 세션 | **센다.** 선택은 처리 상태가 아니라 최근 순서로만 정한다. | 같은 `--recent 5`로 여러 번 나눠 돌려도 같은 다섯 개를 이어서 하고, 뒤로 번지지 않는다. 처리된 세션은 단위가 0개라 아무것도 보내지 않는다. |
| 고른 세션들 사이의 순서 | **오래된 것부터**(세션 안도 같다). 최신 세션 먼저가 아니다. | 관계는 앞에서 뒤로 간다. 고른 안에서는 앞 세션의 사건이 이미 그래프에 있어야 뒤 세션의 검증·수정이 걸 대상이 있다. 일부만 하고 멈추는 것은 `--units`가 정하고, 같은 선택으로 다시 돌리면 이어진다. (단위 수로 멈추면 고른 것 중 가장 최신이 남을 수 있다. 계획 문구가 몇 개 중 몇 개인지 보여 준다.) |
| 결과 표시 | 이번 실행이 추가한 사건은 `out_of_order_events`. **고른 세션 밖의 기록이 아직 처리 대기 중일 때만** 표시한다(Git 기록 포함). 고른 것이 대기 중인 전부이면 표시하지 않는다. | 오래된 것부터 순서와 같은 결과이므로 거짓 표시를 하지 않는다. `--session`도 같은 규칙이 됐다(예전에는 항상 표시). |
| 나머지 세션 | 나중의 일반 실행이 기본 순서로 채운다. 상태는 `partial`이고 `pending_records`가 남은 수를 센다. | 빠진 것을 숨기지 않는다. |
| `--units`, `--max-calls` | 그대로. `--units N`은 고른 세션의 단위 중 앞 N개, 호출 상한은 단위당 6(`--max-calls`로 고정). 단위 수 없이 주면 호출 상한이 멈춘다(기본 30 → 최대 15단위). | `--session`과 같다. 선택은 "무엇을"이고 단위 수·호출 상한은 "얼마나"다. |
| 동의 화면 | `plan_text` 앞에 한 줄: `최근 세션 먼저: 5개 세션(2026-10-03 ~ 2026-10-08; 8f3a1c2d, …)의 단위만 · note 세션 2개 제외 · 나머지 세션은 나중의 일반 실행(오래된 것부터)이 채움`. `scan`의 JSON `plan.selection`에 세션별 ID·마지막 시각·단위 수, 후보 수, 제외한 note 세션 수. | 어느 세션을 먼저 보내는지 동의하기 전에 보인다. 길면 최근 5개 ID만 쓰고 나머지는 생략 표시. |
| `--session`과 함께 | **거부**(`함께 쓸 수 없습니다`). | 둘 다 "무엇을"이라 뜻이 겹친다. 합치면 어느 쪽이 이기는지 추측이 된다. |
| `--audit`와 함께 | **거부.** 감사할 세션은 `--session`으로 고른다. | 감사는 note가 있는 세션을 읽고 `--recent/--since`는 note가 없는 세션을 고른다. 반대 집합이다. |
| `--trigger hook`(자동 갱신) | **거부.** 훅은 오래된 순서를 유지한다는 기존 결정. 훅이 이 옵션을 넣는 일은 없고, 사람이 넣어도 막는다. | |
| 고른 게 없을 때 | 오류로 끝낸다(후보 수, 제외한 note 세션 수, `--since` 이후 없음을 말한다). 모델은 부르지 않는다. | `--session nobody`와 같다. 조용한 빈 실행은 "분석했다"로 읽힌다. |

## 4. 구현 지점

- `analysis.recent_sessions`(고르기), `since_cutoff`(`--since` 해석), `Engine._select_sessions`(`--session`과 `--recent/--since`를 한 곳에서). `_plan_units`의 `family`/`in_scope`가 그대로 받는다: 고른 가족의 단위만 계획하고, 그 안을 스냅숏 순서(시간순)로 정렬한다. 저장된 미통합 단위(`extracted` 등)도 같은 범위로 거르므로 다른 세션의 단위는 건드리지 않고 `superseded`로 바꾸지 않는다.
- `Engine.ahead_of_order`: `_plan_units`가 정한다. `studio_graph.publish_result`가 이것으로 `out_of_order_events`를 채운다(`--session` 포함).
- `Engine.plan_fields`: 감사 또는 선택 계획 필드. `preview_plan`(`scan`)과 `plan_work_units`(실행)가 같은 함수를 쓴다.
- 실패 단위 건너뛰기·보류(`_hold_back_failed`)는 고르기 뒤에 적용되므로 그대로 맞물린다: 고른 세션의 단위가 실패하면 건너뛰고 `partial`로 끝나며, 같은 선택으로 다시 돌려도 같은 입력이면 보내지 않는다(`--retry-failed`로 강제). 호출 상한(`_can_start`)도 그대로다.
- **모델 입력은 바뀌지 않는다.** 프롬프트, limitation, 검증 메시지를 더하지 않았다. 계획 문구와 오류는 사람이 읽는 화면 문자열(`tr`)이다. 그래서 `informational` 목록과 라우팅 서명(`_routing_signature`)도 건드리지 않아 끝난 단위가 다시 보내지지 않는다.

## 5. B: 분석 기간 제한(저장하는 "이 날짜 이후만")은 하지 않는다

이유:

- A로 필요가 거의 채워진다. `--since 30d`나 `--recent 20`으로 최근 것을 먼저 하고, 오래된 것은 일반 실행을 돌리지 않으면 되고, 남은 것은 `pending_records`/`partial`로 정직하게 보인다.
- 저장하는 제한은 "빠진 것"의 뜻을 바꾼다. 제한 밖 기록을 `pending`에서 빼면 `complete`가 거짓이 되고, 넣으면 영원히 `partial`이다. 둘 다 `freshness`, `status`, `find`의 머리말, `finish_run`, 보류(`_hold_back_failed`), `acknowledge_*`, 계획 문구를 함께 고쳐야 하고, 제한 문구를 모델 입력(`input_limitations`)에 넣으면 `informational` 목록과 라우팅 서명도 건드린다. 작지 않다.
- 쓰는 사람이 실제로 "영구히 제외"를 원하는지 아직 모른다. 필요하면 별도 설계로: "분석하지 않음"을 `skipped_by_window`로 따로 세어 `status`와 limitation에 항상 보이고, `complete`는 "제한 안에서 완료"로 구분한다.
