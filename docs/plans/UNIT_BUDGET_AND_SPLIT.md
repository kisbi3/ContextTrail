# 단위 입력 예산 산정과 분할

**상태: 제안. 미구현. 측정은 완료. 2026-09-29 검수에서 빠진 점 두 가지와 결정 사항이 나왔다 — 7절.**

Linux 실측에서 발견된 결함. 171개 작업 단위 중 **46%가 처리되지 못하는** 원인이다.

측정 근거: [`artifacts/unit-budget-measurement-2026-09-29.json`](../reports/artifacts/unit-budget-measurement-2026-09-29.json) — 본문의 모든 수치가 여기서 나온다. 실행 배경은 [Linux 실측](../reports/LINUX_LIVE_EVAL_2026-09-28.md).

> **측정의 한계:** 페이로드 크기는 **현재 그래프 상태에 따라 변한다.** `existing_events`, `existing_evidence`, `context_only`가 분석이 진행될수록 커지므로 아래 숫자는 한 시점의 값이지 재현되는 상수가 아니다. 순서와 규모는 유효하고 절대값은 아티팩트 실행 시점에만 맞는다.

## 1. 증상

`project analyze --units 10` 이 2개 완료 후 중단됐다.

```
단위 완료 2/10 · 그래프 v4
오류: 분석 입력 예산을 초과했습니다. 이 단위는 처리 완료로 저장하지 않습니다.
```

3번째 단위에서 멈췄고 남은 7개는 실행되지 않았다. 이 프로젝트 기준 **4/171개(2.3%)** 만 처리된 상태다.

### 메시지가 의도한 것과 구현이 다른 점

메시지는 "이 단위는 처리 완료로 저장하지 않습니다"라고 한다. 단위 하나만 넘기고 다음 단위로 가자는 뜻으로 읽힌다. 하지만 구현은 **실행 전체 abort**다.

`studio_graph.py:907`의 최상위 `except`가 예외를 잡아 `status="partial"`로 끝내고 반환한다. 단위 수준으로 격리하는 경로가 없다.

격리만 하면 뒤쪽 단위들은 계속 처리되므로 **일부는 진행된다.** 다만 한계가 분명하다.

- 예산을 넘긴 단위는 여전히 처리되지 않는다. 원인이 남아 있으므로 다음 실행에서 같은 지점에서 다시 터진다.
- 이 프로젝트에서는 건너뛴 단위가 3번째에 있어, 뒤 167개가 진행될 수는 있지만 1개짜리 구멍이 남는다.
- 격리는 **완료를 보장하지 않는다.**

그래서 순서를 뒤집는다. **격리를 추가하는 게 아니라 1단계를 먼저 하고**, 1단계로도 넘치는 단위가 남으면 그때 격리를 보조 수단으로 둔다. 그만큼 격리의 필요성이 작아진다.

README §4는 이미 "예산을 넘으면 단위를 defer/fail 한다"고 적고 있다. **거부된다고 한 것도 아니고, 그 문장이 현재의 abort 동작을 정확히 서술하지도 않는다.** 서술이 실제보다 관대하다.

## 2. 왜 큰가

### 2.1 실제 페이로드 구성

실패한 단위(`<unit-id>`, 소스 79개)를 조립해 분해했다.

| 구간 | 측정 시점 | 크기 | 내용 |
| --- | --- | ---: | --- |
| `system` | 전송 직전 | 8,067 | `prompts/common.md` — 역할·규칙. 매 호출 동일 |
| `instructions` | 전송 직전 | 4,033 | `prompts/extract.md` — 이번 단계 지시 |
| `wire_contract` | 전송 직전 | 680 | 응답 형식 계약 (짧은 ID, 인용 규칙) |
| **`data` 소계** | 전송 직전 | **257,289** | 아래 표 |
| **전체 합계** | **전송 직전** | **270,166** | **`task_chars`(240,000)의 113%** |

`data` 257,289자의 구성. **이 표는 ID 치환 전 원본에서 측정한 값이라 위 합계와 더해지지 않는다.** `IdAliases.wire()`가 ID를 `src_…`(28자)에서 `S12`(3자)처럼 짧게 바꾸면서 줄기 때문이다. 비율과 순서만 읽을 것.

| --- | ---: | --- |
| `new_records` | 101,226 | 이 단위가 직접 다룰 로그 |
| `context_only` | 78,525 | 앞선 기록에서 끌어온 참고 문맥 |
| `manifest` | 34,439 | 읽기 가능 범위 주소록 |
| `existing_evidence` | 20,917 | 저장된 인용 |

`new_records`와 `context_only` 둘 합이 179,751자로, 이 표의 키 합(275,323자)의 약 65%다(위 표시된 `data` 257,289자 기준으로는 70%). **단위 자기 내용과 끌어온 문맥이 예산의 대부분을 차지한다.**

`new_records` 1건의 실제 구조:

```json
{
  "source_id": "<source-id>",
  "session_id": "<session-uuid>",
  "recorded_at": "<timestamp>",
  "cwd": "<lab-host>:<project>",
  "worktree_id": "<worktree-id>",
  "tool_call_id": "<call-id>",
  "git": { "commit_hash": "<commit>...",
           "branch": "main",
           "repository_url": "https://github.com/<owner>/<project>.git" },
  "content_hash": "<content-hash>",
  "lines": [ { "line": 1, "text": "Chunk ID: <redacted>" }, ... ]
}
```

`lines`가 실질 내용이고 나머지는 전부 **봉투**다. `context_only`는 같은 구조에 `context_only: true`가 붙는다.

### 2.2 예산은 무엇을 세는가

`unit_cost()`(`analysis.py:326`)가 세는 것: 레코드 **내용물**의 잘라낸 부분. 잘린 뷰를 가진 레코드에는 상수 120이 붙지만 봉투 크기와는 무관하다. 이 단위는 79개 중 77개가 잘림 대상이 아니라 그 상수도 붙지 않았다.

세지 않는 것: 레코드를 감싸는 모든 메타데이터.

| 필드 | 대략 크기 |
| --- | ---: |
| `source_id` | 28 |
| `cwd` (절대 경로) | 40 |
| `worktree_id` | 29 |
| `content_hash` | 64 |
| `git.commit_hash` | 40 |
| `git.repository_url` | 52 |
| `session_id` | 36 |
| `locator`, 줄 번호, `derivation`, `lineage` 등 | 약 600 |
| **레코드당 합계** | **약 900** |

79건 × 900자 = 71,100자.

```
unit_cost 합계        28,700   → unit_chars(60,000)의 48%  → "문제 없음" 통과
new_records 실제     101,226
간격                  72,526   ← 전부 봉투 비용
전체 페이로드         270,166   → task_chars 초과 → 실패
```

**"48%라 자르지 않아도 된다"는 판단이 3.5배를 놓쳤다.**

`context_only`도 같은 문제다. 자기 예산 `read_chars = 36,000`인데 78,525가 들어갔다.

### 2.3 검사 시점은 조립 이후 단 한 번

`analysis.py:1133-1134`:

```python
sent = aliases.wire(task)
if len(dumps(sent)) > self.config.task_chars:
    raise FlowError("분석 입력 예산을 초과했습니다. 이 단위는 처리 완료로 저장하지 않습니다.")
```

이미 만들어진 뒤에 재고, 넘쳤으면 예외뿐이다. 조립 과정에 되돌아가 덜어낼 수단이 없다.

### 2.4 범위는 단발이 아니다

미분석 167개 단위의 페이로드를 전부 조립해 잰다.

| | |
| --- | ---: |
| `task_chars`를 넘는 단위 | **76 / 167 (46%)** |
| 최대 페이로드 | 304,429자 (127%) |

상위 10개가 모두 280,000~304,000자다. 특정 세션의 문제가 아니라 **`tool_call`이 많은 대화의 일반적 형태**로 보인다. 프로젝트 사정이 아니라 구조적 결함이다.

> 참고: 원문 합계가 `unit_chars`를 넘는 단위는 96/167이지만, 그것은 **결정적이지 않다.** `unit_cost`가 절단을 반영하므로 계상 값은 예산 안이다. 문제는 계상과 실제의 간격이지 원문 크기가 아니다.

## 3. 쪼갤 수 있는가 — 있다

### 3.1 쪼갘으면 안 되는 것

도구 실행은 항상 쌍으로 나온다.

```
[11:20:03] tool_call    "CUDA_VISIBLE_DEVICES=0 pytest tests/ 실행"   ← 지시
[11:20:44] tool_result  "24 passed in 8.3s"                          ← 결과
```

이 둘을 갈라놓으면 두 가지가 깨진다.

1. 모델이 "무엇을 실행했는지"만 보고 "결과가 어땠는지"를 모른다. `observed_success`를 근거 없이 만들어낸다.
2. `tool_call_id`로 묶인 쌍이 서로 다른 단위에 흩어져 연결이 끊긴다.

### 3.2 쪼갘어도 되는 지점

- `tool_result` │ 다음 `tool_call` — 쌍이 앞쪽에 온전히 있음
- 사람 발화(`assistant`) 직후 — 새 요청의 시작점

### 3.3 이미 계산되고 있다

`analysis.py:629-646`에 이 규칙이 이미 있다. `tool_call_id` 쌍과 `lineage.fragment_of` 사슬이 경계를 가로지르지 않는 위치를 `safe` 경계로 모은다.

```python
last_link[(kind, str(value))] = index          # 각 id의 마지막 위치
...
if boundary == len(ordered) or open_until >= boundary:
    continue                                    # 쌍이 걸치는 경계는 제외
safe.add(boundary)
```

**쪼개는 법을 모르는 게 아니다. 부르지 않았을 뿐이다.** 계상 값이 48%여서 "자르지 않아도 된다"고 판단했고, 그 판단이 틀렸다.

### 3.4 실패한 단위의 실제 쪼갤 가능 지점

레코드 79개, `tool_call_id` 쌍 34개.

```
전체 경계          78
쪼갤 수 있는 경계   37
쌍 내부가 막는 경계  41
→ 최대 분할 조각     38개
```

경계 78개 중 **41개가 쌍 내부**라 자를 수 없다. 즉 여유가 있는 게 아니라 **절반뿐**이다. 쪼갤 수 있는 37개는 그만큼 조각이 나오는 근거가 된다.

> 정정: 이 문서를 초안에 썼을 때 "68 경계 / 69 조각"이라고 적었는데, 쌍 내부를 제외하지 않은 계수였다. 재측정 결과가 위 값이다. `tool_call` 34 + `tool_result` 34가 자연 순서에서 쌍을 이루므로 경계 중 최소 34개는 쌍 내부여야 하고, 실측이 41이다.

### 3.5 쪼갤 크기의 현실적 상한

38조각이 나오지만 균등하지 않다. 실제로 예산을 1/3로 낮춰 재현한 결과는 2조각(60 + 19)이었다. 경계는 쌍 뒤에만 있으므로 조각 크기가 고르게 분포하지 않는다. **2단계는 "한 번에 38조각"이 아니라 "예산을 넘으면 한 쌍 경계에서 잘라 다시 시도"를 반복해야 한다.**

## 4. 제안

세 단계다. 1단계를 건너뛰면 2단계가 커버해야 할 범위가 줄지 않는다.

### 1단계 — 산정 고치기 (반나절)

`unit_cost`가 **실제로 전송되는 문자 수**를 세게 바꾼다.

- 레코드당 봉투 비용을 상수로 더하거나
- 조립 후 실측해 그 값을 분할 판단에 반영하거나
- **둘 다.** 상수로 대충 좁힌 다음 실측으로 보정

`context_only` 쪽도 같은 방식으로 고친다. 현재 `read_chars`와 실제의 간격이 2.2배다.

같이 줄일 것:

- `git.repository_url`은 모든 레코드에 동일하게 반복된다. 단위 단위로 한 번만 두고 참조만 넣으면 79건 기준 약 4,100자를 절약한다. **계정 식별자가 반복 노출되는 문제도 같이 사라진다.**

### 2단계 — 안전한 지점에서 분할 (하루)

`_session_unit_chunks`에 조건을 하나 추가한다.

> 조립 예상 페이로드가 예산을 넘으면, `safe` 경계에서 쪼개고 다시 시도한다.

`safe` 경계 목록은 이미 계산되어 있으므로 반복하면 된다. 단위 `id`가 content hash 기반이라 쪼갠 결과도 결정론적이다. 재실행해도 같은 분할이 나온다.

주의: 분할된 단위는 "같은 세션의 연속 구간"이므로 통합 시 관계가 이어져야 한다. `link_request_turns`가 대화 순서로 매단다.

### 3단계 — 그래도 넘으면 덜어내기 (반나절)

`context_only`부터 줄인다.

- `context_events` 24 → 12
- `read_chars` 절반
- 우선순위부터 잘라낸다 (같은 파일 경로·같은 세션·명시적 참조 순)

정보다 소실되지만 단위는 처리된다. 2단계까지 해도 넘으면 이 단계가 필요할 수 있다.

## 5. 검증 방법

각 단계는 되돌려 보고 깨지는지 확인한다. 이전 회귀 테스트들이 이 문제를 놓쳤듯, 결과만 확인하는 테스트는 worthless다.

| 단계 | 판정 |
| --- | --- |
| 1단계 | 167개 단위 전부 조립해 `unit_cost` 예측값과 실제 페이로드의 오차가 기준 이하인지 |
| 2단계 | `analysis --units 10`이 10개를 완료하는지. 3번째 단위가 69개 이하로 쪼개지는지 |
| 2단계 | 쪼갠 뒤 `tool_call`/`tool_result` 쌍이 서로 다른 단위에 들어가지 않는지 |
| 2단계 | 쪼감 뒤 조각 수가 **1**이면 실패다. 쪼갤 수 있는 경계가 없는 경우다 |
| 2단계 | 동일 입력 재실행 시 동일 분할이 나오는지 |
| 3단계 | 문맥이 줄었을 때 사건 수와 품질 저하 폭 |

전 단위 조립 검사는 AI 호출 0으로 가능하다. `project eval --preview` 경로를 재사용하면 된다.

## 6. 예상 효과

| | |
| --- | --- |
| 처리 불가 단위 | 76/167 (46%) → 0 목표 |
| 최대 페이로드 | 304,429 → `task_chars` 이하 |
| 1단계만 | 1단계는 초과를 줄이지만 제거하진 못한다 |
| 1+2단계 | 37개 쪼감 지점이 있으므로 반복 분할로 예산 아래로 내릴 수 있다. 조각이 균등하지 않아 단几次 반복이 필요할 수 있다 |
| 1단계 없이 2단계 | 분할로 통과하되, 예산 계정이 계속 어긋나 있어 규모가 더 크면 재발한다 |

**1단계를 먼저 하는 이유:** 계정이 고쳐지지 않으면 2단계가 "몇 개 쪼갤지"를 근거 없이 정해야 한다. 1단계가 있어야 2단계가 정량 판단이 되고, 3단계의 절감량도 정해진다.

## 7. 검수 후 정정과 결정 (2026-09-29)

위 제안을 코드와 대조해 검수한 결과다. 1·2번은 제안 자체의 빠진 점이고, 3번 이후는 이 대화에서 정한 방향이다.

### 7.1 빠진 점 1: 이미 실패한 단위는 저장되어 있어 재분할되지 않는다

- `Engine._extract_unit`은 예산 검사(`analysis.py:1133`, `Harness.task` 안)보다 **먼저** `save_unit(..., "parsed")`를 실행한다(`analysis.py:1493`). 그래서 예산에서 실패한 단위는 소스 목록 그대로 `work_units`에 남는다.
- `_plan_units`(`analysis.py:1657`)는 저장된 미통합 단위를 **그 소스 목록 그대로** 다시 계획에 넣고, 그 레코드를 `scheduled`에 넣어 새로 묶는 대상에서 뺀다.
- `superseded` 상태는 `_plan_units`가 읽기만 하고(`analysis.py:1691`) 어디서도 쓰지 않는다.
- 결과: 2단계를 `_session_unit_chunks`에만 구현하면 새 단위만 쪼개지고, 이미 막힌 단위와 같은 이유로 실패한 다른 단위들은 계속 막힌다.
- **추가할 것:** 저장된 미통합(`parsed`·`draft`) 단위의 소스를 새 규칙으로 다시 묶어 보고, 묶음이 다르면 옛 단위를 `superseded`로 돌려 그 레코드를 다시 계획에 돌려보낸다. 통합이 끝난 단위(`integrated`, `extracted`)는 건드리지 않는다.

### 7.2 빠진 점 2: 로그가 아닌 부분이 예산의 70%다

- 전송 270,166자 중 `new_records`(101,226자)를 뺀 약 168,940자가 `task_chars`의 70%다. 1단계로 레코드 몫을 `unit_chars`(60,000)에 맞추면 합계는 약 229k/240k로 여유가 4%다.
- 이 중 `manifest`·`tool_steps`·`assigned_source_ids`(약 4.6만자)는 단위 크기에 비례해 줄 것으로 보인다(측정 전). `context_only`(78,525자)와 지침(약 1.3만자), `existing_*`(약 4.2만자, 그래프와 함께 커짐)는 단위를 쪼개도 조각마다 다시 붙는다.
- 따라서 **3단계(문맥 줄이기)는 "필요할 수 있다"가 아니라 필수**다. `manifest`(34,439자, 13%)가 어느 단계에도 없었다. 3단계 대상에 넣는다.
- `unit_records = 80`(`AnalysisConfig`) 상한도 같이 본다. 실패한 단위는 79개 레코드라 글자 수가 아니라 개수 상한에 걸려 잘렸을 가능성이 있다(미확인).
- 1단계로 단위가 작아지면 단위 수와 호출 수가 늘 것이다. 효과 표(6절)에 이 비용이 없다. 실측으로 채운다.

### 7.3 결정: 상수만 낮춰 전부 작게 쪼개지 않는다

`unit_chars`만 낮추면 가장 작은 변경이지만 채택하지 않는다.

- **채택:** 1단계로 실제 전송량을 재고, 목표를 `task_chars`의 60% 안팎으로 둔다. 무거운 단위만 작아지고 가벼운 단위는 그대로 크다.

### 7.4 결정: 자르는 위치 — 요청 직전, 실행 결과 직후

"요청 → 시도 → 결과"를 각각 별도 단위로 보자는 제안을 검토했다. 세 수준으로 나눴다.

| | 내용 | 판정 |
| --- | --- | --- |
| A | 요청 하나를 한 단위로 | 이미 반쯤 그렇다. 묶기 코드가 요청 직전(`turns`)을 우선한다. 한도를 넘는 요청은 B로 |
| B | 요청 안에서 시도와 결과 사이를 자름 | **채택.** 우선순위: 자연스러운 끊김 > 요청 직전 > **실행 결과 직후** > 그 외 안전한 경계 |
| C | 요청·시도·결과를 각각 별도 호출 | 비채택. 호출이 폭증하고, 결과만 보면 무엇을 확인한 건지 쓸 수 없다 |

- 실행 결과 직후는 도구 호출과 결과 쌍이 끝난 지점이라 안전하다. 도구 단계의 `hint`(`edit`/`read`/`run`)로 찾는다(`extract_request_data`).
- 조각 사이 연결은 지금 구조가 이미 한다: 통합 단계가 기존 사건과 잇고, `link_request_turns`가 요청에서 그 턴의 사건으로 `follows`(구조적)를 만든다.
- 뒷조각이 앞조각의 시도를 참조할 수 있도록 뒷조각 입력에 앞 시도의 **도구 단계 요약(수백 자)** 을 넣는다. 원문을 다시 싣지 않는다.
- 단위 간 연결의 품질은 아직 측정한 적이 없다. 이전 평가의 변동은 추출이 사건을 합치고 쪼개는 문제였고 단위 간 연결과는 별개다. 구현 후 평가로 확인한다.

### 7.5 측정 계획 (AI 호출 0)

구현 전에 실패한 단위와 큰 단위 상위 10개에서 잰다.
1. 안전한 경계 37개 중 요청 직전, 실행 결과 직후, 그 외가 각각 몇 개인가.
2. B 규칙으로 자르면 조각 수와 조각별 전송량은 얼마인가. 각 조각이 `task_chars` 안인가.
3. 목표를 `task_chars`의 60%로 둘 때 단위 수(호출 수)가 지금 대비 얼마나 늘어나는가.
4. `unit_records` 상한이 실제로 잘린 원인이었나.

### 7.6 수정된 실행 순서

1. 실제 전송량으로 재기(1단계) + 측정 7.5.
2. 저장된 미통합 단위를 다시 묶는 절차(7.1).
3. B 규칙으로 쪼개기(2단계) + 조각 사이 요약.
4. 문맥 줄이기(3단계): `context_only`, `manifest`, `context_events`, `read_chars`.
5. 마지막에 격리(1절): 그래도 넘치는 단위 하나가 실행 전체를 멈추지 않도록.
6. 각 단계는 되돌려 보고 깨지는 테스트로 검증한다(5절).

### 7.7 소유자 판단과 코드 확인 (2026-09-29, 이어서)

- **글자 수보다 의미 경계로 자르는 쪽이 품질에도 낫다는 것이 소유자 판단이다.** 요청 → 시도 → 결과를 각각 단위로 다루되 서로 연결한다. 코드로 보면 셋으로 나누는 것은 그대로는 안 된다.
  - 요청은 모델 없이 코드가 사용자 사건으로 만든다(`add_user_requests`, `link_request_turns`). 요청만으로 단위를 만들 필요가 없다.
  - 도구 호출과 그 결과는 한 쌍이다. 둘 사이는 "막힌" 경계(쌍 안쪽)라 자를 수 없다.
  - 그래서 실질적인 단위는 "시도+결과 묶음"이고, 자르는 규칙은 7.4절의 B(실행 결과 뒤)와 같다. 다음 조각에는 앞 시도의 얇은 도구 단계 요약을 붙인다.
- **문맥 줄이기는 쪼개기의 전제다.** 조각마다 문맥 약 12만 자가 다시 실린다(`context_only` 78,525, `manifest` 34,439 등). 조각을 잘게 할수록 호출당 고정 비용이 그대로 반복되므로, 문맥을 줄이지 않고 잘게 쪼개면 호출·토큰이 늘기만 한다. 4단계(문맥 줄이기)를 3단계(쪼개기)보다 먼저, 또는 함께 한다.
- **`context_only`가 큰 이유 (`analysis.py` `Harness.context`, 코드로 확인):**
  - 들어가는 기록: (a) 배정된 첫 기록 바로 앞 4개, (b) 15분 안의 다른 출처(git 등) 최대 4개, (c) 관련 사건 24개가 인용한 기록 전체, (d) 같은 도구 호출 기록.
  - (c)는 기록 전체를 다시 보낸다(`self.provide(record.source_id)`, 줄 범위 없음). 사건의 인용은 `existing_evidence`에 이미 있는데 원본 기록 전체를 한 번 더 싣는다. 인용 줄 앞뒤 몇 줄만 보내면 줄어들 여지가 있다. 측정 전이다.
  - **예산 계산 결함이 같은 종류로 또 있다.** 문맥 예산 `read_chars`(36,000)는 기록 원문 길이(`len(record.content)`)로 센다. 그러나 실제로는 `provide`가 줄마다 `{"line": n, "text": …}` 객체와 기록 메타데이터를 붙여 보낸다. 문제 단위에서 원문 36,891자가 `new_records` 101,226자로(약 2.7배), `context_only`는 예산 36,000자인데 78,525자로 나갔다. 줄 래핑과 기록 메타데이터가 각각 얼마인지는 측정 전이다.
  - 줄을 `"12| 본문"` 같은 문자열로 보내면 모든 기록(`new_records`, `context_only`, 읽기 요청 응답)이 한꺼번에 줄어들 수 있다. 인용 검증은 줄 번호로 하므로 바뀌지 않지만, 모델이 보는 형식이 바뀌므로 프롬프트와 평가 재확인이 필요하다.
- 측정 계획(7.5절)에 추가: `context_only`를 (a)(b)(c)(d) 이유별로 나눈 글자 수, 줄 래핑과 메타데이터 비중, 인용 ± N줄만 보냈을 때의 크기.

### 7.8 의미 경계로 자르는 방법 — 검토 (2026-09-29)

세 가지를 비교했다. 결정 전이다.

| 방식 | 하는 일 | 장점 | 위험 |
| --- | --- | --- | --- |
| 규칙 기반 (B) | 압축·공백, 사용자 메시지 앞, 실행 결과 뒤 순으로 자른다 | 모델 호출 0회. 단위 ID가 기록 내용 해시로만 정해져 안정적이다. 테스트로 고정할 수 있다 | 주제 전환은 모른다. 사용자 메시지 없이 오래 이어지는 작업은 실행 결과 사이에서만 자른다 |
| 모델 분할기 | 세션의 얇은 개요(요청, `tool_steps`, 결과 첫 줄)만 보고 경계와 주제를 정한다 | 의미에 가장 가깝다. 개요가 작아 세션당 호출이 적다 | 비결정적이라 단위 ID·"다시 보내지 않는다" 불변식과 충돌한다. 호출과 동의 절차가 늘고, 잘못 자를 수 있다 |
| 혼합 | 코드가 안전한 후보 경계를 종류와 함께 주고, 모델은 그중에서만 고르거나 거절하고 묶음 이름을 붙인다 | 모델이 만든 경계가 후보 밖이면 코드가 거부하므로 안전 검증이 유지된다 | 결과를 세션별로 저장해 두어야 한다. 이미 통합된 부분은 절대 다시 자르지 않고, 아직 처리하지 않은 뒤쪽만 대상으로 한다 |

- **하위 에이전트(대화 기록 안의 sub-agent)는 이미 의미 경계다.** 부모가 띄운 하위 에이전트 세션은 별도 세션이라 자연스럽게 다른 단위가 되고, 부모의 직전 메시지가 요청, 하위 에이전트의 마지막 보고가 결과 역할을 한다(`link_request_turns`가 부모 메시지에 잇는다). 하위 에이전트를 많이 쓴 프로젝트일수록 규칙 기반 경계가 의미와 잘 맞을 가능성이 있다. 이 비율은 측정 전이다.
- **모델 하위 에이전트로 앞 조각을 요약해 다음 조각에 붙이는 안:** 요약은 코드가 `tool_steps`(종류, 대상, 결과 첫 줄, 실패 여부)로 이미 만들 수 있고, 통합이 끝난 앞 조각은 그 사건들이 `existing_events`로 실린다. 다만 다음 단위를 미리 추출하는 경로(`_prefetch_next`)에서는 앞 조각 통합이 끝나기 전에 추출하므로 그래프에 앞 조각 사건이 없다(미리보기가 "provisional initial graph"라고 표시하는 이유). 앞 조각과 이어져야 할 때 이 경로를 어떻게 다룰지 정해야 한다.
- **권고:** 먼저 규칙 기반 B로 만들고 측정한다. 남는 문제(너무 큰 조각, 어색한 경계)가 수치로 보이면 그때 혼합안을 도입한다. 모델 분할기가 자유롭게 경계를 정하는 방식은 불변식과 충돌하므로 택하지 않는다.
- **측정 도구:** `scripts/measure_unit_payloads.py`. 실제 ddakrate 기록을 읽는 실행은 2026-09-29에 자동 승인 검사(개인정보 처리)에서 거부되어 아직 하지 못했다. 합성 데모에서는 앞부분(조립·크기·이유별 분류)만 돌아가는 것을 확인했고, 모의 분할 부분은 아직 검증되지 않았다.

### 7.9 결정: 분류·문맥·컷 순서 (2026-09-29, 소유자 승인)

소유자가 아래 방향을 승인했다. 구현은 아직 하지 않았고, 순서와 조건은 이 절이 기준이다.

1. **분류는 코드가 먼저, 애매한 것만 모델.** 편집 도구·패치 표식(edit), 읽기 전용 명령(read)은 코드 판정을 그대로 쓴다. 지금 `run`으로 떨어지는 셸 명령 중 애매한 것만 모델이 분류한다.
   - 모델은 `run`을 `edit`/`read` 등으로 올리기만 하고, 코드가 확실한 edit을 내리지 못한다. 실패하면 코드 힌트로 되돌린다.
   - 세션마다 명령 한 줄 요약을 모아 한 번에 묻고, 결과를 명령 해시별로 저장해 다시 묻지 않는다.
   - 자르는 시점이 추출보다 앞이므로 이 분류는 추출 앞의 별도 단계다. 결과가 저장되어야 단위 ID가 안정된다.
   - 애매한 명령의 실제 비율은 측정 전이다. 비율이 낮으면 이 단계를 생략하고 코드 규칙만 늘린다.
2. **코드로 분류할 것을 늘린다.** `commit`(`git commit`, 결과의 `[branch hash]`로 Git 레코드와 연결), 검증 실행(`test`/`check`: 테스트·린트·빌드 명령), 그 밖의 버전 관리 명령, 하위 에이전트 호출, 계획 도구, 사용자에게 묻는 도구, 거절된 도구 호출. 도구 이름과 결과 형식은 실제 기록에서 확인한 뒤 넣는다.
3. **문맥을 먼저 줄이고 그다음에 자른다.** 모델이 쓰지 않는 `context_selection`(6.7k)은 모델 입력에서 빼고 원장에만 남긴다(프롬프트가 참조하지 않는 것을 다시 확인한 뒤). 그다음 `context_only`를 인용 줄 ± N줄로, 줄 형식을 압축 문자열로, 예산을 전달 글자로 센다. `manifest`, `existing_*`는 관련된 것만.
4. **자르는 위치는 실행 결과 뒤다.** 편집→실행→결과를 한 조각에 두어 `verifies`가 조각을 가로지르지 않게 한다. 우선순위: 압축·공백 > `commit` 뒤 > 사용자 메시지 앞 > 실행 결과 뒤 > 그 밖의 안전한 지점.
5. **조각 간 `verifies` 품질을 측정한 뒤에** 편집과 실행을 서로 다른 조각으로 나누는 안을 다시 판단한다.
6. 단계마다 되돌려 보고 깨지는 테스트로 검증한다. 문맥 형식 변경은 모델이 보는 입력이 바뀌므로 소유자 동의를 받은 평가로 확인한다.
