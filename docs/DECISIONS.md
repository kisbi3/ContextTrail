# 구현 결정 기록

2026-09-22 · 원본 PRD/SPEC v0.1은 기준선으로 그대로 보존한다. 이 파일은 현재 대화의 추가 합의와 개발자가 선택한 구현 방법을 구분한다.

## 사용자가 확정한 사항

| 항목 | 합의 | 문서 적용 |
| --- | --- | --- |
| 실제 사례 검증 | 사용자가 완성된 실행물을 자신의 프로젝트에 적용하고 평가 | 실제 프로젝트명·로그 선제 공유를 착수 조건으로 두지 않음. 기술 자동 검증은 별도 수행 |

## 이번 구현의 선택 — 사용자 요구 자체와 구분

**Python + SQLite:** SPEC의 기본안을 사용했다. Python 표준 라이브러리 `curses`로 TUI를 작성했다. 후보였던 Textual을 채택하지 않았고, 기본 화면에 마우스·터미널 이미지 프로토콜을 요구하지 않는다.

**안전한 Mermaid subset / 자체 SVG:** 프로그램이 출력하는 제한된 노드·관계 문법만 파싱하는 문자 렌더러와 자체 SVG 레이아웃을 만들었다. MMD export는 Mermaid flowchart 형식이다. 일반 Mermaid 입력·모든 Mermaid 배치 기능·공식 Mermaid JS 런타임은 제공하지 않는다. 외부 CDN이나 빌드용 Node 의존성을 제품에 추가하지 않았다. 실제 복잡한 도식의 가독성 검증은 남아 있다.

**bubblewrap 격리:** 실제 CLI 실행은 Linux bubblewrap 내부에서만 허용한다. CLI 네이티브 인증 파일은 read-only bind로 연결하되, 사용자 설정·hooks·프로젝트 문서·원본 폴더를 통째로 노출하지 않는다. 파일 기반 인증/CLI 옵션 호환 제약이 생기며, 실제 설치 환경의 검증이 필요하다. 보안 검증이 불충분한 직접 실행 fallback은 두지 않는다.

**문자 수 기반 초기 예산:** 실제 fixture/모델을 측정할 수 없어 시작용 상한을 명시했다. 최적값·토큰 길이·처리 비용·성능을 보장하지 않는다.

**검증 단계:** 합성 fixture·Mock Runner·실제 로컬 Git·HTTP·PTY에 대한 자동 회귀 시험은 수행했다. 실제 CLI/model과 실제 사용자 단말 환경은 수행하지 않았다. 따라서 완성된 MVP 릴리스로 표시하지 않는다.

## 아직 결정하지 않은 것

최종 제품명, 명령어명·패키지명의 공개 충돌 확인, 공개 라이선스, 실제 CLI 최소 지원 버전, 고용량 프로젝트의 기본 튜닝. 이 항목들을 임의로 확정하거나 다른 기능(Watch, Canvas, MCP 등)을 추가하지 않았다.

## 2026-09-23: 사용자가 승인한 계층화 방향

모든 기록을 대형 모델에 보내는 대신 Harness가 작은 추출 worker, 선택적 강한 재검토, 통합 모델을 관리한다. provider-native subagent는 사용하지 않는다. 단계 모델과 병렬 수를 명시하고, 비교 가능한 고정 fixture eval 및 로컬 Ops를 제공한다. 코드 단계의 프로젝트 선별은 선행조건으로 유지한다.

구현 선택: worker 기본 1/최대 8, 분석 호출 상한 200/eval 20, 같은 기준 graph의 bounded 병렬 추출 후 순차 통합. 계약 실패만 extraction validation recovery를 일으키며, 의미 검토는 통합 후 Delta issue를 기준으로 선택적으로 진행한다. 실제 모델 ID·비용·의미 품질은 미검증이다.

## 2026-09-25: 인용 검증과 평가 fixture 보강

`reviewed-live` 독립 의미 검토의 0·1단계 개선이다. 스키마 enum·관계 종류·프롬프트 routing signature는 바꾸지 않았다.

- **이스케이프 표기 인용:** Codex `exec` 도구 호출처럼 코드가 문자열 리터럴 안에 있으면 원문에는 `\"`·`\n`이 글자 그대로 남는다. 부분 인용이 원문과 0건 일치할 때만 한 겹의 이스케이프를 푼 조회용 사본에서 다시 찾는다. 그 사본에서 정확히 한 번 일치하고, 대응하는 원문 구간도 원문에서 유일할 때만 통과한다. 저장하는 quote와 hash는 항상 원문 표기 그대로이며 감사 모드는 `escape_decoded_substring_expanded_to_lines`다. 유사도 비교나 공백 무시 같은 완화는 하지 않는다.
- **인용 초점 보존:** 부분 인용은 계속 줄 전체로 정규화해 저장하되, 모델이 가리킨 문자 범위를 근거 항목의 `focus`에 남긴다. 줄 전체 인용은 focus를 만들지 않는다. 화면과 Markdown은 400자를 넘는 근거에서 focus 앞뒤 120자만 보여 주고, 전체 원문 줄은 근거 색인·웹 상세의 펼침·JSON export에 남는다.
- **수리 입력:** "유일하게 일치하지 않습니다" 인용 오류에도 `exact_source_lines`를 첨부한다. 수리 지시는 이스케이프 표기를 그대로 옮기고, 검증 통과만을 위한 짧은 조각 인용을 피하도록 요구한다. `wire_contract`의 "줄 전체" 문구를 common 프롬프트의 부분 인용 허용과 일치시켰다.
- **평가 fixture 완결성:** `project eval`, `--preview`, `scripts/make_eval_fixture.py`가 결과 없는 도구 호출, 호출 없는 결과, 시작 기록이 없는 `write_stdin` 세션 참조를 보고한다. 평가를 중단하지는 않고 report의 `fixture_integrity`와 `limitations`에 남긴다.
- **반복 인용:** 부분 인용이 여러 곳에서 일치해도, 모든 일치가 같은 줄 범위로 정규화되면 통과한다. Codex `apply_patch`처럼 패치 전체가 한 줄인 원문에서는 삭제 줄(`-`)과 추가 줄(`+`)의 같은 문구가 이 경우에 해당한다. 어느 일치를 골라도 저장되는 근거(ID·quote·hash)가 같으므로 근거의 무결성은 바뀌지 않는다. 일치 위치는 5곳까지 focus로 남기고, 그보다 많으면 줄 전체를 보여 준다. 여러 줄 Git diff에서는 일치한 줄이 모두 diff 본문 줄(`+`/`-`/공백)이고 같은 hunk 안에서 20줄 이내일 때만, 첫 일치 줄부터 마지막 일치 줄까지를 근거로 저장한다. `+` 줄을 자동으로 고르지 않으므로 삭제를 주장하는 인용이 잘못 연결되지 않는다. 그 밖의 반복은 기존처럼 거부한다. 2026-09-25 `expected-live-2`의 첫 추출·통합 응답을 재생하면 거부됐던 인용 3건이 모두 이 규칙으로 통과한다.
- **source 기준 기대값:** 모델 제목이 달라도 채점할 수 있도록, `source_ids`가 있는 사건 기대값은 `title_contains`를 생략할 수 있다.

## 2026-09-25: 변경과 검증의 분리 (그래프 스키마 2)

같은 검토의 2단계 개선이다. `expected-live-2`에서 모델이 패치 여러 건과 일부만 확인한 테스트 결과를 한 사건으로 묶어 "관측 성공"을 붙였다. 사건 요약에는 한계가 적혀 있었지만 그래프에는 제목과 상태만 보였다. 사용자 질문은 `proposed`("제안")로 표시됐고, 최종 답변은 사건이 되지 않았다.

- **변경과 확인 결과를 나눈다:** `observed_success`/`observed_failure`는 `outcome`에만 허용한다. 변경 사건에는 새 상태 `applied`(패치·diff 등 변경 기록 필요) 또는 `reported_complete`를 쓴다. 확인은 새 관계 `verifies`(변경 → 그 변경을 실제로 실행·시험한 관측 결과)로 표현한다. `verifies`는 `inferred`일 수 없고, 도착점이 관측 상태가 아니게 갱신되면 GraphDelta 전체를 거부한다.
- **질문과 답:** 새 kind `question`과 상태 `asked`를 둔다. 답은 새 관계 `answers`(질문 → 답한 사건)로 표현한다. 사용자 질문·완료 보고는 앞선 사건을 요약하더라도 사용자에게 한 주장이므로 사건으로 남긴다.
- **표시는 관계에서 파생한다:** 변경 사건은 "변경 적용 · 검증 통과 N건"·"검증 실패 N건"·"미검증", 질문은 "질문 · 답변됨/답변 없음"으로 표시한다. 저장된 상태를 표시용으로 다시 쓰지 않으므로 모델이 질문 상태를 따로 동기화할 필요가 없다.
- **호환:** 새 그래프와 새 규칙으로 게시한 그래프의 `schema_version`은 2다. 버전 1 그래프는 그대로 읽는다. 이전 계약의 observed 상태 변경 사건은 표시를 바꾸지 않고, 그 사건을 갱신할 때만 새 규칙을 적용한다.
- **평가:** 기대값에 `forbidden_relations`(`from`, `relation`, 선택적 `to`)를 둔다. 예를 들어 다시 실행하지 않은 수정에서 나가는 `verifies`를 금지한다. 대응할 사건을 찾지 못해 부재를 확인할 수 없으면 통과로 세지 않는다.
- **데모:** 합성 데모의 "JSON 저장 구현"은 `applied`이고, 이어지는 실패 테스트와 `verifies`로 연결된다.

## 2026-09-25: 검증 표시 보완과 메타데이터 추적

그래프 스키마 2를 실제 Codex로 두 번 평가한 뒤의 보완이다.

- **과소 연결:** 과장을 막는 규칙 때문에 모델이 테스트 결과를 테스트 파일 변경에만 잇고, 그 테스트가 직접 호출한 코드 변경은 "미검증"으로 남겼다. 공통 지시문에 "테스트나 명령이 변경한 함수·명령·스크립트를 직접 호출하면 그 코드 변경도 verifies로 잇는다"와 "설치된 파일이나 출력에 변경의 결과물이 보이는 것도 근거다"를 추가했다.
- **검증 강도:** 검증이 한 건뿐인 변경은 개수 대신 그 결과 사건의 제목을 표시한다(예: "변경 적용 · 검증: 수정본 install.sh 구문 검사 통과"). 문법 검사만 거친 수정이 실제 실행과 같은 무게로 읽히지 않게 하기 위해서다. 여러 건은 개수로 표시하고 상세 화면의 관계 목록에서 각각을 본다.
- **확인 대상 없는 실행 결과:** 들어오는 관계가 하나도 없는 관측 결과는 "관측 성공 · 확인 대상 미연결"로 표시한다. 새로 추가된 경우 의미 재검토 신호 `unlinked_observed_outcome`을 남긴다. 재검토 모델이 설정된 경우에만 추가 호출이 일어난다.
- **LangSmith 추적:** `--langsmith`만 줘도 실제 LangGraph 노드, 노드 안 단계, 모델 호출이 하나의 trace 트리로 보인다. 모델 호출은 호출한 노드 아래, 같은 프로젝트·trace에 붙는다. 추적은 실행 코드에 직접 붙이며 별도 재현 경로를 만들지 않는다. 원문 없이 보내기 위해 SDK 전송 직전(`create_run`/`update_run`)에 허용 목록 필터를 둔다. `--langsmith-content`의 동작은 바꾸지 않았다. 명시적 client가 없으면 그래프 추적을 켜지 않아, 환경변수만으로 SDK 기본 client가 쓰이지 않는다.
- **수리 입력 버그:** 주장 검증은 인용을 제자리에서 원문 줄 전체로 정규화한다. 검증이 실패하면 이 확장된 응답이 수리 요청의 `previous_output`으로 들어가, 모델 응답이 약 32k자인데도 수리 요청이 121k자가 되어 입력 예산(240k)을 넘었다. 이 경우 수리 호출을 하지 못하고 단위 전체가 실패한다. 이제 검증 전에 떠 둔 모델 원래 응답을 수리 입력, 호출 기록의 `output_chars`, LangSmith 응답에 쓴다. 성공 경로에서는 지금처럼 정규화된 결과를 사용한다.

## 2026-09-26: 모델 명시, 재검토 기본 실행, 기계적 보정, 터미널 상세 보기

- **모델을 항상 이름으로 지정한다:** 격리 환경은 사용자의 CLI 설정 파일을 가져가지 않는다. 그래서 지금까지는 `--model`을 주지 않으면 Codex·Claude CLI 자체 기본값이 조용히 쓰였고, 어떤 모델이 분석했는지도 기록되지 않았다(live-2~6의 요청 모델·실제 모델이 모두 비어 있음). 이제 Runner 기본 모델(Codex `gpt-6-luna`, Claude `sonnet`, 소유자 지정)을 항상 넘긴다. 역할별 추론 수준(추출 `medium`, 통합·재검토 `high`)도 넘기고, 두 값을 호출 기록과 평가 보고서에 남긴다. Claude는 응답의 `modelUsage`에서 실제 모델을 기록한다. Codex는 응답에 모델을 보고하지 않는다.
- **재검토 기본 실행과 신호 축소:** 변경안 재검토는 재검토 모델을 지정해야만 실행됐다. 그래서 앞 단계에서 추가한 "확인 대상 미연결" 신호가 기록만 되고 실행되지 않았다(live-6 `skipped_no_runner`, 쌓인 이슈 7건). 이제 기본으로 실행하고 `--no-review`로 한 번만 끈다. 모든 새 관측 결과에 붙던 `new_observed_outcome` 신호는 없앴다. 인용은 코드가 이미 확인하므로, 재검토는 코드가 알 수 없는 빠진 연결을 본다: `unlinked_observed_outcome`, 새 신호 `unlinked_revision`(들어오는 revises가 없는 revision), 기존 사건 갱신, 기존 관계 무효화. 합성 데모는 첫 통합에서 수정 대상 연결을 빠뜨리고 재검토에서 그 관계를 그리는 경로를 보여 준다.
- **기계적 오류는 코드가 바로잡는다:** 모델을 명시하자 `gpt-6-luna`·`gpt-6-sol` 추출이 계약 검증에서 연달아 실패했다. 실패 응답을 분류하면 상당수가 의미가 아닌 표기 실수였다. 셋 다 결과가 하나로 정해지는 경우에만 고치고 `citation_normalization_audit`에 모드를 남긴다.
  - `relocated_within_provided_lines`: 인용문이 모델에게 보여 준 줄 안에 정확히 한 곳 있는데 줄 번호만 틀린 경우(뒤집힌 범위 포함)에 줄 위치를 옮긴다. 8자 미만 인용, 보여 주지 않은 줄, 두 곳 이상 일치는 그대로 거부한다. 유사도 비교나 공백 무시는 하지 않는다.
  - `event_provenance_from_evidence`: 사건의 `recorded_at`·`session_ids`·`worktree_ids`는 인용한 원문에서 읽는다. 모델 값이 다르면 인용 원문 값으로 바꾼다.
  - `relation_direction_corrected`: 두 모델 모두 `verifies`를 영어 문장 방향(결과 → 변경, "테스트가 변경을 검증한다")으로 썼다. 스키마 2의 방향(변경 → 결과, 이른 사건 → 늦은 사건)과 반대다. 관측 결과 → 변경, 답한 사건 → 질문처럼 끝점 종류로 뜻이 하나로 정해지면 방향만 뒤집는다. 변경 → 변경 같은 잘못된 연결은 계속 거부한다.
- **터미널 상자 그림:** 가지 목록(`├──검증 → [08]`, `↗ 합류`)은 읽기 어렵다는 소유자 의견에 따라, 사건 흐름을 cli-diagram처럼 상자와 이름 붙은 화살표로 그린다(`diagram.flow_diagram`). 왼쪽 열은 관측 결과가 아닌 사건의 기록 순서, 관측 결과는 그것을 가리키는 사건 오른쪽에 둔다. 이웃한 왼쪽 상자는 아래 화살표, 떨어진 것은 여백 레일(최대 4개), 다른 곳에 이미 그린 결과는 `[08] ↑ 위` 참조, 결과에서 나가는 관계는 대상 상자 안의 `← [NN] 관계` 줄로 보여 모든 활성 관계를 한 번씩 표시한다. 칸이 좁으면 가지 목록으로 돌아간다.
- **터미널에서 상세 보기:** `project view`·`analyze`와 `project graph`가 같은 두 칸 화면(`ui.FlowPanels`)을 쓴다. 흐름에는 상태 표식(✓ 확인됨, ! 확인 필요, ✗ 실패)을 붙이고, 상세 칸에는 `render.event_detail`이 만든 설명·검증한 결과·연결·원문 근거를 보여 준다. 한 줄로 저장된 도구 호출 인자는 화면에서만 줄바꿈을 복원한다. 파이프 출력(`project graph`)도 같은 상세를 사건마다 출력한다. 브라우저 상세 보기(B)는 선택 사항으로 남는다. 상태 색은 `--no-color`·`NO_COLOR`로 끄며 표식은 남는다.
- **호출 제한 시간 600초:** 실제 평가에서 통합 호출은 기존 기본 모델로도 236초, `gpt-6-astra` high로는 300초를 넘었다. 모델 호출 하나의 기본 제한 시간을 300초에서 600초로 늘린다. 멈춘 호출은 여전히 끊는다.

## 2026-09-26: Codex 기본 모델 sol, 흐름 그림 보완, 과잉 이스케이프 인용

- **Codex 기본 모델 `gpt-6-sol`:** 소유자 결정이다. `gpt-6-luna`는 두 사례에서 인용 오독과 의미 규칙 위반이 반복됐고, `gpt-6-astra`는 비용이 크다. 측정된 sol 구성은 추론 수준 high다(보정 후 설치 12/18 완료, 수리 버그 7/19 일부 완료). 기본 추론 수준(추출 `medium`, 통합·재검토 `high`)은 바꾸지 않았다. sol의 추출 `medium`은 보정 전 코드에서만 측정됐다.
- **"떨어져 보이는" 사건:** 결과를 모두 오른쪽 열에 두던 배치 때문에, 수정을 부른 실패(`[01] 통합 실패 → 동기 → [02] 진단`)가 오른쪽 위에 따로 놓였다. 연결은 대상 상자 안의 작은 글씨로만 보였다. 이제 오른쪽 열에는 `verifies`·`produces`로 들어오고 다른 곳으로 나가지 않는 결과만 둔다. 나머지 결과는 세로줄에 남아 화살표로 이어진다. 레일이 모자라 그리지 못한 연결은 양쪽 상자에 모두 적는다(`→ [06] 동기`, `← [05] 동기`). 관계가 하나도 없는 사건에는 "연결된 사건 없음"을 표시한다. 이 표시는 추측 연결을 만들지 않는다. 실제 평가 그래프 9개 중 4개에 이런 사건이 1~2개씩 있었다. 모두 모델이 연결을 적지 않은 경우였다(문서 갱신, 여러 변경 뒤의 전체 테스트, 강제 설치 출력 등). astra는 두 사례에서 0개였다.
- **흐름 나누기:** 세션도 관계도 공유하지 않는 사건 묶음은 따로 그린다(`══ 흐름 1/2 · 사건 7개 · 세션 1개 · 시각 ══`). 서로 다른 세션에서 독립 기능을 만든 경우가 여기에 해당한다. 세션 사이에 근거 있는 관계가 하나라도 생기면 한 흐름이 된다. 시간이 가깝다는 이유로 흐름을 합치지는 않는다.
- **자르지 않기:** 터미널은 스크롤하므로 상자의 제목·상태·연결 줄을 "…"로 자르지 않고 줄을 바꾼다. 상태는 `·` 사이에서 먼저 바꾼다.
- **과잉 이스케이프 인용:** sol 수리 버그 두 번째 단위의 통합이 첫 시도와 수리 모두 같은 인용 하나로 실패했다. 원문 `"content_included": false`를 `content_included\": false`로 적어 0건 일치였다. 기존 규칙은 원문 쪽이 이스케이프된 경우만 풀었다. 이제 인용문의 이스케이프를 한 겹 풀어 제공된 줄에서 유일하게 일치할 때도 받아들인다. 모드는 `quote_unescaped_substring_expanded_to_lines`이고, 저장은 원문 표기다. 다른 단어로 바뀐 인용은 계속 거부한다. 저장된 응답에서 이 인용이 이제 통과하는 것은 확인했다. 인용 검사를 통과한 뒤의 의미 검사까지 통과할지는 실제 재실행으로만 알 수 있다.

## 2026-09-26: 사용자 발화 노드, 대화 차례 연결, 짧은 ID, 도구 단계 목록

- **사용자 발화는 모두 노드:** 소유자 제안이다. 대화로 진행한 작업이라면 모든 사건은 어떤 사용자 발화를 처리하던 중에 생긴다.
  - **무엇을 발화로 치나:** `model.is_user_prompt`는 사람이 입력한 user 역할 기록만 발화로 본다. 하네스가 user 역할로 넣은 글(task-notification, 명령 caveat, system-reminder 등), 하위 에이전트, 요약, 나뉜 조각의 뒷부분은 제외한다.
  - **모델이 빠뜨리면:** 추출이 빠뜨린 발화는 통합 호출이 있을 때 question 후보로 넣어 모델이 이을 수 있게 한다(`add_user_requests`). 그래도 없으면 게시 전 그래프 단계가 원문 그대로를 제목으로 한 question 노드를 만든다.
  - **표시:** 질문·지시·요청을 모두 담으므로 종류와 상태를 "요청"으로 표시한다.
- **대화 차례 연결:** 새 사건 중 들어오는 관계가 하나도 없는 것은, 같은 세션에서 바로 앞 사용자 발화 노드에 잇는다(`link_request_turns`).
  - **저장 형태:** `follows`, basis `structural`, `origin: "dialog_turn"`이다. 원인 주장이 아니라 "이 발화 다음, 다음 발화 전에 한 일"이라는 대화 구조다. 몇 분 안이라는 시간 근접이 아니라 차례로 정한다.
  - **그림:** 한 발화의 차례 연결은 한 레일에 괄호처럼 모아 그리고, 모델이 만든 관계가 나머지 레일을 쓴다. 상세 보기에는 "후속 (대화 순서)"로 흐리게 표시한다.
  - **기존 결과에 적용한 모의(모델 재실행 없음):** 연결 없는 사건이 CLI 기본값 설치 2→0개, sol 설치 1→0개로 줄었다.
- **짧은 ID:** Runner에 보내는 입력에서만 `src_…`·`ev_…`·`edge_…` 등을 `S12`·`E3`·`L2`로 바꾸고, 응답은 검증 전에 되돌린다(`IdAliases`).
  - **범위:** 문자열 값 전체가 ID일 때만 바꾸므로 원문 안의 ID는 그대로 간다. 저장·검증·호출 기록은 원래 ID를 쓰고, `input_chars`는 실제로 보낸 입력 기준이다.
  - **이유:** luna가 24자리 ID를 잘라 적은 실패가 있었다.
- **도구 단계 목록:** 추출 입력에 `tool_steps`와 `user_requests`를 더한다. 입력 크기는 설치 사례 첫 추출이 65,084자에서 65,785자로, 짧은 ID로 준 만큼 목록이 채웠다.
  - **`tool_steps` 힌트:** 도구 호출마다 도구 이름과 patch 표시만 보고 edit·read·run 힌트를 붙인다. 읽기 명령으로 시작해도 `>`·`sed -i` 등 쓰기 표시가 있으면 run이다.
  - **필수 인용:** 파일을 바꾼 것이 확실한 호출(edit, 실패 결과 제외)은 모두 어떤 추출 사건의 근거여야 한다. 빠지면 검증 오류로 수리 기회를 쓴다. luna·sol 실행에서 문서·설정 변경 사건이 빠진 기대값 실패가 많았다.
  - **파서 수정:** Claude의 Write 호출 기록에는 파일 경로가 빠지고 내용만 남았다. 도구 인자를 모두 JSON으로 기록하도록 고쳤다.
- **"연결 없는 사건의 이유 필수"는 하지 않는다:** 앞 대화에서 제안했지만, 차례 연결로 떨어진 사건이 사라진다. 필드를 더하면 계약과 수리 부담만 는다.
- **실패 이유 표시:** 2026-09-26 위 변경을 실제 Codex로 평가하려 했으나 6회 모두 첫 호출에서 끝났다. Codex workspace 크레딧 소진("Your workspace is out of credits. Add credits to continue.") 때문이었다. 이전 Runner 오류는 "CLI 인증·계정 한도·옵션 호환성을 확인하세요"뿐이었다. 이제 Codex JSON 이벤트나 Claude 결과에 있는 공급자의 실패 이유를 한 줄(최대 200자)로 오류에 붙인다.

## 2026-09-26: 터미널 요청 목록, 도착 번호, 연결 따라가기, 연결 강조

소유자는 여백 선을 거슬러 올라가 출발 상자를 찾기 어렵고, 긴 흐름에서 원하는 곳으로 가기 어렵다고 했다. 합의한 계획은 `docs/plans/TERMINAL_UI_NEXT.md`에 있다.

- **도착 번호:** 여백 선은 도착하는 상자 앞에 출발 번호와 관계를 적는다(`[02] 동기 ▶`, 이전 `─동기─▶`). 요청의 차례 괄호도 같은 형식이다(`[01] 후속 ▶`). 여백은 가장 긴 표시만큼 넓어진다.
  - **같은 상자의 선 끝:** 한 상자에서 나가는 선과 들어오는 선이 같은 줄을 쓰던 결함을 고쳤다. 선 끝마다 상자의 다음 안쪽 줄을 쓰고, 줄이 모자라면 상자를 늘린다.
- **요청별 흐름:** 사용자 발화가 있는 그래프는 요청 하나의 차례만 그린다(`diagram.request_turns`, `flow_diagram(only=…)`).
  - **차례의 범위:** 그 발화부터 같은 세션의 다음 발화 전까지다. 세션이 없는 사건(Git 커밋 등)은 그 사건으로 이어지는 사건의 차례를 따른다. 어느 차례에도 없는 사건은 `요청 기록 없는 사건`으로 묶는다. 수리 버그 사례처럼 작업을 시작한 발화가 기록 범위 밖이면 이렇게 된다.
  - **번호와 연결:** 번호는 전체 목록 번호를 유지한다. 차례 밖 사건과의 연결은 상자 안에 `← [02] 동기`처럼 적는다.
  - **이동:** `[` `]`로 요청을 옮기고, `A`로 전체 흐름으로 바꾼다. 방향키는 차례 끝에서 다음 요청으로 넘어간다.

## 2026-09-26: 터미널 키 확장과 마우스

소유자가 더 직관적이고 다양한 키를 원했다. 확인 필요한 곳 이동은 `!`, 마우스도 넣기로 했다.

- **새 키:** 모든 키는 `?` 도움말에 있고, 아래 안내 줄은 자주 쓰는 키만 보인다(`ui.KEYS`, `ui.HELP`).
  - `←→`/`h l`: 상자 그림에서 옆 칸의 이어진 상자로 이동한다(변경 ↔ 오른쪽 결과). 전에는 가지 목록에서만 가로 스크롤을 했고 상자 그림에서는 반응이 없었다.
  - `!`: 다음 확인 필요한 사건(`!`·`✗`)으로 순환한다. 합의 때는 `n`/`N`이었으나 `/` 검색의 다음·이전 결과와 겹쳐, 화면 표식과 같은 글자로 정했다.
  - `/` → `n N`: 제목·요약·원문 근거를 검색한다. 일치한 상자 제목에 밑줄을 긋고, 흐름 칸 제목에 개수를 적는다. 근거까지 찾으므로 파일 경로도 걸린다.
  - `J K`: 칸을 옮기지 않고 상세를 스크롤한다.
  - `e`: 원문 근거를 전부 펼치거나 근거마다 8줄로 접는다.
  - `z`: 지금 칸을 화면 전체로 키운다.
  - `Space`: 한 화면씩 이동한다.
  - `Esc`: 검색·크게 보기를 닫고, 상세 칸에서 흐름 칸으로 돌아온다. `set_escdelay(25)`로 기다림을 줄였다.
  - 검색어를 입력하는 동안과 도움말이 떠 있는 동안에는 패널이 모든 키를 받는다(`FlowPanels.modal`). 그래서 검색어의 `q`가 종료로 처리되지 않는다.
- **한글 입력 상태:** 두벌식 자모를 같은 자리의 영문 키로 읽는다(`ui.latin`). `ㅂ`→q, `ㅓ`→j, `ㄲ`→R이다. 검색어 입력 중에는 바꾸지 않는다. 입력기가 조합 중인 글자를 터미널이 바로 보내지 않으면 효과가 없을 수 있어, 실제 터미널 확인이 남았다.
- **마우스:** 클릭과 휠만 받는다. ncurses가 `?1000h`만 켜므로 움직임 보고는 없다.
  - **클릭:** 상자·요청 목록·상세의 번호 붙은 연결을 고른다. 상자 안 `← [02] 동기` 메모, `[08] ↑ 위` 참조, 여백 선, 도착 표시를 누르면 그 연결의 상대 상자로 간다(`Cell.edges`). 연결 이동은 Backspace로 되돌릴 수 있다.
  - **휠:** 흐름에서는 사건, 요청 목록에서는 요청을 옮기고, 상세는 스크롤한다.

  - **끄기:** `--no-mouse`(`view`·`analyze`·`graph`·`demo`)는 마우스를 끄고 터미널의 글자 선택을 쓰게 한다.

## 2026-09-26: 분석 중 화면이 `database is locked`로 끝나던 문제

- **증상:** 기록이 많은 프로젝트(기록 약 5만 8천 개, 상태 DB 82MB)에서 `R`을 누르면 화면이 `sqlite3.OperationalError: database is locked`로 끝났다. 앱이 끝나면서 분석도 함께 끊겼고, 그 실행은 `scanning` 상태로 남았다. 이런 실행은 다음 분석이 잠금을 잡을 때 `cancelled`로 정리된다.
- **원인:** `Store.ingest`가 매번 모든 기록 행을 한 트랜잭션에서 다시 썼다. rollback journal 모드에서는 큰 쓰기가 캐시를 넘치면 배타 잠금을 잡고, 그동안 읽기도 막힌다. 화면은 0.1초마다 `last_check`를 읽는데 10초 대기 제한을 넘겨 예외가 났다.
- **고친 점:**
  - **WAL:** 상태 DB를 WAL 모드로 연다. 쓰기 중에도 화면과 브라우저는 마지막으로 게시된 상태를 읽는다. 상태는 로컬 디스크에만 둔다는 SPEC 조건 안에서 쓴다. 기존 DB는 처음 열 때 전환된다.
  - **바뀐 행만 쓰기:** `ingest`는 내용 해시·메타데이터·사용 가능 여부가 달라진 행만 쓰고, 세션 행도 달라진 것만 쓴다. 변화 없는 재수집은 쓰기가 0건이다. 결과(`changed`·`missing`)는 전과 같다. 기록마다 다섯 번 계산하던 내용 해시는 한 번만 계산한다.
  - **화면 방어:** `TerminalApp`의 DB 읽기(`last_check`, 토큰 합계, 저장된 그래프, 근거)가 잠금에 걸리면 직전 값을 그대로 보여 준다. 앱과 분석은 계속된다.
- **검증:** 합성 기록 5만 8천 개 기준으로, 동시 읽기의 최대 대기가 5~6초에서 0.06초로 줄었다. 시험 3개를 추가했다. 배타 쓰기 중 읽기, 변화 없는 재수집의 쓰기 0건, 잠긴 읽기에서 화면이 유지되는지다. 시험 284개가 통과했다.

## 2026-09-26: 대형 프로젝트 분석량 줄이기 — 재분석 방지, fork 중복 제거, 긴 기록 앞뒤 보기, 실행 전 확인

`측정 프로젝트`(Codex 세션 282개, 기록 약 5만 7천 개, 원문 약 2억 자)에서 `R` 한 번이 작업 단위 하나(대화 약 10초)만 처리했다. 흐름도는 바뀌지 않았다. 원인을 AI 호출 없이 로컬에서 측정하고 다음 네 가지를 바꿨다.

- **1. 통합된 단위는 자기 원문이 바뀔 때만 다시 분석:**
  - 9월 23일 통합까지 끝난 단위가 원문 해시가 그대로인 채 오늘 다시 추출·통합됐다(호출 2회 낭비). 당시 참고 목록이 덮어써져 정확한 경로는 증명하지 못했다.

## 2026-09-27: 에이전트가 CLI로 쓰는 ContextTrail — 단위 수로 제한, 사건 첨부, 세션 먼저 분석

소유자 요청: Codex·Claude Code에서 slash command로 ContextTrail을 쓰고, 노드를 근거로 첨부하고, 실행량을 쉽게 제한하며 대화로도 제한할 수 있어야 한다. MCP 대신 CLI를 쓴다(소유자 판단, 동의). 이유는 두 가지다. 에이전트는 셸 명령을 잘 다루고, 사람이 쓰는 명령과 에이전트가 쓰는 명령이 같아진다. MCP 서버는 따로 띄워 두어야 하고 도구 정의가 대화마다 문맥을 차지한다.

- **제한 기준을 작업 단위 수로:** 사용자가 정하는 값은 이번 실행에서 처리할 작업 단위 수다(`--units N`, 터미널 `R` 확인 창에서 숫자 입력, 에이전트 대화에서 답). 정하면 AI 호출 상한은 단위당 6회(`CALLS_PER_UNIT`)이고, `--max-calls`를 주면 그 값이 우선한다. 저장하지 않는다. 정하지 않으면 이전처럼 호출 상한 30만 적용된다.
- **계획 미리 보기:** `scan`이 AI 호출 없이 `plan`, `plan_text`, `plan_choices`를 출력한다. 5·15·30개를 처리할 때의 입력 토큰과 시간이다. 이를 위해 `scan`도 분석과 같은 잠금 아래에서 입력 기록을 상태 DB에 반영한다.
- **추정 보정:** 기본 추정에 3배를 곱한다. 단위 하나는 추출, 통합, 재검토, 복구나 읽기 요청을 합쳐 여러 번 호출한다. 근거는 두 가지다. `측정 프로젝트`에서 실제 분석한 단위 1개가 이전 추정의 2.95배를 썼다. 평가 단위는 18~22만 토큰을 썼는데 이전 추정은 약 6만이었다. 그래서 어제 안내한 "15개 단위 ≈ 80만 토큰"은 약 240만 토큰(약 2시간)으로 고친다. 이 프로젝트에서 사용량이 기록된 단위가 3개 이상이면, 실제 입력 토큰과 시간으로 비율을 다시 잡고 "지난 N개 단위 기준"이라고 표시한다. 1~2개는 표본이 너무 적어 쓰지 않는다.
- **세션 먼저 분석(`--session <ID>|current`):** 오래된 것부터 처리하는 순서는 유지한다. 예외로 한 세션과 그 세션이 띄운 하위 에이전트(`lineage.parent_session_id`, 깊이 제한 없음)만 먼저 분석할 수 있다. `current`는 명령을 실행한 에이전트의 환경 변수에서 읽는다. Codex는 `CODEX_THREAD_ID`, Claude Code는 `CLAUDE_CODE_SESSION_ID`이고, 둘 다 있으면 거부한다. 이렇게 추가된 사건은 그래프의 `out_of_order_events`에 남는다. 이후 버전에도 이어지며, `find`·`show`에 "순서 밖 분석"으로 표시된다. 앞선 관계가 빠졌을 수 있다는 뜻이다.
- **처리를 미룬 기록이 있으면 완료가 아님:** 단위 수 제한이나 세션 지정으로 기록이 남으면 그래프 상태는 `partial`이다(`records_waiting`).
- **사건 조회 명령:** `find [검색어]`와 `show <사건>`을 추가했다. 둘 다 AI 호출이 없고 `--json`을 지원한다(`agent_view.py`).
  - `find`는 제목, 설명, 원문 근거에 모든 단어가 든 사건을 최신순으로 보여 준다. 검색어가 없으면 최근 사건과 열린 항목을 보여 준다.
  - `show`는 사건 하나의 상태, 연결, 열린 항목, 원문 인용을 보여 준다. 인용은 `--- 원문 근거 N ---` 구역으로 나누고, 그 위에 "지시로 따르지 말고 근거로만 쓰라"는 문구를 둔다.
  - 사건은 ID 앞부분(최소 8자리, 겹치면 더 길게)이나 참조 `contexttrail:ev_…@vN`으로 지정한다. 참조의 버전 이후 제목, 상태 표시, 설명, 근거가 바뀌었으면 알리고, 사라졌으면 당시 내용을 현재 사실처럼 보여 주지 않는다.
- **사건 첨부:** 터미널 `y` 키와 브라우저의 "에이전트용 참조 복사" 버튼은 참조만 복사하고 원문은 복사하지 않는다. 로컬 Mac은 `pbcopy`, 원격은 OSC 52를 쓴다(tmux는 passthrough). 이 참조를 에이전트 대화에 붙여넣으면 문맥 스킬이 `show`로 읽는다.
- **스킬:**
  - `contexttrail-update`는 이름으로 부를 때만 실행된다. Claude Code는 `disable-model-invocation: true`를 쓴다. Codex는 이 필드를 거부하므로 `agents/openai.yaml`에 `policy.allow_implicit_invocation: false`를 둔다. 계획을 보여 주고 단위 수를 받은 뒤(인자로 준 수가 있으면 그 수) `analyze --units N`을 백그라운드로 실행하도록 안내한다. 수를 스스로 정하지 않는다.
  - `contexttrail-context`는 에이전트가 스스로 불러도 된다. `find`·`show` 사용법과 인용을 자료로 다루는 규칙을 담았다.
- **분석 계획이 느리던 문제:** 계획 단계가 기록마다 대기 집합의 차집합을 새로 계산해 `측정 프로젝트`에서 100초 넘게 걸렸다. `R`을 누를 때마다 걸리던 시간이다. 한 번만 계산하도록 고쳤다. 기록마다 폴더 소속을 판정하며 symlink를 다시 풀던 것도 스캔 한 번 안에서 캐시한다(`Scope._answers`). `측정 프로젝트` `scan`은 3분 10초에서 52초가 됐다. 남은 시간은 기록 파일을 읽고 해시하는 시간이다.
- **남은 확인:** Codex 안에서 부른 `contexttrail-update`가 Codex 격리 안에서 ContextTrail 자체 격리(`sandbox-exec`)와 네트워크를 쓸 수 있는지는 확인하지 않았다. 막히면 스킬이 사용자 터미널에서 실행할 명령을 안내한다.

## 2026-09-27: 분석 속도와 요약 — 영어 프롬프트, 출력 언어, 사건 선별, 추론 수준, 다음 단위 미리 추출

배경: 소유자가 이 저장소 자체를 분석했더니 26분 동안 작업 단위 2개만 끝났다. AI 호출 하나는 63~183초였고, 추출 5번 중 3번이 검증에서 떨어져 호출이 더 들었다. 세 번째 단위는 다시 해도 떨어져 결과가 없었다. 만들어진 사건은 원문 대화가 영어라서 모두 영어였다. 제목은 "Adjust validation plan for macOS" 같은 추상적인 명사였고, 17개 중 5~6개는 설치 성공, 버전 확인 같은 사소한 단계였다. 소유자 결정: 프롬프트는 영어로, 언어는 AI가 쓰게, 추론 수준은 낮추고, 속도 개선과 요약 규칙은 모두 진행한다.

- **프롬프트 영어화:** `common`·`extract`·`integrate`·`repair`와 `wire_contract`의 규칙을 그대로 영어로 옮겼다. 한글이 약 4천 자였으니 호출당 약 2천 토큰, 전체의 2~7%가 줄어든다. 모델이 지시를 더 일관되게 따르고, 공개 후 기여자가 읽기 쉬운 효과도 있다. 모델에게 돌려주는 검증 오류 문구는 아직 한국어다. 복구 단계가 그 문구를 패턴으로 찾기 때문이다.

  - 정하는 순서는 `--language`, 저장된 값, `detect_language` 순이다.
  - `detect_language`는 사용자 메시지마다 한 표씩 센다. 한글·가나·한자 등 글자 종류가 2자 이상이면 그 언어다. 코드와 경로가 대부분인 한국어 요청도 한국어로 센다.
  - 라틴 문자만 있으면 시스템 로캘로 언어를 정하고, 알 수 없으면 English로 한다.
  - `--language auto`는 다시 정한다.
- **사건 선별과 제목·요약 규칙:** 나중에 읽는 사람에게 필요한 것만 사건으로 남긴다. 사용자 메시지, 결정, 변경, 확인과 그 결과, 실패, 철회, 열린 질문이다. 둘러보기(파일 읽기·목록, 버전 확인, 폴더 확인, 시험 삼아 설치)는 실패했거나 예상 밖이었거나 계획을 바꿨을 때만 사건으로 둔다. 그렇지 않으면 그 단계가 도운 사건의 요약에 넣는다. 제목은 무엇이 어떻게 됐는지를 구체적인 이름과 숫자로 40자 안팎에 쓰고, 요약은 제목에 없는 이유와 영향을 1~2문장으로 쓴다. 예시를 프롬프트에 넣었다.

- **추론 수준:** 통합과 재검토의 기본을 `high`에서 `medium`으로 낮췄다. 추출은 원래 `medium`이다. 품질 영향은 다음 실제 평가로 확인한다.
- **다음 단위 미리 추출:** 추출 worker가 1이면, 한 단위를 통합하는 동안 다음 단위의 추출을 백그라운드 스레드 하나로 시작한다(`_prefetch_next`). 미리 추출하는 단위는 기존 병렬 추출처럼 앞 단위가 게시되기 전의 그래프를 기준으로 한다.
  - 다음 경우에는 건너뛴다: 한 Runner 인스턴스를 공유하는 factory(스레드마다 독립 인스턴스가 필요), 남은 호출 예산이 8회 미만, 취소됨, 마지막 단위.
  - 실행이 끝나거나 실패하면 미리 추출을 취소하고 끝날 때까지 기다린다(`stop_prefetch`). 분석 잠금이 풀린 뒤에 도는 호출이 없게 하기 위해서다.
  - 토큰은 같고 걸리는 시간만 준다.
- **평가 보고서의 읽기 쉬움 숫자(`style`):** 사건 수, 제목 평균 길이, 40자를 넘는 제목 수, 읽기 호출만 인용한 사건 수, 출력 언어를 기록한다. 평가를 실패시키지는 않고 실행끼리 비교하는 데 쓴다.
- **실패 호출 줄이기:** 아래 "실패 호출 줄이기" 항목에서 따로 정했다.

## 2026-09-27: 실패 호출 줄이기 — 답변받은 사용자 목표, 짧은 인용, 통과한 후보 살리기

배경: 이 저장소 분석에서 추출 5번 중 3번이 검증에서 떨어졌다. 한 번 떨어질 때마다 복구 호출이 약 2분 더 들었고, 복구에서도 떨어진 단위는 후보 전체를 버렸다. 원인은 셋이었다. 소유자가 쉬운 설명을 듣고 세 가지를 모두 진행하기로 했다.

- **답변받은 사용자 목표는 질문으로 읽는다:** 모델이 사용자 메시지를 `goal`로 분류하고 거기서 `answers` 관계를 이었다. `answers`는 `question`에서만 나올 수 있어 거부됐다. 사용자 메시지는 규칙상 질문(`question`/asked) 또는 결정(`decision`/adopted)이고, 답변을 받을 수 있는 것은 질문뿐이다. 그래서 다음 조건을 모두 만족하면 코드가 `question`/`asked`로 고치고 `normalizations`에 `user_goal_as_answered_question`으로 남긴다(`schema.retype_answered_user_goals`).
  - `actor=user`인 `goal` 또는 `proposal` 사건이다.
  - 사람이 직접 친 메시지(`is_user_prompt`)만 인용한다.
  - 그 사건에서 `answers` 관계가 나간다.

  답변 관계가 없는 사용자 목표는 질문인지 결정인지 코드가 정할 수 없어 그대로 둔다. 추출과 통합 모두에 적용한다.
- **짧은 인용은 한 번만 나올 때 받는다:** 한 줄짜리 긴 JSON 도구 출력에서 8자 미만 조각(`denied` 같은 값)을 인용하면 이전에는 이유 없이 "인용문이 고정 원문과 다릅니다"로 거부됐다. 모델이 이유를 몰라 복구에서도 같은 인용을 냈다.
  - 이제 조각이 인용한 줄 범위에 원문 그대로 정확히 한 번 나오면 받는다. 다른 부분 인용처럼 줄 전체를 저장하고 조각 위치를 `focus`로 남긴다(`short_unique_substring_expanded_to_lines`).
  - 두 번 이상 나오거나, 이스케이프를 풀어야 맞거나, 공백뿐이면 여전히 거부한다. 그때 오류 문구에 "8자 미만 조각은 인용한 줄 범위에 정확히 한 번 나올 때만 쓸 수 있습니다. 그 조각을 포함한 더 긴 부분을 원문 그대로 인용하세요"를 붙인다. 문구 앞부분은 그대로라 복구 단계의 원문 줄 첨부(`exact_source_lines`)도 그대로 동작한다.
- **복구 뒤에도 틀리면 통과한 후보는 살린다:** 복구 호출까지 떨어지면 이전에는 단위 전체가 실패했다. 이제 코드가 마지막 응답의 후보를 하나씩 검사해 통과한 것만 남긴다(`EvidenceValidator.salvage_extraction`, 모델 호출 없음).
  - 버린 사건 후보는 제목으로, 관계 후보는 개수로 그래프 한계(limitations)에 "근거 검증을 통과하지 못해 제외한…"이라고 남긴다. 통합 모델이 한계를 무엇으로 쓰든 이 문구는 그래프에 들어간다.
  - 남은 결과도 전체 검사를 다시 통과해야 저장한다. 검증을 통과한 것만 저장한다는 원칙은 그대로다.
  - 파일을 바꾼 도구 호출은 원래 어떤 사건이 인용해야 한다. 버린 사건만 그 호출을 인용했다면 그 호출은 이번 단위에서 면제하고 `waived_citations`로 저장한다. 어떤 사건도 언급하지 않은 변경은 여전히 단위를 실패시킨다. 모델이 변경을 빠뜨린 것과, 설명했지만 근거가 틀린 것을 구분하기 위해서다.
  - 살릴 후보가 하나도 없거나, 응답이 미완료이거나, 미처리 record를 남겼으면 이전처럼 단위가 실패한다. 미처리 record는 다음 실행에서 다시 보내야 하기 때문이다.
  - `--escalation-model`을 준 실행은 먼저 상위 모델에 다시 추출을 맡기고, 그것도 떨어지면 같은 방식으로 살린다.
  - 버린 후보는 그 단위가 완료로 저장되므로 다시 보내지 않는다. 한계 문구로 무엇이 빠졌는지 알 수 있다.
- **그대로 둔 것:** `verifies`를 관측 결과가 아닌 사건에 이은 경우는 의미 판단이라 복구 호출이 고치게 둔다.
- **효과 확인:** 아직 실제 평가 전이다. 다음 평가에서 검증 실패 호출 수와 버린 후보 수(한계 문구)를 본다.

## 2026-10-06: 세 도구가 같이 쓰는 프로젝트 기억

소유자의 방향: ContextTrail은 Claude Code·Codex·opencode 중 무엇으로 프로젝트를 열든 같은 그래프를 읽고, 세 도구의 기록이 모두 그 그래프에 들어가는 "프로젝트를 따라다니는 기억"이다. 계획은 `docs/plans/SHARED_CONTEXT_STORE.md`. 이때 정한 원칙:

- **쓰는 손은 하나.** 그래프에 쓰는 경로는 분석(모델이 트랜스크립트를 읽고 인용으로 뒷받침한 결과)뿐이다. 에이전트가 그래프에 직접 메모를 쓰는 두 번째 경로는 만들지 않는다. 에이전트가 말한 것은 트랜스크립트에 남아 다음 분석에 들어간다. "모든 항목에 증거가 있다"를 지키기 위해서다.
- **분석은 명시적 요청에만.** 훅으로 돌리는 자동 갱신(계획 B2)은 사용자가 프로젝트마다 켜는 선택 사항이고, 켜지 않은 프로젝트에서 훅은 아무것도 하지 않으며 호스트 도구를 막지 않는다.
- **MCP 서버를 만들지 않는다.** 세 도구 모두 셸이 있으므로 CLI(`find`/`show`/`status`)로 충분하고, 설치물이 하나다.
- **오래된 것은 오래됐다고 말한다.** 읽기 경로마다 마지막 scan 기준 미분석 기록 수와 scan 이후 세션·기록 수를 센 값으로 적는다(`freshness.py`). 추정하지 않는다.
- **opencode는 입력이지 Runner가 아니다.** Runner는 Codex·Claude이고, 프로젝트에 저장된 runner가 없으면 스킬이 사용자에게 묻는다. opencode에는 스킬의 "명시적 호출만" 장치가 없어, 설치 뒤 `permission.skill` 설정으로 승인을 요구하라는 안내를 보여 주되 사용자 설정 파일은 고치지 않는다.

## 2026-10-07: 에이전트가 적는 note와 분석 보강 감사

소유자의 제안: "별도로 분석을 돌리지 말고, 작업한 AI가 ContextTrail을 써서 그래프를 만들게 하자." 계획과 진행 기록은 `docs/plans/LIVE_JOURNAL.md`.

- **감사는 더하기만 한다** (2026-10-08, `LIVE_JOURNAL.md` §11): 기존 사건·관계·미해결 항목을 바꾸거나 무효화하지 않고(`audit_guard`), 추가한 것에는 `origin: "audit"`를 붙인다. 시맨틱 리뷰는 끄고, 자동 갱신 훅은 감사를 하지 않는다. 실제 모델로 중복률과 비용을 재는 평가는 아직 하지 않았다.

## 2026-10-09: 전체 이력은 오래된 것부터, 최근 세션 먼저는 선택 기능 (`--recent`, `--since`)

소유자 결정. 계획·표는 `docs/plans/RECENT_SESSIONS_FIRST.md`.

- **기본 순서는 오래된 것부터 그대로 둔다.** 관계는 앞 사건에서 뒤 사건으로 가고(`prompts/common.md`), 단위는 그 시점의 그래프에 한 번만 통합된다. 최신부터 하면 수정이 고친 대상, 검증이 확인한 변경이 아직 없어 관계가 끊긴다. (2026-09-27의 "세션 먼저 분석"과 같은 예외 방식이다.)

- **거부하는 조합:** `--session`(뜻이 겹침), `--audit`(note 세션을 읽는 기능과 반대 집합; 감사 대상은 `--session`으로), `--trigger hook`(훅은 오래된 순서 유지). 고른 세션이 없으면 오류.

- **B(저장하는 분석 기간 제한)는 하지 않는다.** A로 필요가 채워지고, 영구 제외는 `complete`/`pending`의 뜻을 바꿔 `freshness`·`status`·`finish_run`·보류를 함께 고쳐야 한다. 필요가 확인되면 "제한 안에서 완료"를 따로 세는 설계로 다시 한다.

- **"모델은 항상 이름으로 지정한다"는 지킨다:** CLI에 넘기는 것은 버전이 붙은 이름이고, 호출 기록의 요청 모델에도 그 이름이 남는다. 찾지 못하면 다른 모델로 넘어가지 않고 멈춘다.
- **내장 목록을 쓰는 이유:** 서버에서 새로 받는 목록은 격리 안의 임시 HOME에 캐시가 없어 네트워크와 인증이 더 필요하다. 내장 목록은 설치된 Codex 버전과 함께 바뀌므로, 새 Sol은 Codex를 업데이트하면 쓰인다.
- **이미 끝난 단위는 다시 보내지 않는다.** 라우팅 서명에는 설정값(`--model`을 주지 않으면 비어 있음)만 들어가므로 기본값이나 해석 결과가 바뀌어도 서명은 같다.
