## 1. 설계 원칙과 불변 조건

1. **독립 엔진 하나, 입력 어댑터 둘, Runner 둘.** Codex용·Claude Code용 분석 로직을 따로 만들지 않는다.
2. **원본과 해석 분리.** 원문·diff는 근거이고 그래프는 해석 결과다. Mermaid는 저장 데이터의 기준이 아니다.
3. **갱신은 명시적으로만.** `analyze` 실행 또는 새로고침 요청이 없으면 분석하지 않는다.
4. **동일 작업 재사용.** 저장된 완료 결과를 재호출하지 않는다. 빈 사건 추출 결과도 처리 완료로 저장한다.
5. **연장 세션은 증분으로.** 새 구간과 필요한 기존 맥락만 분석하며, 기존 노드 ID는 유지한다.
6. **읽기 전용 분석.** 원본 프로젝트·로그·Git refs/index를 수정하지 않고 과거 명령을 실행하지 않는다. 자체 상태·임시 자료·명시적 export만 기록한다.
7. **잘못된 완결보다 명시적 한계.** 오류·누락·미확인 근거를 부분 분석으로 남긴다.
8. **Trace는 개발 도구.** 사용자는 프로젝트의 근거를 보며, 내부 추론 과정이나 Trace 대시보드를 요구받지 않는다.

시간에 따른 흐름을 표시하더라도 전체 의미 그래프를 무조건 DAG로 제한하지 않는다. 되돌아본 결정과 수정·대체 관계가 있을 수 있다. 그래프의 모든 노드를 하나의 연결 성분으로 만들 의무도 없다.

## 2. 구성요소와 기술 기본안

### 2.1 최소 모듈

| 구성요소 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| `sources/` | Codex·Claude 로그 발견, 파싱, 원문 ID·역할·tool 연결 보존 | 의미 요약·결정 추론 |
| `git_context` | 범위·worktree·고정된 Git 근거·현재 변경 snapshot | 실행 기록 없는 과거 상태 추정 |
| `store` | SQLite, 처리 ledger, 근거 보존, 그래프 버전·원자적 저장 | 공개 서버·외부 동기화 |
| `analysis` | 분석 단위 계획, 프롬프트, 근거 읽기, GraphDelta 검증 | 범용 Coding Agent 새 구현 |
| `runners/` | 설치된 두 CLI의 호출·출력 정규화·취소·오류 처리 | 인증 토큰 복사·다중 모델 합의 |
| `render` | 동일 그래프의 개요·상세 표현, Mermaid·문자 그래프·export | 추가 AI 요약 |
| `ui` | CLI/TUI, 최소 로컬 상세 뷰어 | 편집 Canvas·LLMOps 대시보드 |

### 2.2 기술 선택의 상태

**구현 기본안:** Python으로 엔진과 CLI를 작성하고, SQLite를 사용한다. TUI는 Textual을 후보로 둔다. 상세 보기는 작은 HTML 페이지와 Mermaid SVG로 구현한다. Textual과 Mermaid의 공식 문서는 각각 터미널 앱 및 웹 렌더링을 설명한다. [T06, T07]

터미널의 Mermaid→ASCII/Unicode 렌더러는 별도 호환성 시험 후 선정한다. Node 기반 렌더러를 사용하면 런타임·버전·배포 방식을 함께 고정한다. 전체 프로젝트를 무조건 Python 단일 런타임으로 제한하거나, 사용자에게 무조건 여러 프레임워크를 설치시키기로 확정한 것은 아니다.

LangGraph·LangSmith는 필수 제품 의존성이 아니다. 필요하면 작은 분석 workflow 또는 개발용 trace에 사용하되, SQLite의 분석 상태와 그래프가 기준이다. 그래프 DB·벡터 DB·분산 큐·범용 플러그인 체계를 먼저 만들지 않는다.

## 3. CLI/TUI 계약

### 3.1 명령 인터페이스 — 구현안

```bash
# 실행 시 변경분을 확인하고 기본 TUI를 연다.
project analyze . --runner codex
project analyze . --runner claude

# 저장된 Runner 설정을 사용한다.
project analyze .

# 자동 분석 없이 저장된 결과를 연다.
project view .

# 터미널/코딩 에이전트에서 그래프를 표준 출력으로 읽는다. eval 결과 폴더도 받는다.
project graph .
project graph /path/to/eval-output

# 저장된 결과를 내보낸다. AI 호출은 없다.
project export . --format md --output ./project-flow.md
project export . --format mmd --output ./project-flow.mmd
project export . --format json --output ./project-flow.json
```

두 Runner가 있으면 첫 선택을 로컬 설정에 보존한다. 하나만 사용 가능하면 그것을 제안하되 다른 실행기로 조용히 전환하지 않는다. `view`·`export`는 로그인 확인이나 모델 연결이 필요 없다. `view`에서 R을 누른 경우에만 정상적인 분석 준비·동의 절차로 전환한다.

설정 변경만으로 과거 분석을 일괄 재실행하지 않는다. 과거 재분석이 필요한 경우 개발용 범위 지정 재분석 기능을 두되, 전체 초기화를 기본 새로고침에 연결하지 않는다.

### 3.2 TUI 동작

| 조작 | 동작 |
| --- | --- |
| R / 새로고침 버튼 | 변경 확인과 증분 분석 요청. 진행 중 중복 요청은 차단 |
| 방향키·스크롤 | 흐름 탐색. 사건 선택 방식은 렌더러와 함께 검증 |
| B / 브라우저 상세 | 같은 그래프 버전·선택 사건의 상세 주소 안내 또는 열기 |
| Q / 종료 | 분석 중이면 취소를 안내하고 자식 CLI를 정리. 저장된 결과는 유지 |

화면은 사건의 짧은 제목, 분기·합류, 선택한 사건의 상태·근거 요약, 마지막 분석 기준 시각, 최소 실행 상태와 기록된 LLM 호출의 총 입력·출력 토큰을 표시한다. 사용량이 없는 호출이 있으면 합계가 부분값임을 표시한다. 도구 trace 원문은 화면에 출력하지 않는다.

첫 실행 이후에는 저장된 그래프를 먼저 표시한다. 새 분석 중에는 이전 그림을 유지하고 진행 문구만 갱신한다. 검증·저장이 완료된 일관된 버전에서 그림을 교체한다. 토큰별 레이아웃 갱신이나 폴더 감시 작업은 없다.

터미널 크기 변경·한글 폭·Unicode 선문자·좁은 SSH 분할 화면을 시험한다. ASCII 대체 문자도 지원할 수 있지만, 단순 사건 목록만으로 FR-10 완료라고 판정하지 않는다.

## 4. 프로젝트 범위와 원본 수집

### 4.1 폴더·worktree 식별 — 구현안

사용자 지정 경로를 실제 경로로 정규화한다. Git 저장소이면 공통 Git 디렉터리와 연결된 worktree 목록을 읽는다. Git이 제공하는 공통 디렉터리 및 worktree 조회 인터페이스를 사용한다. [T04, T05]

```bash
git -C <folder> rev-parse --path-format=absolute --git-common-dir
git -C <folder> worktree list --porcelain -z
```

명령은 문자열을 shell에 붙이지 않고 인자 배열로 실행한다. 경로 포함 여부는 문자열 접두사가 아니라 경로 구성요소로 검사한다. `/app`과 `/app-backup`을 같은 범위로 취급하지 않는다.

기본 입력은 저장소 root 또는 worktree root다. 하위 폴더를 지정하면 그 하위 범위를 유지하고, 다른 연결 worktree에서도 같은 저장소 상대 경로가 있는 범위만 대응시킨다. 다른 하위 프로젝트나 별도 저장소로 자동 확대하지 않는다. 저장소가 없으면 지정 폴더와 하위 경로만 사용한다.

Worktree의 `cwd`, branch, commit은 가능한 경우 각 기록의 당시 메타데이터와 함께 저장한다. 세션 전체에 마지막 branch를 소급 적용하지 않는다. 삭제된 worktree는 과거 수집 시 보존한 연결 정보가 있을 때만 연결하고, 없는 연결을 이름이나 시간만으로 추측하지 않는다. Submodule·별도 clone·다중 컴퓨터 자동 통합은 하지 않는다.

### 4.2 로그 경로와 어댑터

대화에서 정한 입력은 SDK/App Server 조회가 아닌 **로컬 파일 직접 읽기**다. 다음 경로는 탐색 기본값이며 실제 지원은 수집한 fixture와 버전으로 검증한다.

| 입력 | 탐색 기본값 | 처리 원칙 |
| --- | --- | --- |
| Codex | `CODEX_HOME` 또는 `~/.codex` 아래 `sessions`, 보존된 `archived_sessions` | 세션·rollout 기록을 읽는다. 압축·새 형식 등 미지원 파일은 경고 |
| Claude Code | `CLAUDE_CONFIG_DIR` 또는 `~/.claude` 아래 `projects` | 프로젝트별 transcript JSONL 및 참조된 tool-result 파일을 읽는다. Prompt history를 전체 대화로 취급하지 않음 |

Codex의 설정 디렉터리와 Claude의 transcript·보존·설정 디렉터리는 공식 문서에서 확인할 수 있다. 개별 rollout 레코드 형식은 배포 버전의 실제 파일로 다시 확인한다. [T03, T08]

먼저 코드가 세션 메타데이터로 프로젝트 관련성을 선별한다. 전체 계정의 무관한 대화를 LLM에 보내고 분류시키지 않는다. 세션이 여러 경로를 다룬 경우 레코드별 범위를 우선하며, 경로가 모호한 구간은 제외 사유를 표시한다.

파서는 다음을 보존한다: 원본 provider·session ID, 원문 record ID가 있으면 그 ID, 역할, 부모/분기 관계, tool call/result 연결 ID, 작성 시각, 당시 경로, 사용 가능한 Git 메타데이터. 새 형식의 알 수 없는 레코드를 조용히 삭제하지 않는다.

Subagent 기록은 부모 연결과 형식이 확인될 때에만 포함한다. 재개·fork·rewind·compaction 결과를 모두 새 독립 사건으로 중복 추출하지 않는다. 요약·압축 레코드는 파생 기록으로 표시하고 원래 실행 결과와 동일한 근거로 취급하지 않는다.

### 4.3 읽기 snapshot과 진행 중 세션

각 분석 실행 시작에 파일별 길이·완전한 JSONL 레코드 경계·내용 digest를 고정한다. 그 이후 추가된 레코드는 다음 새로고침에서 처리한다. 고정한 구간의 원문은 분석 중 읽기 전용 임시 snapshot으로 사용한다.

끝부분이 작성 중인 JSON이면 다음 실행까지 보류한다. 도구 호출은 있으나 결과가 아직 없으면 ‘진행 중’ 또는 ‘결과 없음’으로 보존하고, 뒤에 결과가 추가되면 같은 호출과 연결한다. 미완성 record를 처리 완료 위치에 포함하지 않는다.

## 5. Git 근거 계약

### 5.1 서로 다른 근거를 분리

| 근거 | 보존할 식별 정보 | 해석 제한 |
| --- | --- | --- |
| 커밋 변경 | commit OID, 비교 parent/base, 파일 경로, hunk 또는 blob digest | 커밋이 존재한다는 것만으로 해당 세션이 작성했다고 확정하지 않음 |
| 두 revision 사이 diff | base OID, head OID, diff digest | 최종 차이이며 중간의 미기록 시도 전체가 아님 |
| 현재 staged/unstaged 변경 | worktree ID, 관측 시각, 기준 HEAD/index 정보, 내용 digest | 과거 특정 시각의 상태로 소급하지 않음 |
| 로그의 patch/tool 출력 | 원문 record ID, tool call/result 관계 | 변경 시도·완료 보고·성공 결과를 구분 |
| 원문이 참조한 파일 | 고정 revision 또는 관측 snapshot, 읽은 범위 | 현재 파일을 과거 파일 대신 사용하지 않음 |

현재 변경·과거 revision 비교의 명령 의미는 Git 문서를 기준으로 확인한다. [T09]

새 커밋이나 현재 변경만 있어도 관련 기존 사건에 영향을 줄 수 있으므로 변경 확인 대상에 포함한다. 반대로 커밋 메시지만으로 숨겨진 동기나 테스트 성공을 만들지 않는다. 새 diff의 내용을 AI가 검토하지 않았다면 검토한 것처럼 표시하지 않는다.

### 5.2 실행 안전성과 일관성 — 구현안

Git 조회는 호스트 코드의 허용된 읽기 연산으로 수행한다. `--no-ext-diff`, `--no-textconv` 등으로 외부 diff/textconv 프로그램 실행을 피하고 pager를 끈다. 사용자가 넣은 shell 조각이나 과거 로그의 명령 문자열을 실행 인자로 사용하지 않는다.

Branch 이름은 조회 순간 OID로 고정한다. Mutable worktree 파일은 읽기 전후 상태를 확인하고 변경 경쟁이 발생하면 안정적인 snapshot을 얻지 못했다고 표시한다. Binary·대용량 파일, 접근 불가 객체, 잘린 출력은 명시하고 임의로 모두 모델에 넣지 않는다.

`.projectflow` 또는 공통 Git 디렉터리 아래의 자체 데이터, exports, 임시 분석 파일은 프로젝트 변경 분석에서 제외한다. 제품이 생성한 결과 때문에 다음 새로고침이 스스로를 다시 분석하면 안 된다.

## 6. 저장 구조와 데이터 모델

### 6.1 저장 경로 — 구현 기본안

동일 worktree 집합에서 한 상태를 공유하고 데이터가 우연히 커밋되는 위험을 줄이기 위해, Git 프로젝트에서는 공통 Git 디렉터리 아래의 자체 전용 경로를 제안한다. 앞서 예시로 사용한 root의 `.projectflow`보다 이 목적에 맞춘 **구현안**이며 제품 요구 변경은 아니다.

```text
<git-common-dir>/projectflow/<scope-key>/
├── state.sqlite
├── analyze.lock
├── tmp/              # 현재 분석의 읽기 snapshot, 완료 후 정리
├── debug/            # 개발용 옵션을 켠 경우에만
└── exports/          # 필요할 때 생성
```

`scope-key`는 저장소 내 지정 하위 경로를 기준으로 정한다. 기본 root의 모든 worktree는 같은 key를 쓴다. Git이 없으면 `<folder>/.projectflow/`를 사용한다. `.git`의 objects·refs·index·config 등은 수정하지 않는다. Export 경로를 따로 지정하면 사용자 요청 경로에만 쓴다.

첫 검증은 원격 서버의 **로컬 디스크**를 대상으로 한다. NFS 등 네트워크 파일시스템의 lock/SQLite 동작은 지원 검증 전까지 보장하지 않는다. 별도 동기화나 원격 DB는 만들지 않는다.

### 6.2 최소 저장 테이블 — 구현안

| 테이블 | 핵심 내용 |
| --- | --- |
| `project_meta` | scope, 경로, Runner 선택, schema 버전, 현재 공개 graph version |
| `sessions` | provider/session 키, 원본 경로, worktree·부모 관계, 알려진 parser 형식 |
| `source_records` | 정규화 ID·내용 hash·원문 locator·역할·시간·Git/도구 메타데이터 |
| `evidence_items` | 실제 인용한 원문 범위·발췌·내용 hash·출처·확인 당시 snapshot 정보 |
| `work_units` | source 범위·입력 digest·단계별 상태·구조화된 중간 결과·의존성·적용 여부 |
| `graph_versions` | 일관된 프로젝트 그래프 JSON snapshot·이전 버전·변경 요약 |
| `analysis_runs` | 시작/종료·기준 입력 manifest·상태·완료/미완료 범위·간단한 오류 코드 |

MVP는 그래프를 JSON snapshot으로 저장해도 된다. 이벤트별 복잡한 영속 event-sourcing 인프라를 요구하지 않는다. **AI는 Delta를 제출하고, 프로그램은 그것을 적용한 일관된 snapshot을 저장**한다.

원본 계정 로그 전체를 영구 복제하지 않는다. `source_records`는 추적에 필요한 metadata·digest·locator를 유지하고, 실제 인용한 원문은 `evidence_items`에 보존한다. 분석 중 사용한 임시 자료는 완료 후 정리한다. 원본이 없어지면 보존한 발췌 밖의 추가 문맥은 ‘확인 불가’로 처리한다.

### 6.3 공통 원본 레코드

```text
SourceRecord
  source_id                 프로그램이 부여한 안정적 식별자
  source_version            같은 원본 식별자의 내용 변경 버전
  provider                  codex | claude | git
  session_id                없으면 null
  native_record_id          원본이 제공할 때만
  parent_record_id           원본이 제공할 때만
  role                      user | assistant | tool_call | tool_result | metadata | git
  recorded_at               원본 시각, 없으면 null
  cwd / worktree_id          당시 기록에 근거해 지정, 모르면 null
  tool_call_id               호출·결과 연결용, 없으면 null
  content_hash              원문 또는 정규화 본문의 digest
  locator                   파일·레코드·범위 또는 고정 Git revision·파일·hunk
  derivation                original | summary | unknown
```

원본 ID가 없을 때의 fallback은 `(provider, session, 원본 파일 계보, 레코드 위치, 내용 hash)`를 사용한다. 다른 세션에서 같은 문장이 나왔다는 이유로 동일 사건으로 합치지 않는다. 파일 이동·archive 변경만으로 새 사건을 만들지 않도록 provider ID와 내용으로 대응시킨다.

### 6.4 그래프 계약

| 개체 | 필수 정보 |
| --- | --- |
| `Event` | `id`, `kind`, `title`, `summary`, `actor`, `status`, `basis`, `evidence_ids`, `session_ids`, `worktree_ids`, `recorded_at`, `occurred_at`, `created_in_run`, `updated_in_run` |
| `Edge` | `id`, `from_event_id`, `to_event_id`, `relation`, `basis`, `evidence_ids`, `rationale`, `active` |
| `OpenItem` | `id`, `text`, `status`, `related_event_ids`, `evidence_ids` |
| `GraphSnapshot` | `version`, `scope_id`, `source_snapshot_id`, `analysis_status`, `events`, `edges`, `open_items`, `limitations` |

`Event.kind`는 `goal`, `question`, `proposal`, `decision`, `action`, `outcome`, `revision`에서 시작한다. 필요한 연구·개발 세부 유형은 선택적인 `subtype` 문자열로 보완한다.

`status`는 `proposed`, `adopted`, `in_progress`, `asked`, `applied`, `reported_complete`, `observed_success`, `observed_failure`, `withdrawn`, `unknown` 중 해당 의미를 사용한다. `asked`는 `question` 사건에만, `applied`는 패치·diff 같은 변경 기록을 인용한 `action`/`revision`에만, `observed_*`는 `outcome`에만 쓴다(2026-09-25 결정). `basis`는 `explicit_statement`, `tool_record`, `git_artifact`, `inference`를 구분한다. 상태와 근거는 다른 축이다. 명확한 결정 기록이 있어도 구현 성공이 확인된 것은 아니다.

한 노드의 설명에 서로 다른 검증 수준의 주장을 섞어 하나의 ‘검증됨’ 표시를 붙이지 않는다. 구분이 중요하면 별도 사건으로 나누고 각 출처를 붙인다. `observed_success`는 해당 출력·시험 조건에 한정된 성공이며 제품 전체나 연구 가설의 참을 보장하지 않는다.

`Edge.relation`은 `follows`, `motivates`, `produces`, `revises`, `verifies`, `answers`로 제한한다. 관계는 먼저 일어난 사건에서 나중 사건으로 향한다. `follows`는 후속 작업이며 인과관계가 아니다. `verifies`는 변경 사건(`action`/`revision`)에서 그 변경을 실제로 실행·시험한 관측 결과(`outcome`, `observed_*`)로 향하며 추정으로 만들지 않는다. `answers`는 `question`에서 그 질문에 답한 사건으로 향한다. `basis`는 `explicit`, `structural`, `inferred`를 구분한다. 추정 연결은 확정 화살표와 다른 표시를 쓰고, 근거가 없으면 생략한다. 기록의 모순은 관련 사건과 `limitations`/`OpenItem`에 남긴다.

사건 발생 시각이 명확하지 않으면 `occurred_at=null`로 둔다. 회고 발언의 작성 시각을 실제 사건의 발생 시각으로 바꾸지 않는다. 일반적인 모델 자신감 숫자를 정확도 확률로 사용하지 않는다.

### 6.5 GraphDelta — 호스트가 적용할 변경안

```text
GraphDelta
  base_graph_version
  source_snapshot_id
  events_to_add[]
  events_to_update[]           대상 ID + 허용된 변경 필드 + 이유 + 근거
  edges_to_add[]
  edges_to_invalidate[]        대상 ID + 이유 + 근거
  open_items_to_upsert[]
  open_items_to_resolve[]      대상 ID + 해결 근거
  limitations[]
```

변경 없는 기존 사건은 다시 쓰지 않는다. 새 후보는 `tmp:<id>`를 사용하고 프로그램이 최종 ID를 부여한다. LLM은 임의 SQL·파일 수정·범용 JSON Patch를 제출하지 못하며, 허용된 변경 필드만 적용한다.

실제 방향 전환은 새 revision 사건으로 보존한다. 이전 AI 해석의 오류는 해당 노드 정정·관계 무효화로 기록한다. 관계를 물리 삭제해 과거 해석 변경을 숨기지 않는다. 이전 snapshot은 오류 확인에 사용할 수 있으나 사용자용 Trace 화면은 만들지 않는다.

## 7. 증분 분석과 재사용

### 7.1 분석 단위와 단계 ledger

세션 전체에 `analyzed=true`를 붙이지 않는다. 세션 내 안정적으로 닫힌 기록 구간을 `WorkUnit`으로 만들고 각 단계의 완료를 저장한다. 도구 호출과 결과는 가능한 한 같은 구간에 둔다. 길어진 진행 중 작업은 연결 정보를 보존한 채 나누고, 아직 없는 결과를 기다리느라 세션 전체를 영구 정지시키지 않는다.

WorkUnit 계획은 provider·session·worktree별로 기록을 모아 세션 간 시간순 교차 때문에 한 세션이 잘게 나뉘지 않게 한다. 세션 안에서는 압축 요약 직전 또는 3시간 이상의 기록 공백을 우선 경계로 삼는다. UTC 날짜가 바뀌었더라도 공백이 1시간 미만이면 같은 흐름으로 본다. 크기 한도에 먼저 도달하면 사용자 차례 시작을 우선해 자르고, 가능한 경우 도구 호출·결과와 긴 원문의 조각을 같은 WorkUnit에 둔다. 한도 때문에 연결된 기록을 나눠야 한다면 limitation에 알린다. 이미 통합한 WorkUnit은 세션이 연장되어도 다시 묶지 않는다. WorkUnit은 입력 묶음이며 최종 사건 노드의 의미 경계가 아니다.

모델이 조회할 수 있는 원문 목록은 현재 WorkUnit의 시점까지로 제한한다. 같은 세션의 뒤 기록과 시각상 미래인 다른 출처 기록은 manifest·ReadRequest·revision 파일 목록에서 제외한다. 순수 `<environment_context>` 메시지는 사용자 의사결정이 아닌 호스트 환경 metadata로 분류하고, 기존 WorkUnit에 묶이지 않은 경우 모델 호출 없이 처리 상태만 기록한다. 인용문이 지정한 범위 안의 유일한 연속 줄과 정확히 일치하면 그 줄 범위로 정규화한다. 최소 8자의 유일한 부분 인용은 그 부분이 든 줄 전체로 정규화하고 모델이 가리킨 범위를 `focus`로 남긴다. 원문의 문자열 이스케이프 표기(`\"`, `\n` 등)를 푼 형태의 부분 인용은 조회용 사본에서 유일하게 일치할 때만 원문 표기로 되돌려 저장한다. 같은 부분 인용이 여러 번 일치해도 모두 같은 줄 범위에 있으면 그 줄 범위로 정규화한다. 여러 줄 diff에서는 같은 hunk의 diff 본문 줄에 20줄 이내로 모인 일치만 그 줄들을 함께 근거로 삼는다. 원문에 없는 부분 인용이나 그 밖의 모호한 중복 인용은 거부한다.

```text
discovered → parsed → extracted → integrated
                  ↘ failed / blocked / cancelled
```

`extracted`는 후보 결과가 저장되었다는 의미이고, `integrated`는 그래프 반영까지 완료됐다는 의미다. 단순히 마지막 record 번호 하나만 저장하지 않고, 완료·실패·보류 구간을 따로 유지한다. 앞에 실패 구간이 있으면 이후 최대 위치를 세션 전체 완료 위치로 간주하지 않는다.

### 7.2 갱신 절차

```text
1. 동일 scope의 단일 분석 lock을 확보한다.
2. 현재 저장 그래프를 유지한 채 로그·Git의 입력 snapshot을 만든다.
3. 동일 내용 / 새 기록 / 수정 / 삭제·접근불가 / 미완료 단계를 구분한다.
4. 내용 변화와 재시도 대상이 없으면 no-op으로 종료한다. Runner 호출은 0회다.
5. 새 구간과 영향받은 구간을 작업 단위로 계획한다.
6. 유효한 extracted 결과는 재사용하고 나머지만 추출한다.
7. 관련 기존 사건과 근거를 제공해 GraphDelta를 생성한다.
8. 구조·출처·snapshot·기준 graph version을 검증한다.
9. 통합 가능한 단위의 그래프와 integrated ledger를 같은 transaction에 저장한다.
10. 완료/부분 완료 상태를 저장하고 TUI에서 새 일관된 버전을 표시한다.
```

독립적인 완료 단위만 안전하게 통합할 수 있다면 부분 결과를 게시할 수 있다. 실패 구간에 의존하는 판단은 함께 완료로 처리하지 않는다. 독립성을 확인하기 어려우면 해당 통합을 보류하고 이전 그래프를 유지한다. 추출 결과는 보존하여 다음 실행에서 재사용한다.

### 7.3 내용 식별과 캐시

파일 mtime·길이는 빠른 탐색 단서일 뿐 동일 내용의 증명이 아니다. 기존 구간의 prefix/block digest와 정규화 record hash를 비교한다. 단순 파일 재저장·이동·로그 archive 이동만으로 LLM을 재호출하지 않는다.

캐시 키의 구현안은 다음과 같다.

```text
stage + source-unit digests + 실제 제공한 context digests
      + 사용한 evidence snapshot digests
      + prompt hash + schema hash + runner adapter version
      + 요청 모델/확인 가능한 실제 모델·설정
```

호스트가 입력·추가 제공 근거의 dependency manifest를 작성한다. **최종 인용된 근거만이 아니라, 실제 입력 맥락으로 제공한 근거도 의존성에 포함**한다. 인용하지 않은 자료를 읽고 내린 해석도 변경의 영향을 받을 수 있기 때문이다.

캐시는 pending 작업을 처리할 때 적용한다. Runner·모델·프롬프트를 바꿨다는 이유만으로 이미 integrated인 모든 구간을 다시 pending으로 바꾸지 않는다. 명시적 재분석 또는 실제 근거 변경이 있는 경우에만 해당 범위를 갱신한다.

### 7.4 세션 연장

어제의 구간 1~300이 완료되고 오늘 301~345가 추가됐다면 새 구간과 열린 작업 요약, 관련 기존 사건을 제공한다. 필요하면 과거 원문 일부만 읽는다. 1~300 전체를 신규 분석 대상으로 다시 제공하지 않는다.

기존 chunk 경계를 매번 전체 재계산해 과거 캐시를 무효화하지 않는다. 미완결 마지막 구간은 이어받을 수 있으나 재사용한 맥락은 `context_only`로 표시하여 새 사건·처리량을 중복 계산하지 않는다. 반복 설명과 별도의 실제 재시도를 구분한다.

### 7.5 기록 수정·소실

| 변화 | 동작 |
| --- | --- |
| 기록 append | 새로운 완전한 레코드와 영향받은 기존 관계만 처리 |
| 동일 내용의 위치 이동 | 원본 ID·내용으로 재연결. 모델 호출 없이 locator 갱신 |
| 기존 본문 수정·재작성 | 변경된 record와 의존하는 추출·통합 단위를 재검토 대상으로 표시 |
| 기록 truncate | 소실 구간에 의존한 결과의 근거 상태를 확인. 마지막 위치를 무조건 뒤로 덮어쓰지 않음 |
| 원본 파일 삭제·보존 기간 만료 | 이미 보존한 인용 근거는 유지. 원본 부재를 사실 철회로 해석하지 않음 |
| parser 미지원 | 해당 범위를 미처리로 표시. 지원했다고 가장하지 않음 |
| 새 Git 근거 | 관련 작업의 구현·결과 확인 수준을 갱신할 후보로 검토 |

원본이 변경되어 현재 해석의 유효성이 불확실하면 기존 그림에도 한계를 표시한다. 새 분석이 실패했다고 오래된 결과를 아무 경고 없이 ‘최신’으로 보여주지 않는다.

### 7.6 중단·중복 실행

단일 process/file lock으로 같은 scope의 동시 분석을 차단한다. 장시간 모델 호출 동안 SQLite write transaction을 열린 채 유지하지 않는다. 그래프 변경은 짧은 transaction과 기준 버전 검사로 적용한다.

추출 응답이 저장되었으면 재시작 후 재사용한다. 통합 저장은 그래프·단계 완료·공개 버전 포인터를 함께 변경한다. 기준 그래프 버전이 달라지면 Delta를 그대로 적용하지 않고 필요한 통합만 다시 수행한다.

모델 응답 직후 저장 전에 강제 종료되면 재호출이 필요할 수 있다. 외부 모델 호출의 exactly-once는 약속하지 않지만, 저장된 Delta의 중복 적용은 막는다. SSH 연결 종료 후에도 실행이 계속된다는 보장은 하지 않는다. 다음 명시적 실행에서 저장 상태로 복구한다.

## 8. 분석 Runner와 읽기 전용 Harness

### 8.1 Runner 계약

```text
Runner.preflight() → 설치 버전, 인증 상태 확인 가능 여부, 지원 기능
Runner.run(task_input, schema, run_limits) → 구조화된 결과, 상태, 제공되는 사용량
Runner.cancel() → 실행 중인 자식 프로세스 종료 및 정리
```

두 Runner는 같은 논리 출력 계약을 따른다. 실제 JSON wrapper·오류·사용량 필드는 어댑터에서 정규화한다. 입력 source가 두 종류라고 두 Runner를 동시에 실행하지 않는다. 한 번의 분석은 선택한 Runner 하나를 사용한다.

Codex의 문서에는 `codex exec`, `--json`, `--output-schema`, `--ephemeral`, 저장된 인증 재사용이 설명되어 있다. Claude Code에는 print 모드, JSON Schema 출력, 세션 저장 비활성화와 도구 제한 옵션이 있다. **이 기능의 문서상 존재와 우리 서버 버전에서의 호환성은 별도로 확인한다.** [T01, T02]

부록의 공식 옵션을 조합한 최종 실행 명령은 Phase 1 시험 후 고정한다. `--help`·버전·fixture로 검증하지 않은 복잡한 명령을 이 문서에서 작동 보장 예제로 제공하지 않는다.

### 8.2 기본 실행 방식 — 구현안

호스트가 선별·고정한 대화와 근거를 입력으로 제공한다. 분석 AI는 기록을 읽고 필요한 추가 자료를 요청할 수 있다. 임의 shell·네트워크 도구를 열어 Git을 직접 탐색시키는 방식은 사용하지 않는다.

초기 구현은 **구조화된 ReadRequest 왕복**을 기본안으로 둔다. CLI는 분석 결과 또는 허용된 자료 요청을 반환하고, 호스트가 요청을 해결해 같은 작업의 맥락으로 다시 제공한다. 이는 범용 Agent 플랫폼이나 사용자용 MCP 기능이 아니라 네 가지 자료 조회만 있는 제한된 Harness다.

| ReadRequest | 허용 대상 | 호스트 동작 |
| --- | --- | --- |
| `read_records` | 해당 snapshot의 session/record ID와 범위 | 고정 원문·역할·출처를 반환 |
| `read_existing_event` | 현재 입력에 허용된 event ID | 사건과 인용 근거를 반환 |
| `read_diff` | manifest에 있는 diff ID | 고정 OID 또는 관측 snapshot의 patch를 반환 |
| `read_file_at_revision` | 허용된 revision ID·파일 ID·범위 | 관련 근거 내용만 반환 |

AI가 임의 절대 경로나 명령문을 요청할 수 없다. 대상이 manifest 밖이면 거부하고 한계로 반환한다. 이 방식이면 새 MCP 서버를 요구하지 않고도 ‘필요한 과거 원문과 diff를 더 읽고 판단’할 수 있다. 나중에 CLI의 제한된 파일 도구를 연결하더라도 같은 범위 계약을 유지한다.

작업별 응답은 `status=needs_evidence|complete`와 `read_requests`, 해당 단계의 payload를 가진다. `needs_evidence` 결과는 최종 분석으로 적용하지 않는다. 추가 근거 왕복은 처음에는 최대 2회, 검증 오류 수정은 최대 1회라는 **조정 가능한 기본안**으로 시작한다. 부족하면 불확실성을 남기며 무한 탐색하지 않는다.

긴 기록은 runner별 입력 예산 아래로 나눈다. 고정된 입력 문자/토큰 예산, 출력 예산, timeout은 실제 fixture 측정 후 설정 파일에 명시한다. 모델의 context 길이나 처리 속도를 추정해 무제한 입력하지 않는다.

### 8.3 권한·설정·인증

Runner는 사용자가 해당 서버에서 설치·인증한 CLI를 실행한다. 기존 대화 세션을 resume하거나 그 안에 분석 프롬프트를 끼워 넣지 않는다. 프로그램은 인증 파일을 직접 읽어 DB·prompt·trace에 복사하지 않는다.

분석용 실행은 원본 repository 밖의 관리된 입력 작업 공간을 사용한다. 기존 `AGENTS.md`, `CLAUDE.md`, 사용자/프로젝트 hooks·plugins·MCP 설정을 무조건 상속하지 않는다. 필요한 CLI 인증과 위험한 자동 실행 설정을 구분해야 하며, 안전하게 제한할 수 없는 설치·정책에서는 분석을 중단하고 안내한다.

‘읽기 전용이라고 프롬프트에 썼다’는 것으로 권한 제한을 충족하지 않는다. 코드 수정·명령 실행·외부 검색 도구를 차단하고 실제로 적용되는지 시험한다. `danger-full-access`, permission bypass, 검증 실패 후 자동 권한 확대는 사용하지 않는다. CLI 프로세스 자체의 정상 인증·캐시 처리까지 전혀 디스크 쓰기가 없다고 보장하는 것은 아니다.

클라우드 분석 전 입력 범위와 전송 사실을 확인한다. CLI의 계정 조건·한도가 적용되며 무료 또는 무제한 호출을 약속하지 않는다. 제3자 로그인 중개나 구독 토큰 전용 API를 만들지 않는다.

### 8.4 자기 분석 방지

지원되는 세션 비저장 실행 옵션을 적용하고, 우리 run/session 식별자와 임시 작업 경로도 입력 제외 목록에 기록한다. 첫 방어가 실패해 자체 세션 파일이 남더라도 두 번째 스캔에서 배제한다. 분석용 로그·그래프·export가 프로젝트의 원래 진행 사건으로 편입되면 안 된다.

## 9. 분석 단계와 실제 프롬프트 v1

### 9.1 작업 순서

**입력 준비(코드) → 구간별 사건 추출(AI) → 필요한 근거 추가 읽기 → 관련 기존 흐름 통합(AI) → 검증·저장(코드) → 렌더링(코드)**

한 명의 선택된 Runner가 두 종류의 작업을 수행한다. 역할별 다중 Agent를 만들지 않는다. 추출 결과가 비어 있고 관련 상태 변경도 없으면 통합 AI 호출을 생략할 수 있다. 사건이 없는 구간도 읽은 입력 단위의 완료를 저장한다.

모든 새 입력 record는 어떤 작업 단위에 배정됐는지 호스트가 관리한다. 하지만 ‘제공한 record 수’나 LLM의 완료 선언만으로 의미적으로 전부 이해했다고 검증했다고 표현하지 않는다.

### 9.2 공통 지침

다음 본문을 두 Runner에 공통으로 전달한다. 파일명 후보는 `prompts/common.md`다.

```text
당신은 프로젝트 이력 분석기다.

임무는 제공된 대화, 도구 실행 기록, Git 변경을 읽고 프로젝트가 어떤
목표·시도·결과·결정 변경을 거쳐 진행됐는지 근거와 함께 복원하는 것이다.

프로젝트를 대신 수행하거나 앞으로 할 일을 새로 추천하지 않는다.

- 판단은 짧은 근거 설명과 인용으로 제시한다. 비공개 내부 사고 과정은 요구하거나 출력하지 않는다.

```

### 9.5 검증 오류 수정 작업

파일명 후보: `prompts/repair.md`. 구조적 검증 오류가 있을 때만 최대 1회 사용한다.

```text
제출 결과에 아래 검증 오류가 있다.
{validation_errors}

문제가 있는 항목만 수정하라. 유효한 항목과 기존 ID를 불필요하게 바꾸지 않는다.
존재하지 않는 출처를 만들지 않는다. 근거가 없는 관계는 제거 또는 미확인으로 남긴다.
전체 프로젝트를 다시 분석하지 않는다.
수정할 수 없는 오류는 미처리 항목으로 반환한다.
원래 단계의 JSON 출력 계약을 유지하라.
```

형식 수정과 의미 검증은 다르다. 이 프롬프트를 거쳤다는 이유로 모델의 해석이 정답이 되었다고 판단하지 않는다.

### 9.6 합성 fixture 예시

| 원본 기록 | 기대하는 사건 |
| --- | --- |
| 사용자: “우선 JSON 파일로 저장하자.” | JSON 저장 채택 |
| AI: “SQLite도 검토할 수 있습니다.” | SQLite 제안. 채택이나 구현 완료 아님 |
| patch: JSON 저장 코드 추가 | JSON 구현 변경 확인 |
| tool result: 동시 쓰기 테스트 오류 | 해당 테스트 실패 |
| 사용자: “동시 쓰기 때문에 SQLite로 바꾸자.” | 실패를 근거로 한 SQLite 전환 결정 |
| AI: “변경했고 테스트도 통과했습니다.”, 실제 출력 없음 | 완료 보고. 실행 성공은 미확인 |

기대 흐름은 **JSON 채택 → 구현 → 테스트 실패 → SQLite 전환 결정 → 완료 보고(미검증)**이다. 이후 실제 변경·출력이 추가되면 기존 보고에 근거를 연결해 확인 상태를 갱신한다. SQLite 제안 시점으로 채택 시점을 소급하지 않는다.

## 10. 검증·게시·실패 계약

### 10.1 저장 전 검사

| 검사 | 차단 또는 보류할 경우 |
| --- | --- |
| 출력 구조 | 스키마 불일치, 알 수 없는 상태·관계, 필수 필드 누락 |
| 출처 존재 | 해당 snapshot에 없는 source/evidence ID |
| 인용 일치 | 원문 범위·발췌·hash가 일치하지 않음 |
| 참조 무결성 | 없는 event로 연결하거나 기존 ID를 임의로 변경 |
| 범위 | 다른 프로젝트·허용되지 않은 경로의 근거를 사용 |
| 증거 수준 | observed_success를 주장하지만 연결된 실행 근거가 전혀 없음 |
| 기준 버전 | Delta의 graph version 또는 source snapshot이 현재 적용 대상과 다름 |
| 처리 coverage | 필수 work unit가 누락됐는데 전체 완료로 제출 |

프로그램은 가능한 구조·참조·범위 검사를 책임진다. 실제 원문이 주장의 의미를 뒷받침하는지는 AI의 원문 대조와 사람이 확인한 회귀 fixture로 평가한다. **유효한 JSON, 존재하는 출처, 모든 record를 입력에 넣었다는 사실은 의미적 정확성을 보장하지 않는다.**

### 10.2 실행 상태

| 상태 | 의미와 사용자 표시 |
| --- | --- |
| `no_data` | 분석 가능한 기록이 없음. 프로젝트가 없거나 작업을 하지 않았다는 의미가 아님 |
| `scanning` | 입력 변화 확인 중 |
| `analyzing` | 새 구간 추출·근거 확인·통합 중 |
| `validating` | 결과 계약과 출처 검사 중 |
| `complete` | 이번에 선택한 snapshot의 대상 작업을 처리함 |
| `noop` | 새 입력·변경·미완료 대상 없음. AI 호출 0회 |
| `partial` | 일부 미처리·접근 불가·불확실한 범위가 남음 |
| `failed` | 이번 갱신 실패. 이전 공개 그래프 유지 |
| `cancelled` | 사용자 중단. 저장된 단계는 재사용 가능 |

`complete`는 모든 Git diff를 완전히 읽었다거나 과거 모든 기록이 존재한다는 뜻이 아니다. 입력 범위·확인한 근거·한계를 함께 보존한다.

### 10.3 기본 오류 처리

| 오류 | 처리 |
| --- | --- |
| Runner 미설치·미인증 | 분석만 차단하고 `view`/`export`는 허용. 다른 모델로 자동 전환하지 않음 |
| 지원하지 않는 CLI 출력 | 원문 결과를 정상 JSON으로 가장하지 않고 어댑터 오류로 종료 |
| timeout·취소 | 자식 프로세스 정리. 추출/게시 완료 결과 유지 |
| 구조 오류 | 해당 단계에 한 번만 제한된 repair 요청 |
| 근거 접근 실패 | 해당 주장 수준을 낮추거나 보류. 없는 내용을 보충하지 않음 |
| 파일 쓰기 중·부분 JSON | 다음 실행까지 보류. 정상 레코드 삭제 금지 |
| DB 저장 실패 | 처리 위치를 앞으로 이동시키지 않음. 이전 버전 유지 |
| 렌더링 실패 | 분석 결과를 보존. 출력 계층 오류를 위해 LLM 전체 재분석하지 않음 |
| 개발 Trace 전송 실패 | 사용자 분석·로컬 저장을 실패시키지 않음 |

## 11. 렌더링·브라우저·내보내기

### 11.1 같은 그래프의 두 표현

```text
SQLite의 검증된 GraphSnapshot
  ├─ 개요 선택 → 안전한 Mermaid subset → ASCII/Unicode → TUI
  ├─ 상세 선택 → 안전한 Mermaid → SVG → 브라우저
  └─ JSON / mmd / md export
```

LLM은 Mermaid를 작성하지 않는다. 프로그램이 안전한 내부 노드 ID와 escape된 제목으로 만든다. 서로 다른 뷰에 별도 AI 요약을 돌리지 않는다.

TUI는 주요 목표·결정·결과·revision을 우선 표시한다. 의미상 분기·실패가 유지되어야 한다. 큰 그래프는 작업 구간 선택과 스크롤로 다루고, 최초부터 자유 레이아웃 편집이나 다단계 대시보드를 구현하지 않는다.

개요에서 중간 사건을 생략하더라도 A→B→C를 원래 없던 ‘A가 C의 원인’ 화살표로 바꾸지 않는다. 필요하면 ‘중간 사건 생략’이라는 표시 전용 연결을 사용하고 분석 그래프에 저장하지 않는다. 생략 수를 알려 주고 상세 보기에 같은 사건 ID로 접근할 수 있게 한다.

렌더러가 지원하지 않는 관계나 한글을 조용히 누락하면 안 된다. 개발 중 텍스트 fallback은 허용하지만, 두 실행기로 만든 유효한 그래프의 TUI 렌더링 시험을 통과해야 FR-10을 완료로 본다.

### 11.2 상세 뷰어의 범위

상세 화면은 그래프, 선택 사건 설명, 명시/추정 구분, 원문 발췌와 주변 문맥, 관련 diff와 관측 시각을 보여준다. 원문이 사라졌다면 저장된 발췌와 원본 부재를 표시한다. 브라우저에 내부 프롬프트·중간 JSON·Trace 타임라인은 넣지 않는다.

작은 로컬 HTTP 뷰어를 만들며, 개념상 다음 동작만 필요하다. 경로명은 구현안이다.

| 요청 | 효과 |
| --- | --- |
| `GET /graph` | 저장된 그래프·버전·coverage 조회 |
| `GET /events/<id>` | 사건과 관련 근거 조회 |
| `GET /evidence/<id>` | 허용된 저장 근거 조회. 임의 경로 읽기 아님 |
| `POST /refresh` | 명시적 증분 분석 요청. 기존 분석 lock 사용 |

브라우저 새로고침(F5)·GET·탭 재접속은 AI를 호출하지 않는다. 이 endpoint는 사용자용 MCP API나 외부 공개 API가 아니다.

### 11.3 SSH와 접속

서버는 기본적으로 `127.0.0.1`에만 바인딩한다. PC 브라우저는 사용자가 설정한 SSH 포트 포워딩으로 접속한다. 예시 포트는 8765이며 충돌 시 실제 포트 안내를 갱신한다. SSH의 `-L` 기능은 공식 매뉴얼을 참고한다. [T10]

```bash
# 사용자의 PC에서 실행하는 접속 예시
ssh -L 127.0.0.1:8765:127.0.0.1:8765 user@server
```

PC 브라우저 주소 예시: `http://127.0.0.1:8765`. 서버가 PC의 브라우저를 열 수 있다고 가정하지 않는다. 자동 SSH 터널 생성·인터넷 공개·데스크톱 창 배치는 구현하지 않는다.

### 11.4 표시·접속 안전성

본문·파일명에서 제어문자, ANSI/OSC escape, Mermaid 구문 삽입을 제거하거나 표시 가능한 텍스트로 변환한다. 브라우저에는 raw HTML을 삽입하지 않는다. 외부 이미지·폰트·스크립트 CDN으로 원문이나 metadata가 유출되지 않도록 필수 렌더링 asset을 패키지에 포함한다.

로컬 서버라도 인증 없이 모든 사용자가 민감한 기록을 읽게 하지 않는다. 프로세스별 임시 접근 토큰 또는 동등한 로컬 접근 제어를 두고 Host/Origin 확인, 상태 변경 요청 보호를 적용한다. 공개 계정 시스템이나 다중 사용자 권한 제품을 만드는 것은 아니다.

Export에는 민감한 대화·코드가 포함될 수 있음을 표시한다. `md`는 Mermaid 코드 블록, 주요 사건 설명, 근거 목록과 분석 기준을 포함한다. `mmd`는 렌더링 코드만, `json`은 버전 있는 그래프와 참조를 제공한다. 개발용 trace나 인증 정보는 포함하지 않는다.

## 12. 개발용 관측과 평가

### 12.1 제품 필수 상태와 Trace의 경계

| 항상 필요한 내부 정보 | 개발 옵션에서만 필요한 상세 정보 |
| --- | --- |
| 완료/실패 unit, source digest, graph version, prompt/schema hash, Runner·버전 | 전체 프롬프트, 중간 JSON, 추가 근거 조회 순서, 상세 CLI event |
| 재사용 여부, 최소 오류 코드, 근거 locator | 상세 timing, 응답 분석, 회귀 실험 비교 |

LLMOps 도구를 사용하더라도 **사용자에게 별도 Trace 화면·계정·설정 체계를 제공하지 않는다.** 사용량은 Runner가 제공할 때만 기록하고, 누락값을 0으로 만들거나 추정치를 실제 과금액으로 표시하지 않는다.

개발용 상세 추적은 기본 비활성화한다. 선택적 LangSmith 연동을 명시적으로 켜면 새 LLM 호출을 외부로 보낸다. 사용자 선택에 따라 모델 입력·출력을 포함할 수 있으므로 실제 프로젝트 대화·코드의 전송 범위를 명확히 알린다. 제3자 연결 실패는 제품 분석을 중단시키지 않는다.

비공개 chain-of-thought를 저장·재현하는 요구사항은 없다. 입력, 관찰 가능한 도구 요청, 구조화된 출력, 짧은 근거 설명, 오류를 기록하면 된다.

### 12.2 평가 방법

사람이 확인한 작은 개발·연구 fixture를 기준으로 사건 누락, 제안→완료 오판, 근거 없는 관계, worktree 오귀속을 검사한다. 전체 대화를 한 번에 요약하는 기준선과 비교할 수 있지만, 복잡한 Harness가 우수하다고 미리 주장하지 않는다.

프롬프트를 바꾸면 같은 원문 snapshot과 같은 초기 graph에서 결과를 비교한다. 초기 분석과 맥락이 정리된 증분 분석을 서로 다른 조건인 채 비교하지 않는다. 자동 점수만이 아니라 잘못된 사건·관계의 실제 예시를 함께 확인한다.

평가 도구 자체를 제품 화면으로 만들지 않는다. 익명화·합성 fixture와 테스트 명령, 개발자가 읽을 수 있는 결과 파일이면 충분하다.

Mock Runner로 결정적 처리·재사용·오류 테스트를 우선 수행하고, 두 실제 CLI로 작은 smoke test를 별도로 수행한다. Mock 성공만으로 실제 CLI 지원을 완료했다고 쓰지 않는다.

릴리스 기준은 필수 계약 테스트의 통과, 두 Runner의 실제 연동 확인, 개발·연구 표본에서 알려진 고위험 오판의 해결이다. 일반적인 모든 프로젝트에 대한 정확도 보장은 아니다.

## 14. 구현 단계와 미확정 사항

### 14.1 작은 수직 구현 순서

| 단계 | 구현할 것 | 범위 확대 금지선 |
| --- | --- | --- |
| Phase 1 — compatibility spike | 실제 로그 표본, native ID/append/worktree 파싱, 두 CLI의 안전한 구조화 호출, 한글 Mermaid 문자 렌더링 | 지원 확인 전 범용 plugin·멀티 OS 자동 설정 만들지 않음 |
| Phase 2 — 기본 흐름 | 한 프로젝트의 수집→추출→통합→SQLite→TUI, 짧은 원문 근거 | UI 꾸미기·다중 Agent 역할 추가보다 근거 연결 우선 |
| Phase 3 — continuity | no-op, append, 변경 의존성, 중단 재사용, 공통 worktree 상태 | 파일 감시·분산 job·동기화 추가 금지 |
| Phase 4 — detail/export | 로컬 HTML 근거·diff, SSH 안내, JSON/mmd/md | 편집 Canvas·사용자 Trace 화면 추가 금지 |
| Phase 5 — regression | 두 Runner 비교 fixture, 보안·부분 실패·자기 분석 방지 | 평가 플랫폼을 별도 제품으로 만들지 않음 |

### 14.2 구현 전 확인할 항목

| 항목 | 현재 상태 | 결정 방법 |
| --- | --- | --- |
| 제품 이름·명령·패키지 이름 | 가칭 | 배포 전 충돌과 선호 확인 |
| 공개 라이선스 | 미선택 | 새 코드·재사용 의존성의 조건 확인 후 결정 |
| Python/TUI/터미널 renderer | 기본안·후보 | Linux/SSH, 한글, 분기·합류, 설치 부담 시험 |
| CLI 최소 지원 버전·flags | 미검증 | 서버의 설치 버전과 공식 문서, 작은 연동 시험 |
| 무관한 설정·도구의 차단 방식 | 릴리스 전 검증 필요 | 두 Runner별 권한·자동 로딩 테스트. 불충분하면 안전하지 않은 fallback 금지 |
| 첫 실제 fixture | 미지정 | 진행 흐름을 기억하는 사용자 프로젝트의 허가된 작은 표본 |
| 입력 예산·timeout·개요 노드 수 | 튜닝 항목 | 실제 기록으로 측정하고 설정값 명시 |

이 항목들은 사용자 요구를 다시 확장하는 안건이 아니다. 구현 선택으로 해결하고, 제품 범위를 바꿀 필요가 생길 때만 PRD를 수정한다.

## 15. 근거와 기술 참고문헌

### 15.1 요구사항의 근거

제품 요구와 우선순위는 이 대화의 최신 합의와 [PRD §12](PRD.md)의 결정 기록을 기준으로 한다. Asterelle의 과거 장기 비전이나 기존 포트폴리오의 기술 표현을 구현 완료 요구·실적으로 바꾸어 넣지 않았다.

SQLite 경로, 최소 테이블, ReadRequest 왕복, 함수·명령 이름, 기술 스택과 튜닝 값은 이 문서에서 구체화한 **구현 기본안**이다. 아직 실행 시험으로 검증된 사실이 아니다.
