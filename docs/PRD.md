## Codex·Claude Code 기록으로 프로젝트 진행 흐름을 복원하는 도구

| 항목 | 내용 |

| 문서 버전 | v0.1 · MVP 범위 기준선 |

## 1. 해결할 문제

Codex와 Claude Code를 사용해 앱을 만들거나 연구를 진행하면, 의사결정의 이유와 시행착오가 여러 세션·도구 출력·커밋에 나뉘어 남는다. 작업을 이어서 하려면 기록을 다시 읽고 다음을 직접 재구성해야 한다.

- 무엇을 하려고 했고, 어떤 방법을 선택했는가?
- 실제로 무엇을 수행했고, 어떤 결과가 확인되었는가?
- 왜 이전 접근을 유지하거나 바꾸었으며, 아직 무엇이 남았는가?

이 제품은 그 재구성 작업을 돕는다. 단순 대화 요약, 커밋 목록 시각화, 새로운 연구나 개발을 수행하는 Agent가 아니다. **이미 남아 있는 기록으로부터 진행 과정을 복원하는 독립 엔진**이다.

## 2. 목표와 성공의 정의

### 2.1 목표

| 목표 | 사용자에게 주는 가치 |
| --- | --- |
| 진행 과정 복원 | 목표·시도·실패·결과·결정 변경을 하나의 흐름으로 확인 |
| 근거 확인 | 각 사건과 중요한 연결을 원문 대화·도구 결과·diff로 확인 |
| 지속적인 재사용 | 결과를 저장하고, 세션을 이어서 작업하면 추가된 부분만 분석 |
| 작업 옆에서 확인 | 터미널 분할 영역에 간략한 흐름을 띄워 두고 필요할 때 상세 탐색 |

### 2.2 첫 성공 기준

**진행 과정을 기억하는 실제 프로젝트 표본에서 흐름이 맞게 복원되고, 같은 입력으로 다시 실행할 때 AI 호출이 없으며, 추가 작업 이후 새로고침으로 기존 흐름이 갱신되어야 한다.**

예쁜 그림만으로 성공을 판정하지 않는다. 제안을 구현 완료로 바꾸거나, 다른 worktree의 테스트 결과를 가져오거나, 철회한 결정을 현재 결정으로 표시하면 실패다. 반대로 근거가 부족한 부분을 미확인으로 남기는 것은 정상 동작이다.

정확도·속도·비용의 실측 수치는 아직 없다. 임의의 달성률이나 처리 시간 약속을 제품 성과로 기재하지 않는다.

## 3. 사용자와 실행 전제

주 사용자는 Codex·Claude Code로 개발 또는 연구를 수행하는 개인이다. 도구를 번갈아 쓰거나 같은 저장소의 worktree에서 병렬 작업할 수 있다. 연구 전용·개발 전용 모드를 먼저 선택하도록 요구하지 않는다.

첫 검증은 원격 Linux에서 한다. 별도 원격 실행 엔진을 만드는 것이 아니라, **프로젝트와 로그가 있는 서버에서 일반 CLI/TUI를 실행**한다. 분석 실행기의 설치와 인증도 같은 서버 환경을 기준으로 한다.

사용자는 프로젝트 폴더 하나만 지정한다. 여러 저장소·컴퓨터의 기록을 하나로 등록·병합하는 기능은 제공하지 않는다. 로컬 저장 파일을 읽되, 클라우드 모델을 통한 분석은 선택한 자료의 외부 전송을 수반할 수 있음을 구분한다.

## 4. 용어와 역할 구분

| 용어 | 의미 |
| --- | --- |
| 입력 어댑터 | Codex 또는 Claude Code의 기존 로컬 기록을 읽는 구성요소 |
| 분석 실행기, Runner | 새 분석 작업을 수행하는 설치·인증된 Codex 또는 Claude Code CLI |
| 분석 Harness | 자료 범위, 분석 지침, 출력 형식, 추가 근거 읽기, 검증을 관리하는 우리 코드 |
| 프로젝트 그래프 | 사용자의 목표·시도·결과·결정 변경을 표현한 결과 데이터 |
| 근거, Evidence | 그래프의 사건·관계를 뒷받침하는 원문 또는 Git·실행 자료 |
| 내부 Trace | 분석기가 어떤 입력·출력·오류·재시도를 거쳤는지 보여주는 개발용 기록 |

**입력 출처와 Runner는 독립적이다.** 두 도구의 기록을 함께 읽고, 분석은 둘 중 하나에 맡긴다. 두 Runner를 동시에 실행해 합의시키는 기능은 포함하지 않는다.

## 5. MVP 범위

### 5.1 포함할 요구사항

| ID | 요구사항 | 완료 판단 |
| --- | --- | --- |
| FR-01 | 지정한 폴더와 같은 저장소의 관련 worktree를 분석 범위로 삼는다. | 다른 저장소나 무관한 세션을 자동 합치지 않는다. Worktree별 출처를 보존한다. |
| FR-02 | Codex·Claude Code 로컬 세션 기록을 모두 읽는다. | 대화·도구 호출·결과·세션 식별 정보를 보존한다. 한 출처가 없어도 나머지를 사용할 수 있다. |
| FR-03 | 관련 Git 변경을 읽기 전용 근거로 활용한다. | 과거 커밋 diff와 현재 미커밋 변경을 구분한다. 코드 변경 없는 결정도 포착한다. |
| FR-04 | AI가 사건과 관계를 추출하고 기존 흐름에 통합한다. | 제안·채택·수행 보고·실제 변경·실행 결과를 구분하고 근거 없는 연결을 확정하지 않는다. |
| FR-05 | Codex·Claude Code를 첫 버전의 분석 Runner로 모두 지원한다. | 사용자가 하나를 선택하며 기존 CLI 인증을 사용한다. 직접 토큰 중개 기능은 만들지 않는다. |
| FR-06 | 분석 그래프와 원문 근거, 처리 상태를 로컬에 저장한다. | 재실행 후 결과를 불러오며, 저장된 결과 열람은 AI 호출 없이 가능하다. |
| FR-07 | 이미 완료된 동일 입력의 분석을 재사용한다. | 새 자료·변경·미완료 작업이 없으면 AI 호출 0회. 화면 변경·내보내기도 0회. |
| FR-08 | 이어진 세션의 변경분을 증분 분석한다. | 새 기록과 필요한 기존 맥락만 읽고 영향을 받는 사건·관계만 갱신한다. |
| FR-09 | 분석 실행 시와 명시적인 새로고침에서만 갱신한다. | 상시 감시·자동 주기 실행이 없고 분석 중에는 이전 그림을 유지한다. |
| FR-10 | 터미널 TUI를 기본 뷰어로 제공한다. | 주요 사건과 분기를 실제 문자 그래프로 보여주고 스크롤·선택·새로고침이 가능하다. |
| FR-11 | 브라우저에서 상세 흐름과 근거를 제공한다. | 같은 사건 ID로 원문 대화·도구 결과·diff를 확인한다. SSH 사용 시 접속 방법을 안내한다. |
| FR-12 | JSON·Mermaid·Markdown으로 결과를 내보낸다. | 같은 저장 그래프에서 생성하며, 별도 AI 요약을 만들지 않는다. |
| FR-13 | 부분 실패·중단에 대응하고 완료된 작업을 재사용한다. | 이전 결과를 잃지 않는다. 미처리 범위를 완료로 숨기지 않는다. |
| FR-14 | 프로젝트와 로그를 분석 목적으로만 읽는다. | 원본 수정, 과거 명령 재실행, 테스트 재실행, 무관한 파일 접근을 허용하지 않는다. |
| FR-15 | 내부 관측은 개발·디버깅용으로 분리한다. | 사용자 Trace 대시보드·외부 관측 계정이 없어도 제품이 작동한다. |

Git이 없는 폴더는 대화 기록만으로 분석하고 Git 근거가 없다는 사실을 표시하는 것을 구현 기본안으로 둔다. 하위 폴더의 범위 해석과 저장 경로의 구체적인 규칙은 SPEC에서 구현안으로 명시한다.

### 5.2 이번 버전에서 제외

| 보류 대상 | 경계 |

Asterelle과 개념적으로 연결될 수 있지만, 이번 제품에 Asterelle의 연구 운영·정책·승인 구조를 이식하지 않는다.

## 6. 핵심 사용 흐름

### 6.1 처음 분석

1. 사용자가 터미널에서 프로젝트 폴더를 지정하고 분석을 시작한다.
2. 처음 필요한 경우 Runner와 전송 범위를 확인한다. 인증은 해당 CLI에서 수행한다.
3. 프로그램은 관련 로그와 Git 근거를 찾고 분석할 범위를 고정한다.
4. AI가 자료를 읽고 사건·관계 후보를 추출한 뒤 기존 그래프에 반영할 변경안을 작성한다.
5. 검증된 결과를 저장하고 터미널 그림으로 보여준다. 부족한 자료는 한계로 표시한다.

### 6.2 다시 열기와 새로고침

저장된 그림이 있으면 먼저 보여준다. `analyze` 실행은 새 자료를 확인하고, `view` 실행은 저장된 자료만 연다. TUI의 **R/새로고침**은 동일한 증분 분석을 명시적으로 요청한다.

변경이 없고 재시도할 미완료 작업도 없으면 AI를 호출하지 않는다. 변경이 있으면 새 구간과 관련된 기존 근거만 분석한다. 성공 후 그림을 교체하며, 실패하면 이전 결과를 유지한다. 한 번에 분석 작업 하나만 실행한다.

### 6.3 세션을 이어서 사용한 경우

어제의 분석이 ‘방식 A 채택 → 구현 진행 중’이었다면, 오늘의 실패·철회·방식 B 채택 기록을 추가해 흐름을 갱신한다. A를 채택했던 과거 사실은 지우지 않는다. 이전 AI 분석 자체가 틀렸던 경우에는 그 해석을 정정하되 실제 프로젝트의 방향 전환과 구분한다.

### 6.4 근거를 확인하는 경우

터미널에서 사건을 선택하면 짧은 설명과 근거 식별자를 본다. **B/브라우저 상세**로 같은 사건의 원문과 diff를 확인한다. 페이지 열기·F5·노드 선택은 저장된 결과 조회이며 분석을 실행하지 않는다. 상세 화면의 분석 새로고침도 명시적인 동작으로만 제공한다.

## 7. 화면 계약

### 7.1 터미널 — 기본 사용이 여기서 완결되어야 한다

다음은 가상의 화면 예시다.

```text
Project Flow · sample-app          분석 기준: 2026-09-22 14:30

[01] 로그인 유지 문제
  ├──> [02] 방식 A 구현
  │       └──> [03] 테스트 실패 / A 철회
  └──> [04] 방식 B 채택
          └──> [05] 완료 보고 / 실행 결과 미확인

선택 [04]  테스트 실패 후 대안을 채택한 기록이 있음.
근거: 대화 2건 · 관련 diff 1건

[R 새로고침]  [B 브라우저 상세]  [Q 종료]
```

단순 로그 화면만 제공해서는 FR-10을 충족하지 못한다. 반면 브라우저와 완전히 같은 배치를 재현할 필요는 없다. 간략 보기에서 생략한 사건 수와 세부 연결의 존재를 알 수 있어야 하며, 분기·실패 경로를 삭제해 허위의 직선 흐름을 만들면 안 된다.

분석 기준 시각과 마지막 확인 시각을 구분한다. 켜 둔 동안 자동 확인하지 않으므로 ‘항상 최신’이라고 표시하지 않는다. 최소 상태는 분석 중, 완료, 변경 없음, 부분 분석, 실패, 중단이다.

### 7.2 브라우저 — 상세 근거 확인

Mermaid로 상세 그래프를 표시하고, 사건별 설명·상태·한계·원문·관련 diff를 제공한다. TUI와 동일한 그래프 버전과 사건 ID를 사용한다. 별도 가입·클라우드 업로드는 요구하지 않는다.

SSH 환경에서 서버가 PC 브라우저를 자동 제어하려 하지 않는다. 서버의 로컬 상세 뷰어 주소와 포트 포워딩 안내를 보여주는 것으로 시작한다. 자동 창 배치·원격 연결 관리 기능은 만들지 않는다.

## 8. 복원 품질 원칙

| 원칙 | 허용하지 않는 해석 |
| --- | --- |
| 수행 주체 보존 | AI가 제안하거나 스스로 결정한 내용을 사용자가 승인한 것으로 바꿈 |
| 근거 수준 분리 | ‘완료했다’는 보고를 테스트로 검증된 성공으로 표시 |
| 관계에도 근거 | 시간상 뒤에 나왔다는 이유로 앞 사건이 원인이라고 확정 |
| 병렬 맥락 보존 | 다른 worktree의 코드·결과를 같은 실험이나 구현에 귀속 |
| 과거와 현재 구분 | 현재 파일·브랜치를 과거 작업 당시의 상태로 표시 |
| 실패와 철회 보존 | 채택되지 않은 시도나 이후 철회를 성공 서사에서 삭제 |
| 모르는 것은 남김 | 누락된 로그나 소실된 diff의 내용을 추측으로 보충 |

사용자가 확인하는 것은 **프로젝트의 근거**다. 분석 프롬프트·중간 JSON·내부 도구 호출 순서는 기본 사용자 기능이 아니다.

## 9. 저장·비용·실패에 대한 제품 약속

저장 그래프와 처리 상태는 로컬 데이터가 기준이다. 같은 worktree 집합의 분석 상태를 공유하되 출처는 구분한다. 원문 경로만 저장하지 않고 실제 인용한 내용도 보존한다. 전체 계정의 대화 영구 백업 서비스는 만들지 않는다.

‘중복 분석 없음’은 **정상 저장된 동일 작업을 재사용한다**는 의미다. 모델 응답 직후 저장 전에 프로세스가 강제 종료되는 등 확인 불가능한 경우까지 외부 모델 호출의 정확히 한 번 실행을 보장하지는 않는다.

Runner·프롬프트를 바꿔도 과거 전체를 몰래 재분석하지 않는다. 새로운 구간부터 새 설정을 적용하고, 필요한 범위의 재분석은 명시적인 요청으로 수행한다. 로그의 내용이 수정되면 그 변경에 의존한 결과만 재검토한다.

비공개 대화와 코드가 저장되므로 저장소와 내보내기 파일은 민감 자료로 취급한다. 제품을 로컬에서 실행한다는 이유만으로 클라우드 모델에 자료가 전송되지 않는다고 표현하지 않는다.

## 10. 수용 기준과 릴리스 판단

다음은 출시 전에 확인할 기준이며 현재 달성된 결과가 아니다. 구체적인 테스트 입력과 검사 항목은 SPEC §13에 연결한다.

| 검증 범주 | 반드시 확인할 결과 |
| --- | --- |
| 두 입력 × 두 Runner | 두 출처가 섞인 기록을 Codex와 Claude Code 각각으로 분석할 수 있음 |
| 연구·개발 사례 | 가설·방법 변경과 요구사항·구현·테스트 흐름을 같은 엔진에서 표현 |
| 근거 무결성 | 저장되는 사건·관계의 출처가 존재하며, 인용된 원문 범위가 일치 |
| 무변경 재실행 | AI 호출 0회, 사건 중복 없음, 그래프 내용 불변 |
| 이어진 세션 | 과거 전체 재분석 없이 추가 기록과 영향받은 연결 갱신 |
| Worktree | 병렬 결과 오귀속 없이 하나의 프로젝트 아래에서 표시 |
| 장애 복구 | 완료 단계 재사용, 이전 그래프 보존, 실패 범위 표시 |
| 사용자 경험 | 터미널에서 흐름 확인, 브라우저에서 같은 사건의 근거 확인 |
| 관측 분리 | 개발용 추적을 꺼도 모든 사용자 기능이 작동 |

품질 평가에는 사람이 내용을 확인한 작은 실제 표본과 익명화·합성 fixture를 사용한다. 모델 평가 점수 하나를 정답으로 삼지 않는다. 위험한 오류가 발견되면 해당 사례를 회귀 테스트로 남긴다.

## 11. 구현 순서와 남은 확인

| 순서 | 산출물 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1. 연동 확인 | 실제 로그 fixture, 두 CLI의 제한된 호출 시험 | 입력 필드·출력·권한·인증·한글 렌더링의 확인 결과 기록 |
| 2. 작은 수직 구현 | 수집 → AI 분석 → SQLite 저장 → 터미널 흐름 | 알려진 사례의 사건·근거가 맞게 연결 |
| 3. 증분·복구 | 무변경·세션 연장·실패 재시도·worktree 시험 | 재호출과 중복 저장 관련 테스트 통과 |
| 4. 상세·출력 | 브라우저 근거 보기, JSON·mmd·md 내보내기 | 같은 그래프·사건 ID로 일치 |
| 5. 회귀 확인 | 두 Runner 평가, 개발용 진단 | 알려진 고위험 오류와 범위 누락 점검 |

첫 실제 프로젝트와 로그 표본, 제품 최종 이름·오픈소스 라이선스, 지원 CLI 버전, 터미널 Mermaid 렌더러는 아직 확정하지 않았다. 구현 검증으로 결정하되, 새 제품 기능을 추가할 근거로 사용하지 않는다.

## 12. 결정 근거와 변경 관리

아래는 이 대화에서 확정된 요구의 핵심 표현이다. 인용은 사용자 발언이며 외부 제품에 대한 사실 주장과 구분한다.

| 결정 | 근거 |
| --- | --- |
| 단일 폴더 중심 | “특정 폴더 내부에 모든 프로젝트가 진행된다고 생각하는게 편하지 않을까?” |
| 두 입력과 worktree | “대표적으로 codex, claude code 이렇게 두 개만 지원”, “git worktree도 지원” |
| 실제 AI 분석 | “ai가 그 기록들을 읽고 진행해야”, “git diff까지 활용” |
| 저장·증분 처리 | “분석한 것을 저장”, “예전에 분석했던 것을 다시 분석하면 안”, “세션을 처음부터 분석할 필요는 없” |
| 두 Runner | “claude code 와 codex 이 두 개는 한번에 지원하는게 좋을듯” |
| 터미널 우선 | “terminal에서는 단순히, 브라우저에서 자세히?” |
| 수동 갱신 | “실시간은 일단 포기”, “프로그램을 실행할 때”, “새로고침 버튼” |
| 사용자 Trace 제외 | 추적의 사용자 노출에 대한 범위 축소 제안 후 “그건 그렇게 진행하자”로 합의 |

**이 PRD의 포함·제외 범위가 이전 대화의 개별 제안보다 우선한다.** SPEC의 기술 선택은 구현안이며, 보류 기능을 추가하려면 PRD 범위 변경을 먼저 명시한다.
